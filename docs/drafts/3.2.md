## Why

CodeQL, Glean's Angle, jQAssistant's Cypher, NDepend's CQLinq and Joern let a user ask a question the tool's
authors did not foresee: "functions that write storage and are reachable from an HTTP handler". Verinoda had
fixed views over the graph (`trace` between two named symbols, `map`, `dsm`, `butterfly`, `routes`) and
`inventory`, whose condition language counts search hits but knows nothing about edges. A question that combines
kinds of nodes, a path of bounded length, a condition on a definition's text and an absence of an edge had to be
answered by chaining commands by hand, and nothing cited the evidence of the whole answer. Done when: a query such
as "functions that write storage and are reachable from an HTTP handler" returns its sites.

## Decisions

- **New command `verinoda q "QUERY" [--max-rows N] [--max-expansions N] [--timeout S] [--verify] [--json]`**
  (module `verinoda/graphquery.py`). The name `query` is taken by the ranked retrieval, so the command is `q`. CLI
  only: no MCP tool is added (the count stays 40) and none goes behind `run_tool`, so the core menu is unchanged.
  Exit 0 with rows, 1 with none, 2 on a bad query, 3 when a budget cut the answer.
- **A small Cypher-like language, nothing more.** `MATCH pattern (',' pattern)* [WHERE cond] [RETURN items]
  [LIMIT n]` (the leading `MATCH` may be left out). A node is `(var:kind|kind)`; the kinds are `file`, `symbol`
  (any code symbol), `function` (functions and methods), `method`, `class`, `handler` (a handler in the HTTP route
  table, the table of `verinoda routes`), `test` (code in a test file, `testcode.is_test_file`) and `section` (a
  heading of a document). An edge is `-[rel|rel*lo..hi]->`, `<-[...]-` or `-[...]-` (either way); no relation
  means any; a length is at most 10 (`*` alone is `1..5`, `*2` exactly two, `*..4` is `1..4`, `*0..1` includes the
  start). Patterns separated by commas join on shared variables. `WHERE` compares `var.field` with a string, a whole
  number or another `var.field`: `name` (the bare name), `label`, `file`, `id` by `=`, `!=`, `~` (a Python regular
  expression, searched, at most 300 characters) and `glob`; `line` by `=`, `!=`, `<`, `<=`, `>`, `>=`; `text` (the
  lines of the node's definition, nested definitions included; a file node's whole file) by `~` only; with `and`,
  `or`, `not`, parentheses and `exists (pattern)`. `RETURN` lists variables, `var.field` and `count(var)` (distinct
  nodes) or `count(*)` (bindings), grouped by the other items; without `RETURN` every named variable is returned.
  Keywords are read in any case. Edge variables, `OPTIONAL MATCH`, `ORDER BY`, `UNION`, sums and arithmetic are
  not in the language: each is a way to write a program, and the point is a query whose every answer can cite its
  lines.
- **Parsed by hand, checked before it runs.** A tokenizer that keeps each token's offset and a recursive-descent
  parser; no `eval`, no `ast` of Python, nothing of the query is ever executed (a regular expression is compiled by
  `re`). Before evaluation the tree is checked: every variable of `WHERE` and `RETURN` is bound by `MATCH` (a
  variable new in an `exists` pattern is existential and cannot be named outside it), the field fits its operator
  (`text` only with `~`, `line` only with numbers), each regular expression compiles, a relation is one the graph
  has or one Verinoda makes (a known relation with no edge is answered with no row and a note; an unknown one is
  refused with the relations the graph has), a node pattern has at most 12 nodes, a query at most 8 patterns and
  4,000 characters, a condition at most 30 levels. An error is `QueryError` with the offset; its text names the
  line (for a query of several lines) and the column and draws a caret under the place (`--json`: `position`).
  Unnamed nodes get names the query cannot spell (`#1`), so `(_1)` is the user's own variable.
- **Evaluation.** Over the loaded graph (`index.load`: the receiver, Java and cross-service edges included). The
  `WHERE` conjuncts that read one variable are pushed to it and checked when it is bound (cached per node), the
  others after the patterns matched. Each pattern is walked from its bound end, else from the end with fewer
  candidates by kind (a `handler` end starts from the route table; a first end with at most 64 candidates is
  walked from without listing the other end's). A one-step edge takes, per neighbour, the best
  edge between the two (`EXTRACTED` first, then the lowest line). A bounded edge is a breadth-first walk that keeps
  one path per end node: the shortest, and at that length one with no `INFERRED` edge when there is one; with a
  lower bound above one it walks level by level, so a node reached at length one can still be an end at length
  three. `exists` stops at its first match and, when it is not negated, its edges are cited with the row.
- **Every row cites its evidence.** Per named variable: its definition (`file:line`) and kinds; every edge of the
  paths that bound it (from, to, relation, confidence, `file:line` of the call); the lines a `text` condition
  matched (three per node, read now); for a handler, its route (`POST /orders`) and the route declaration. A row
  that several bindings produce cites the strongest one and says how many (`bindings`). A count row cites three
  example bindings.
- **Status honest per the evidence rules.** Graph edges are extractions: a row is `strong_inference` when every
  edge it rests on is `EXTRACTED`, `weak_inference` when one is `INFERRED` (with the reason in `uncertain`), and
  `unknown` when it cites a file that `freshness.check` finds changed since the index (`stale_files`); the result
  also says how many files changed and that rows through them may be missing. A count row is the weakest of its
  bindings. `NOT EXISTS` reads an absence in the graph: every row of such a query says that an edge the extraction
  cannot see (dynamic dispatch, reflection) is not there. Nothing is ever above `strong_inference` without
  `--verify`.
- **`--verify` re-reads, as `analyze` does.** Each call edge of the row is graded with `entail.call_site` (the
  check behind `analyze`'s relation claims); each definition line must still name its symbol; a route must be
  parsed from Python (the route table is read from the current files). A row becomes `statically_verified` only
  when every edge is an `EXTRACTED` `calls` edge whose Python call site grades `full`, every definition line names
  its symbol, nothing is stale and no part is an absence; otherwise it keeps its status and `verified` lists what
  was not confirmed (an `INFERRED` edge, a `contains` or `method` edge no call site can show, code outside Python,
  an absence). A row citing a stale file is `not checked`. Counts are not re-read (said in a note).
- **Budgets.** Rows (default 200), expansions (every edge looked at, every node checked: default 1,000,000) and
  seconds (default 30, checked at every start node and every 1,024 expansions). A budget that runs out stops the
  walk: the rows found so far are returned, `complete` is false, `truncated` names the budget, and the note says
  rows may be missing and counts and bindings are lower bounds. `LIMIT n` stops at the n-th distinct row and says
  whether more exist (`limited`, not a cut). A count's groups are all counted; `--max-rows` only cuts how many are
  listed (`groups_total`, and a note).
- **No stored query fact.** `fact add --query` was considered: a query fact would rest on the whole graph like a
  search fact over the whole project. The `facts` table's `kind` has a `CHECK (kind IN ('derived','search'))`, and
  SQLite changes a check only by rebuilding the table, a schema migration out of proportion for this item; a query
  stays a command to re-run.

## Measured

On this repository's own index (the main checkout's, read without writing: the graph loaded with the sidecar
edges it already had; 36,028 nodes, 88,526 edges; 43 files had changed since that index), Windows, the graph
loaded once (1.60 s, not counted below), three runs each, the freshness check and the route table included:

| query | time | expansions | answer |
|---|---|---|---|
| `match (h:handler)-[calls*1..4]->(f:function) where f.text ~ "INSERT INTO\|UPDATE .* SET\|DELETE FROM\|\.commit\(" return f, h` | 2.13 s first, 0.89-0.93 s after | 1 | no row: the route table found no handler in this repository |
| functions under `verinoda/` that reach `write_json_atomic` within three calls, `count(f)` | 1.43-1.50 s | 148,555 | 23 |
| functions under `verinoda/` with no `calls`, `indirect_call`, `references` or `registers` edge in, `count(*)` | 0.97-0.98 s | 93,335 | 1,137 |
| two functions under `verinoda/` that call each other (a join of two patterns) | 1.20-1.31 s | 115,480 | none |
| functions under `verinoda/` counted by file, `limit 5` | 0.78-0.87 s | 43,440 | 5 groups (4 `unknown`: their files had changed) |

The first run of the handler query includes reading the route table the first time (`cross_service.collect`,
facts reused from the sidecar by hash); before the handler end was walked from without listing the other end's
candidates, the later runs took 1.24-1.27 s. `match (a)-[*1..6]-(b) return count(*)` with `--max-expansions
200000` stopped at 200,001 expansions in 1.62 s; with `--timeout 1` it stopped and returned after 1.24 s, the
freshness check made before the clock starts included. Under `cProfile` the grouped count took 3.95 s while
`Graph.is_file_node` (a `PurePosixPath` per node) was asked for every node and 2.51 s once the kind of a node was
computed with string operations; the `method` edges' ends were then collected in one pass (not measured apart).

On the test fixture (six files, a Flask app): the done-when query returned its one row, `save_order()` reached from
`post_order()` through `create_order()`, with the route `POST /orders`, both call sites and the `INSERT` and
`commit()` lines, `statically_verified` with `--verify`, in 0.099 s (23 expansions); `write_log()`, which also
writes but is reached only from a function that is no handler, was not listed. The other fixture queries took
0.04-0.05 s.

## Limits

- One path is cited per pair of ends (the shortest); a query cannot ask for all paths or for a path avoiding a
  node. With a lower bound above one a path is a walk and may repeat a node.
- `handler` is the HTTP route table only (Flask, FastAPI, Django, Express, Spring and the other frameworks of
  `verinoda routes`); RPC procedures and event listeners are not handlers here. It is read from the current files
  and placed on the index's symbols: in a file changed since the index the row is `unknown`.
- `--verify` confirms Python call sites of `EXTRACTED` `calls` edges and definition lines; any other relation, an
  `INFERRED` edge, code in another language or an absence keeps the row at its inference status.
- An absence (`not exists`) is as complete as the extraction: a call it cannot see (dynamic dispatch, a call
  through a variable, reflection) is missing, and such rows are never verified.
- Rows through a file changed since the index may be missing; the result says how many files changed, not which
  rows are missing.
- The time budget is checked between nodes and edges: a regular expression that backtracks badly on one long line
  is not interrupted.
- A start variable with no bound end and no `handler` kind scans every node of the graph (the grouped count above,
  which does little else, took 0.78-0.87 s on this repository); conditions over two variables are checked after all patterns matched, so a join is pruned only by
  its shared variables.
- No `fact add --query` (the facts table's kind check would need a table rebuild), no MCP tool, no `ORDER BY`,
  no edge variables or edge conditions (confidence, line), no `OPTIONAL MATCH`, no sums.
- `function` includes methods; a class from a language whose extractor marks neither `_callable_class` nor
  `method` edges is only a `symbol`.

## Upgrading note

New command `verinoda q "QUERY"`: a declarative query over the graph (node patterns with kinds, edges with a
relation, a direction and a bounded length, joins on shared variables, `WHERE` with `not` and `exists`, `RETURN`
with `count`, `LIMIT`) answered with rows that cite their evidence; `--verify` re-reads the cited call sites;
`--max-rows`, `--max-expansions` and `--timeout` bound it. Nothing to migrate; the MCP tools are unchanged (40).

## Tests

`tests/test_query_language.py` (32 tests, one scanned fixture: a Flask app, a service layer, a storage module, a
test file): the done-when query returns exactly the storage writers a handler reaches, with the route, every hop
(relation, confidence, `file:line`) and the matched lines, in JSON and text; an `INFERRED` hop makes its row
`weak_inference` and `--verify` raises only the all-`EXTRACTED` row to `statically_verified`; a join of two
patterns on a shared variable and a comparison of two variables; exact, lower-bounded, incoming and either-way
paths and a `method` edge; `not exists` (no caller, no test within three calls) with its absence said and never
verified, and `exists` with its witness edges; `count(var)` and `count(*)` grouped, a zero count, `LIMIT` on groups
and groups counted but not listed; kinds, fields, `glob`, `~` and line comparisons, and an unnamed node that never
takes the place of a variable named `_1`; 19 errors with their column (unclosed node, unknown kind, field,
relation and keyword, bad range, bad regular expression, a string not closed, a Python call, an edge variable, a
repeated return item) and one with line and column; a known relation with no edge answered with a note; nesting
and size refused; `--max-rows`, `--max-expansions`, `--timeout` and `LIMIT` each stop the answer and say so; a
file changed since the index makes its rows `unknown` with the file named and `--verify` not checking them; the
CLI's JSON shape, its error JSON with the position and the caret on stderr, and exit codes 0, 1, 2 and 3.
