## Why

"Where does this argument's value come from?" is the question a reviewer asks before trusting a call, and the one
taint analysis (the next item) is built on. Joern, GitNexus, narsil-mcp and CodePrism answer it with a program
dependence graph and slices. Verinoda's graph has calls and imports between symbols, nothing inside a function:
the agent reads the function and guesses which assignments and branches matter. Done when: a slice answers
"where does this argument's value come from" with its lines.

## Decisions

- **New command `verinoda slice PATH:LINE [--var NAME] [--arg N|NAME] [--forward] [--depth N] [--json]`**
  (module `verinoda/slicing.py`), Python only, computed from the file as it is now (no index needed inside a
  function; the index is read only to follow callers). CLI only: no MCP tool.
- **A control-flow graph per function, statements as nodes.** A compound statement is its header (an `if`'s test,
  a `for`'s target and iterable, a `with`'s items, an `except`'s type and name, a `case`'s pattern and guard).
  Edges follow `if`/`elif`/`else`, `while` and `for` with their `else` and `break`/`continue`, `return`, `raise`,
  `try` (every statement of a try body may jump to each of its handlers, and to `finally`), `with`, `match`.
  Nested functions and classes are one statement that defines their name and reads their decorators, defaults and
  (for a function) the free names it uses.
- **Definitions and reads.** A name assigned (`=`, annotated, augmented, `for` and `with` targets, `except ... as`,
  imports, walrus, `case` captures) replaces earlier definitions; `x.a = v`, `x[i] = v` and a method called on a
  name as a statement (`items.append(v)`) update `x` - they define it without replacing what it held, and read
  it. Names a comprehension or lambda binds for itself are not reads of the function's names.
- **Reaching definitions** by an iterative data-flow analysis; **control dependence** from post-dominators
  (bitsets, then each branch edge walked up the post-dominator tree), so a statement after an `if` that returns or
  raises depends on that `if`, and a loop body on the loop's test. A node that never reaches the exit (inside
  `while True` with no way out) depends on nothing.
- **Backward slice:** from the criterion's reads (`--var`: one name read or defined there; `--arg`: the names of
  one argument of the call on the line, by position or keyword; default: every name it reads), the definitions
  that reach them, their reads in turn, and the branches every node in the slice depends on. A name with no
  definition in the function (module, builtin, closure) is listed, not guessed.
- **Across callers:** when the slice reaches a parameter, the index's `calls` edges into the function (found by
  name and definition line; by name alone, with a note, when the index is older than the file) give its call
  sites; the call of that name at the cited line is read, the parameter mapped to its argument (keyword first,
  then position, `self`/`cls` dropped for a call through an attribute, `*args` makes it unknown) or to its default
  value, and that argument sliced in the caller - up to `--depth` calls up (default 2, at most 3) and 8 call sites
  per parameter. A call site that cannot be read is listed with why (`unknown`), never dropped.
- **Forward slice (`--forward`):** from the definitions at the line, every node they reach and are read at,
  transitively, and the nodes a predicate among them controls.
- **Output:** each line with its role (`criterion`, `def`, `control`, `use`, `controlled`), the names it defines
  and reads, and the data (definition -> read, with the name) and control edges. Status `strong_inference`: the
  lines are read from the source, the dependence between them is the analysis's (the heap is approximated), never
  an observation. Exit 2 for a line outside a function, a file that does not parse, or a name or argument not on
  the line; a function over 4,000 statements is not analysed.

## Measured

On this repository (the main checkout's index of 2026-09-30, graph loaded once in 2.1 s), backward slices of the
last `return` of the two largest functions of four large files, callers followed to depth 2: `review.review`
(227 lines) 126 slice lines and 33 call-site hops in 6.7 s (19.8 s before parsing each caller file and function
once per slice); `review._guard_diff` (194 lines) 83 lines, 1.9 s; `analysis.analyze` (228 lines) 53 lines and 26
hops, 3.6 s; `codecheck._api` 0.6 s; `cli.build_parser` (1,095 lines) 1.0 s. On the test project the
done-when holds: the second argument of `db.execute(...)` in `save` is traced to `amount` in `checkout` (its
`= 0`, the loop over the cart, `+= price_of(...)`, the `if not cart: raise` that decides the call) and on to the
`cart` that `handler` reads from the request.

## Limits

- Python only; one function at a time plus its callers' arguments: a value returned by a called function is a read
  of that call's names, the callee's body is not entered.
- The heap is approximated: aliasing (`b = a; b.append(x)` does not update `a`), attributes as separate locations,
  globals or attributes changed by other functions, `exec`/`eval`, `getattr` and `setattr` are not seen.
- Exceptions raised inside called functions are not followed; any statement of a try body may reach its handlers.
- Callers come from the index (an INFERRED edge is a resolver's guess; its confidence is shown per hop) and are
  matched by the callee's name at the cited line; a call through a variable or `functools.partial` is not found.
- No query over the dependence graph yet (taint, the next item, builds on it); no CFG or PDG export.

## Upgrading note

New command `verinoda slice PATH:LINE` (`--var`, `--arg`, `--forward`, `--depth`): a backward slice of a Python
line inside its function, across callers' arguments via the index, or a forward slice. Nothing to migrate.
