# 6.1 Dead code

Row: symbols and files no entry point reaches; zero-caller functions; orphan modules. Done when each dead
symbol is a claim naming the entry points searched and the dynamic uses that could keep it alive.

## Decisions

- **A map view, not a new command or MCP tool.** `verinoda map --view dead [--json]` and the MCP `map_view`
  (reached through `run_tool`, so the core profile stays at five tools). Dead code is a whole-project view like
  the other map views; it reuses their `coverage.method` / `coverage.limits` contract, the text renderer and
  the `--max-lines` cap.
- **Roots.** `architecture_map.entry_points` (the dataflow view's entries: framework entries, route/command
  decorators, entry-like names, public callables of entry modules), every node of test code, entry modules
  (a `__main__` guard, `__main__.py`, `setup.py` / `conftest.py` / `manage.py`-like names, entry-like file
  names, `package.json` `main` / `bin`) and the scripts `pyproject.toml` declares (`project.scripts`,
  `gui-scripts`, `entry-points`, `tool.poetry.scripts`).
- **Reachability** follows every graph edge but containment and documentation (`contains`, `defines`,
  `method`, `rationale_for`, `cites`). Extra steps the graph does not hold as edges: a reached symbol reaches
  its module and the package `__init__.py` files above it; a method its class; a class its protocol members
  (dunders, constructors); a method the same-named methods of project subclasses (dynamic dispatch); a
  function the functions and classes its body defines.
- **One claim per unit.** An unreached file whose code is all unreached is one `orphan_file` claim (its symbols
  counted as `members`); else an unreached class (members folded under it); else a function or method, as
  `zero_callers` or `callers_unreached` (the callers named with their call sites). Unreached dunders and
  constructors of a reached class are not claimed (`kept_by_protocol`).
- **Dynamic uses** (what could keep it alive), each with `kind`, `at` (file:line) and `why`: the name in a
  string (getattr, reflection, registries), in a config/data/build file, or in code the graph did not resolve;
  a decorator or annotation that may register it (plain ones such as `staticmethod`, `property`, `@Override`
  excepted; `@Override` is its own `override` use); a class extending a type outside the project (a method may
  override one called through it); a framework naming convention (pytest hooks, unittest fixtures,
  `load_tests`); and `via`: reached from an unreached unit that a dynamic use could keep alive. The known
  unreached callers' own call sites and definition lines are not counted as mentions.
- **Status.** Reachability over extracted edges is a heuristic: `strong_inference` at most, `weak_inference`
  when any dynamic use was found. Never `verified`. Claims are returned, not stored in the claim store (the
  view is recomputed per index, like the other map views).
- Every claim carries `entry_points_searched` (counts of entry points, test-code nodes and entry modules; the
  same text is in the claim sentence), `evidence_at` (the definition, then the callers' sites) and `derived_by`.
  The view's `searched` block lists the entry points (first 100, with `why` and `basis`), entry modules and the
  relations followed. Output is capped at 80 claims (`truncated`, `claims_not_shown`).

## Measured

On a copy of Verinoda itself (HEAD of this branch's base, `verinoda/` + `tests/` + `pyproject.toml`): 6289 code
symbols, 251 entry points, 19 entry modules, 3164 test-code nodes searched; 667 claims (5 files, 662 symbols):
43 `strong_inference`, 624 `weak_inference`. Spot check of five strong claims (`turkish_intents`,
`kotlin_files`, `_guard_desc`, `_py_def_ends`, `graph_diff`): each name occurs only on its definition line in
`verinoda/` and `tests/`, so all five are dead. The run took about 4.5 minutes including the first scan.
`examples/orders_app`: one claim, `load_settings()` (defined, never called), `strong_inference`.

## Limits

- Calls the extractor does not resolve (reflection, getattr, dependency injection, routing tables) are not
  edges; the name search stands in for them and makes the claim weak. On a large project most claims are weak
  because common names appear elsewhere; the strong ones are the actionable list.
- Entry points are heuristic; a library's public API that other projects call is not an entry point, so a
  library's unused public functions are reported (weakened when named elsewhere).
- Python module-level calls are not graph edges: a name a reached module imports counts as used through the
  module.
- Code reached only by tests counts as reached (a test is a root).
- Detected copies and reference trees are searched from but not reported.
- The name search reads the code, config and build files of the project (files over 2 MB skipped, comment
  lines skipped); prose documents are not a use.

## Upgrading note

`verinoda map --view dead` and MCP `map_view {view: "dead"}` are new; no existing view, output field or
default changes. Nothing is stored; the index format is unchanged.
