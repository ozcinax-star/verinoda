## Why

The change review says which tests reach a change (the test map, static reach), and `review --run-tests` says whether
they pass. Neither says whether those tests *check* the change: a test that calls a changed function and asserts
nothing about the changed branch passes before and after any edit to it. Mutation testing answers that directly
(mutmut, cosmic-ray, PIT, cargo-mutants, Stryker), but run over a whole project it costs hours. Scoped to the lines
a diff changed and to the tests that reach them, it costs one test run per mutant and answers the question a
reviewer has: is this change tested, or only executed?

## Decisions

- New command `verinoda mutate [--base REF] [--tests TEST_ID ...] [--file PATH] [--max-mutants N] [--timeout S]
  [--json]` (module `verinoda/mutate.py`). Python only; no MCP tool (each mutant is a test run: too slow for an
  agent's turn by default).
- **Changed lines:** the added and replaced lines of the working tree against the base (default HEAD), in `.py`
  files that are not tests or test support, from `treestate.changes_vs_base`. Deleted lines have nothing to mutate.
- **Operators**, one mutant per site on a changed line: comparison swaps (`<`/`<=`, `>`/`>=`, `==`/`!=`,
  `in`/`not in`, `is`/`is not`), `+`/`-`, `*`/`/`, `//` -> `*`, `and`/`or` (two operands), `True`/`False`, an
  integer `n` -> `n+1`, `not x` -> `x`, an `if`/`while` condition negated (single-line conditions), `return x` ->
  `return None`. A fixed, small set chosen for the faults reviews miss (off-by-one, inverted conditions, ignored
  results), not completeness.
- **Splicing, not unparsing:** each mutant replaces one span of the source text at the AST's offsets (UTF-8 columns
  converted to characters), so the rest of the file is byte for byte the same and line numbers in failures match.
  An operator is located in the text between its two operands with comments blanked, and only when exactly one
  match is there. Docstrings and comments are never mutated. A mutant that does not compile is dropped; identical
  texts are one mutant. At most `--max-mutants` (default 25, cap 500) are run, in source order; the rest are
  counted (`not_run_over_limit`), never silently dropped.
- **Tests:** the change review's `affected` block (the test map's observed tests, tests the change edits, static
  reach), or `--tests`. No test: status `no_tests` with a next step.
- **Runs:** every run is an experiment (`experiments.run`) on a copy of HEAD with the working tree's changed files
  replayed on top (deleted ones left out), and the mutant on top of that: the same command policy, trust rule and
  isolation as any test run (an untrusted project runs only in a container). The command is `python -m pytest -q
  -x -p no:cacheprovider <test ids>`.
- **Baseline first:** the selected tests run once on the unmutated change. When they do not pass, no mutant can be
  judged and none is run (`baseline_failed`, or `not_run` when the run was refused or inconclusive).
- **Verdicts:** `killed` (the tests failed), `survived` (they passed), `timeout` (counted apart: nothing failed),
  `not_run` (refused or inconclusive). Each row carries its experiment id and `status: observed` (what that run
  showed). A survivor carries a `strong_inference` claim "the selected tests do not check path:line": never
  verified, since the mutant may be equivalent and the selection may have left out a test that kills it.
- **Exit codes:** 0 when every mutant run was killed and none was left out, or no mutant could be made; 2 on an
  error (bad arguments, not a git work tree); 3 otherwise (survivors, a timeout, a run not made, mutants over the
  limit, no test, a failing baseline).

## Measured

- A scratch repository with `price(n, vip)` changed to `if vip and n > 5: return n - 1` and one test that calls
  `price(10, False)`: 7 mutants, 2 killed (`and` -> `or`, the negated condition), 5 survived on lines 2 and 3 -
  the test never takes the `vip` branch. About 20 s in total (8 runs of one test, each a copy of the repository),
  so about 2.5 s per mutant on that repository; a run costs what copying the repository and one pytest start cost.
- With no `--tests`, the change review selected the one test by static reach.

## Limits

- A surviving mutant may be equivalent to the original; it is a lead, not proof.
- Only the selected tests run. A test the selection left out may kill a survivor; name more with `--tests`.
- Python only; a fixed operator set; no mutants on deleted lines or in non-Python files; multi-line conditions are
  not negated; comparisons with more than one operator (`a < b < c`) and `and`/`or` with three or more operands are
  left alone.
- Each mutant is one full run of the selected tests in a fresh copy of the repository: large repositories pay the
  copy every time. Mutants run one after another.
- `-x` stops at the first failing test, so a killed mutant names no test that killed it beyond its experiment's log.

## Upgrading note

New command `verinoda mutate`: mutation testing scoped to the diff (Python). It runs the selected tests once per
mutant through `experiments.run`, so each mutant is a recorded experiment under `.verinoda/runs/`. Nothing else
changes; no MCP tool changes.

## Tests

`tests/test_mutate.py`: mutants only on changed lines, never in docstrings or comments, the rest of the file
unchanged, every mutant compiles; the operator set and deduplication; non-ASCII offsets; unparseable text gives no
mutant; changed-line detection; an end-to-end run on a scratch repository (a path with a space and `ş`) where the
negated condition is killed and the untested branch's mutants survive with their line, experiment and a
`strong_inference` claim, with the over-limit count; a failing baseline runs no mutant; CLI exit codes (0 nothing
to mutate, 3 when mutants exist but were not run, an argument error).
