# Specs traced to code and tests (`verinoda spec check`)

## Why

Kiro specs, GitHub spec-kit and Tessl keep requirements next to the code, but nothing checks that a
requirement is still backed by anything: a test gets renamed, a claim goes stale, a function moves, and the
spec keeps saying the system does X. Verinoda already has the pieces (claims with a status, file:line
evidence, symbol facts per file, test detection); this decision joins them to requirement criteria and makes
the unbacked ones visible, with an exit code a CI job can read.

## Decisions

- **Format.** A spec is a Markdown file (`.md`, `.markdown`) anywhere under the specs folder. A criterion is a
  line that starts, after an optional list marker or bold, with an id in brackets holding a digit
  (`[CART-1]`, `[R1]`, `[AC-2.3]`; a task box `[x]` is not one). The EARS style is recommended, not required:
  the criterion's EARS pattern is named (`event` WHEN, `state` WHILE, `unwanted` IF, `optional` WHERE,
  `ubiquitous`), or null without a SHALL. `evidence:` lines under a criterion (any number, until the next
  criterion or heading) list references separated by commas or spaces; one with spaces goes in backticks.
  Fenced code is skipped.
- **Folder.** `.verinoda/specs/` by default, like the decision records; a committed folder for CI through
  `[specs] dir` in `verinoda.toml` or `[tool.verinoda.specs] dir` in `pyproject.toml` (read with the same
  helper as the decisions folder), `specs.dir` in `.verinoda/config.json`, or `--specs-dir`. A folder outside
  the repository is an error.
- **References are written, never guessed.** A claim id (`clm_...` or `claim:ID`); a test id `path::name` or
  `path::Class::name` in a test file (parameters ignored), or `test:ID`; `path::Name` in other code;
  `path:12` / `path:12-30`; a bare path; `code:` forces a path. Nothing is matched by text similarity: a
  criterion with no reference is unevidenced, and no suggestion is made.
- **What counts as evidence.** A claim whose recorded status is verified (observed, experiment, static,
  primary source), or a test that is defined in the file. A code pointer is checked to resolve but only shows
  where the behaviour lives, never that it holds; an inference claim is not evidence.
- **How a reference resolves.** Paths compare with their case on disk (a case-insensitive file system would
  accept `SRC/a.py`), names in NFC (macOS may store them decomposed), and a link leading outside the
  repository does not resolve; a definition is found in the file's facts (`anchors.facts_for_path`: Python and the
  tree-sitter languages), exactly for a test, by name for code. Where a language has no facts the name is
  searched as a word, and a test absent from the facts is searched as a quoted title (`it("adds an item")`);
  both say so and are `strong_inference`. Lines must be inside the file.
- **Criterion status**, strongest problem first: `broken` (a reference does not resolve, or cites a stale or
  contradicted claim; a newer claim superseding it is named), `verified`, `tested`, `unchecked` (a claim with
  no Verinoda state to read it from: the check opens the store read-only and never creates it),
  `unevidenced`.
- **Exit codes**, as the other checks: 1 while a criterion is broken or unevidenced or a spec line has a
  problem (a SHALL line with no id, an evidence line with no criterion above it or with nothing on it, an id
  used twice: compared case-insensitively, across files); else 3 when something was not checked (unchecked
  claims, a spec file too large or unreadable, a configured folder that does not exist); 2 on an error; 0
  otherwise. The default folder missing is `no_specs`, exit 0.
- **Lines** are split at LF only, a CR before it dropped, so a CRLF file or a Unicode line separator inside
  a sentence keeps the line numbers an editor shows. A criterion's sentence may wrap onto the following lines;
  `none`, `tbd` and `todo` on an evidence line are no reference. A closing fence must be as long as the
  opening one.
- CLI only (`spec check [--specs-dir DIR] [--json]`); no MCP tool, so the core menu does not change.

## Measured

- A five-criterion spec over this repository's own tests and code: 2 tested, 1 unevidenced (lines only),
  1 broken (a test name and a file that do not exist), 1 unchecked (a claim with no store), exit 1, in 0.68 s
  wall time including the interpreter start.
- 14 tests in `tests/test_specs.py` cover each status, each reference kind, CRLF, a non-ASCII repository
  path, duplicate ids, fences, task boxes, wrapped sentences, path case, paths outside the repository, an
  unread file and the folder settings.

## Limits

- Whether the cited claim or test really covers the criterion is the author's statement; it is not judged.
- Claim statuses are read as recorded; `verinoda update` marks claims stale after code changes, so run it
  first.
- A test is checked to be defined, not run, and its last outcome is not read.
- Kiro's and spec-kit's own files are not read as they are: their criteria need an `[ID]` added.
- No suggestion of tests or code by name for an unevidenced criterion.

## Upgrading note

New command `verinoda spec check [--specs-dir DIR] [--json]`: requirement criteria (`- [ID] WHEN ... THE
SYSTEM SHALL ...`) in Markdown files under `.verinoda/specs/` (or `[specs] dir` in `verinoda.toml`) with
`evidence:` lines naming claim ids, test ids, `path::Name` or `path:lines`; each criterion is verified,
tested, broken, unchecked or unevidenced. Exit 1 while one is broken or unevidenced, 3 when something was not
checked. Nothing changes for projects without specs.
