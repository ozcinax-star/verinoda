# Specs traced to code and tests (`verinoda spec check`)

## Why

Kiro specs, GitHub spec-kit and Tessl keep requirements next to the code, but nothing checks that a
requirement is still backed by anything: a test gets renamed, a claim goes stale, a function moves, and the
spec keeps saying the system does X. Verinoda already has the pieces (claims with a status, file:line
evidence, symbol facts per file, test detection); this decision joins them to requirement criteria and makes
the unbacked ones visible, with an exit code a CI job can read.

## Decisions

- **Format.** A spec is a Markdown file (`.md`, `.markdown`) under the specs folder. A criterion is a line that
  starts, after an optional list marker, task box (`- [ ] [R21] ...`) or bold, with an id in brackets holding a
  digit (`[CART-1]`, `[R1]`, `[AC-2.3]`; a task box `[x]` alone is not one; the id is at most 64 characters).
  The EARS style is recommended, not required: the criterion's EARS pattern is named (`event` WHEN, `state`
  WHILE, `unwanted` IF, `optional` WHERE, `ubiquitous`), or null without a SHALL. `evidence:` lines under a
  criterion (any number, until the next criterion, heading, or another list item or paragraph at the
  criterion's indent or less) list references separated by commas or spaces; one with spaces goes in backticks.
  Not read: fenced code at any indent (inside list items too), indented code (four columns past the enclosing
  list item, after a blank line), HTML comments (one line or several) and link reference definitions
  (`[v2]: https://...`, `[RFC2119]: ...`).
- **Folder.** `.verinoda/specs/` by default, like the decision records; a committed folder for CI through
  `[specs] dir` in `verinoda.toml` or `[tool.verinoda.specs] dir` in `pyproject.toml` (read with the same
  helper as the decisions folder), `specs.dir` in `.verinoda/config.json`, or `--specs-dir`. A folder outside
  the repository is an error, and so is a setting that cannot be known: a `verinoda.toml`, `pyproject.toml` or
  `.verinoda/config.json` that does not parse, a `specs` that is not a table or object, a `dir` that is not a
  string (exit 2, never the default folder). The folder is walked without following links or junctions (they
  are listed as skipped), dot folders and vendored folders (`node_modules`, `venv`, `dist`, `build`, ...) are
  left out, and a file whose real path is outside the repository is not read.
- **References are written, never guessed.** A claim id (`clm_...` or `claim:ID`); a test id `path::name` or
  `path::Class::name` in a test file, or `test:ID`; `path::Name` in other code; `path:12` / `path:12-30`; a
  bare path; `code:` forces a path. Nothing is matched by text similarity: a criterion with no reference is
  unevidenced, and no suggestion is made.
- **What counts as a test.** Python: a `test*` function, or a `test*` method of a `Test*` or `TestCase` class,
  not a pytest fixture; a test class stands for the tests it holds (listed). Go: `TestX`, `BenchmarkX`,
  `ExampleX`, `FuzzX`. Java, Kotlin, C#, Rust: a function with a test annotation or attribute (the rules of
  `testcode`). These are definitions read from the file's facts (`statically_verified`). JavaScript and
  TypeScript: the title as the first argument of an `it(` / `test(` call, found by a text pattern, so
  `strong_inference`; a `describe(` suite or an `it.skip` / `todo` is not a test. A helper, fixture, a class
  with no test, or a method of a non-test class is a code pointer; a quoted string anywhere else, and any
  string in a Python file, is never a test. A parametrized id is checked by its function name; the parameters
  are not checked, and the reference says so.
- **What counts as evidence.** A claim whose recorded status is verified (observed, experiment, static,
  primary source) and whose cited file lines (source code, documents, dependency or reference sources, static
  resolutions) still hold the content recorded for them (`evidence.check_source`: the content hash, or the
  anchored symbol for a block that moved); a test as above. A code pointer (`path::Name`, `path:lines`, a
  bare path) is labelled `pointer`: checked to resolve, it only shows where the behaviour lives, never that it
  holds; an inference claim is not evidence.
- **The store is read-only.** It is opened only when a claim is cited, with `sqlite3.connect("file:...?mode=ro",
  uri=True)` (the path URI-quoted, so spaces and non-ASCII names work on Windows), no migration, no journal
  setting, nothing written. A missing store, a file that is not a database, or a schema version other than this
  build's leaves the claims `unchecked` with the reason; a corrupt store is never opened when no claim is cited.
- **How a reference resolves.** Paths compare with their case on disk (a case-insensitive file system would
  accept `SRC/a.py`), names in NFC (macOS may store them decomposed), and a link leading outside the
  repository does not resolve; a definition is found in the file's facts (`anchors.facts_for_path`: Python and
  the tree-sitter languages). Where a language has no facts the name is searched as a word, which is
  `strong_inference` and says so. Lines must be inside the file.
- **Criterion status**, strongest problem first: `broken` (a reference does not resolve, cites a stale or
  contradicted claim, or a verified claim whose cited lines changed), `verified`, `tested`, `tested_inferred`
  (a test found only by a text pattern or a word search), `unchecked`, `unevidenced`. A stale claim's
  supersession is followed (`superseded_by`, else the newest claim that `supersedes` it) to the live claim,
  which the reference names.
- **Exit codes**, as the other checks: 1 while a criterion is broken or unevidenced or a spec line has a
  problem (a SHALL line with no id, an evidence line with no criterion above it or with nothing on it, an id
  used twice: compared case-insensitively, across files), with status `failed` when something is broken or
  malformed and `unevidenced` when that is the only cause; else 3 when something was not checked (unchecked
  claims, a spec file too large or unreadable, a configured folder that does not exist); 2 on an error; 0
  otherwise (`ok`, `no_criteria`, or `no_specs` when the default folder does not exist).
- **Output.** The text lists every criterion with its references, a cited claim's evidence locations with
  what the re-read found, the problems, the limits and, when claims were read, the last index time and its age.
  The JSON adds the spec `line` of each reference, the claim's evidence `at`, and problems as
  `{at, kind, message}`.
- **Lines** are split at LF only, a CR before it dropped, so a CRLF file or a Unicode line separator inside
  a sentence keeps the line numbers an editor shows (spec files and the files a test is searched in alike). A
  criterion's sentence may wrap onto the following lines; `none`, `tbd` and `todo` on an evidence line are no
  reference. A closing fence must be as long as the opening one. The line patterns are linear: an id is
  bounded, the text is taken greedily and trimmed in code, `path:lines` is split in code.
- CLI only (`spec check [--specs-dir DIR] [--json]`); no MCP tool, so the core menu does not change.

## Measured

- A five-criterion spec over this repository's own tests and code: 1 tested, 2 unevidenced (a helper cited as
  a test, now a pointer; lines only), 1 broken (a test name that does not exist), 1 unchecked (a claim with no
  store), a link reference definition not read, status `failed`, exit 1, in 0.75 s wall time including the
  interpreter start.
- Review round: two reviews found fourteen issues, all confirmed and fixed. A helper, fixture or class counted
  as a test, and a quoted string anywhere (Python files included) matched a test title; a link reference
  definition was read as a criterion; a verified claim whose cited code had changed passed; the id and text
  patterns backtracked (`"[a" + "1" * 20000` took 11 s, now the six long-line cases of the timing test take
  0.07 s together); the store was migrated and given a `.gitignore` by a read-only check, and a corrupt store
  failed the check even with no claim cited; a broken `verinoda.toml` silently fell back to the default
  folder; links and junctions were followed and dot or vendored folders read; indented code, fences in list
  items and HTML comments were read; references had no spec line; code pointers were labelled
  `statically_verified`; an evidence line under an unrelated item attached to the criterion above; a
  supersession chain stopped after one step; a task box before an id hid the criterion.
- 30 tests in `tests/test_specs.py` cover each status, each reference kind, real tests against helpers,
  fixtures and classes, JS titles, CRLF, a non-ASCII repository path, duplicate ids, fences, indented code,
  comments, link definitions, task boxes, wrapped sentences, path case, paths outside the repository, an unread
  file, the folder settings and broken ones, links and junctions, dot and vendored folders, the read-only store
  (empty, corrupt, another schema), changed claim evidence, a supersession chain and the timing of long lines.

## Limits

- Whether the cited claim or test really covers the criterion is the author's statement; it is not judged.
- Claim statuses are read as recorded; the claim's cited file lines are re-read, but other evidence (an
  experiment, a URL) is not re-run, so `verinoda update` is still the way to refresh claims.
- A test is checked to be defined, not run, and its last outcome is not read; the parameters of a
  parametrized test id are not checked.
- A JS/TS test is found by a text pattern on its title (a commented-out call would match); it is
  `tested_inferred`, never `tested`.
- The Markdown reading is line based: lazy continuation lines, block quotes holding criteria and list items
  nested in other containers are approximated.
- Kiro's and spec-kit's own files are not read as they are: their criteria need an `[ID]` added.
- No suggestion of tests or code by name for an unevidenced criterion.

## Upgrading note

New command `verinoda spec check [--specs-dir DIR] [--json]`: requirement criteria (`- [ID] WHEN ... THE
SYSTEM SHALL ...`) in Markdown files under `.verinoda/specs/` (or `[specs] dir` in `verinoda.toml`) with
`evidence:` lines naming claim ids, test ids, `path::Name` or `path:lines`; each criterion is verified,
tested, tested_inferred, broken, unchecked or unevidenced. Exit 1 while one is broken or unevidenced, 3 when
something was not checked, 2 when the folder setting cannot be read. Nothing changes for projects without
specs.
