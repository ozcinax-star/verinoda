## Why

`verinoda update` after one edited file rebuilt the whole graph: every file of the corpus extracted again (the
AST cache made most of them cheap), every cross-file pass over the whole corpus, a NetworkX graph built from the
result, clustered and written. On a 2,760-file copy of Verinoda's own repository one appended function took 98.8 s
(docs/drafts/1.1-plan.md: extraction 32 s, the rest of the rebuild about 43 s, Verinoda's post-work 8 s, outside
the build 16 s). Incremental extraction alone could not reach seconds; the graph had to be patched without the
whole-corpus rebuild, and the patched graph had to equal a full scan's node for node and edge for edge.

## Decisions

- One module, `verinoda/incremental.py`, behind a switch: `VERINODA_INCREMENTAL=1` (or `verify`, below) or the
  config key `index.incremental: true`; the variable wins over the key. Off by default (see Limits).
- **The ledger** (`.verinoda/index/incremental/`), written after every full build with the switch on: what the corpus
  `extract()` returned (taken before the reconcile changes it: the input `build_from_json` gets on a fresh scan),
  the files in extraction order with their detect category and AST-cache key, every directory detect can read with
  its modification time and entries, each file's identifier tokens (lower case), and per file the ids its own
  extraction makes or ends edges on that are not derived from its path (a Go `store_store`, a Java stub
  `glowmod`), captured during the build by wrapping `load_cached` and the two per-file extraction loops. A build
  that did not write the ledger (switch off, a changed-paths build, a failure) removes it; one that rewrites
  graph.json behind it is caught by a hash of graph.json the ledger keeps.
- **When it patches**: only existing files changed content (no file added, removed or renamed: every recorded
  directory listing is the same, a stat per directory and a listing only when its time moved, `__pycache__` and
  the other names detect never reads left out), the same extraction stamp, the same build configuration, the
  same vendored `build.py`/`export.py` (pinned digests), every changed file in the corpus (or an inert data
  suffix) and of the same category, and the affected files in the languages the closure was checked for
  (Python, JavaScript/TypeScript, Go, Java, Markdown).
- **The affected set A**: the edited files; the files whose text names a definition that changed (a definition is
  everything of a node but its id, place and file; rationale nodes left out); the files that share an id stem with
  one of them; the files that make or end an edge on a non-path id an edited file starts or stops making, or
  starts or stops naming as a base (the corpus pass salts colliding ids apart, and a stub node one file makes can
  merge into a definition taking every file's edges on that id along); the importers of an edited file whose
  imports changed. **The batch B**: A plus the files defining a name A's own extraction references as a stub, an
  import or a base (a file also defines its module: its id stem and bare name), the files its imports were
  resolved to, the files A imported before, and for each non-path id A makes the first two other files making it
  (enough for the corpus pass to salt it as a full build does; a `Path` stub made by 500 Python files does not
  bring 500 files in). Call names are not followed: the shared call pass and the language resolvers read the whole
  corpus through the resolution context, so their ambiguity counts are a full build's.
- The unmodified vendored `extract()` runs over B in the full build's order, with the rest of the corpus as the
  read-only resolution context the vendored incremental path hands it. The definitions the batch made for A are
  compared with the ledger's: a change seen only now widens A and the batch runs again (at most three rounds); a
  file of A that did not change but defines something else now is a fallback.
- **The splice**: the rows A's files own (by `source_file`) replace theirs in the stored extraction; a stub node
  (no file) stays while an edge of a file outside A ends on it, or no edge does and a file outside A makes it,
  and comes from the batch when an edge of A does; the two must agree. The stored rows keep their order (two rows
  with one id are merged by the builder in that order). An edited file's row sharing an id with a different row,
  or an edited file and another one making two different edges with the same ends and relation (their order in a
  full build is not known here), fall back.
- **The graph** without NetworkX or the whole-corpus rebuild: `build_rows` does what `build_from_json` (undirected,
  no root) and `to_json` do to an AST-only extraction, every rule in the same order (endpoint repair through
  normalized ids and the unique old-stem aliases, external stubs for import targets, the cross-language drops, one
  edge per pair with first-seen direction and specific-over-generic, the file-label disambiguation, `norm_label`
  and the default `confidence_score`; rows with one id merged in order). It refuses (falls back on) non-AST
  nodes, hyperedges, document twins and an edge end that normalizes to two ids. Each node keeps its community and its name; a new
  node takes the community most nodes of its file have. graph.json is written once, as `index.build`'s
  post-processing leaves a full build's: ids made portable, the nodes of missing and of Verinoda's own files
  dropped; the "graph unchanged" keeper's record is removed (it describes another graph now).
- Not redone by a patch: the clustering, GRAPH_REPORT.md, the labels file and the upstream manifest. Verinoda's
  post-work runs as after a full build (the receiver sidecar reuses its per-file facts by hash; the search index,
  the lexicon and the symbol facts are per changed file already).
- Every doubt falls back to the full build, and the update says why: `incremental: {used: false, reason: ...}`;
  `index_mode` is `incremental` when the patch was used. `VERINODA_INCREMENTAL=verify` also builds the graph from
  the patched extraction with the vendored builder and falls back on any difference (tests and the fuzz).
- `tools/graph_equal.py` now leaves `community_name` out with `community` (it is the name of the community).

## Measured

Windows 11, Python 3.13, the PC shared with other work (times vary by some seconds between runs).

A copy of this repository at the merge commit (2,786 files, `git archive HEAD`), scanned with the switch on; the
reference is always a scan of a FRESH copy of the edited tree (no index, no cache), compared with
`tools/graph_equal.py`:

| edit | update before (switch off) | update with the patch | of which the graph stage | batch | equal to a fresh scan |
|---|---|---|---|---|---|
| a function appended to `verinoda/paths.py` | 125.9 s (index 109.8 s)* | 39.0 s (index 23.0 s) | 11.9 s, + receiver sidecar 9.8 s | 11 files | yes: 38,058 nodes, 92,679 edges |
| a call pointed at another function (`verinoda/workflow.py`) | 101.1 s (index 85.2 s)* | 37.4 s (index 21.4 s) | 13.7 s, + receiver sidecar 6.6 s | 40 files | yes: 38,058 nodes, 92,679 edges |

\* the "before" edits were the same kinds on a second copy (`verinoda/textnorm.py` appended,
`verinoda/buildlock.py` call changed). Inside the graph stage of the first patch: checks and ledger load 0.8 s,
the edited file extracted alone 0.4 s, closure 0.2 s, `extract()` over the batch 1.6 s, splice 0.2 s, graph.json
load 2.0 s, `build_rows` 2.6 s, communities 0.9 s, write (ids made portable, missing files pruned) 2.1 s, ledger
1.0 s. The rest of the update is Verinoda's work after any graph build, unchanged: lexicon 6.1 s, search index
2.9 s, snapshot, stale claims and facts. A first scan with the switch on wrote a ledger of 38.6 MB
(`extraction.json`) and 6.4 MB (`ledger.json`).

The full update with the switch off is not equal to a fresh scan on this repository either way (before and after
this change): both updates of the second copy left 6 extra `..._unresolved` nodes and moved 6 edges onto them
(`tests_upstream/fixtures/cjs_require.js` requires a missing `./foundation`; after an update its import targets
are `..._unresolved` ids, after a fresh scan they are not; the cause was not traced). The patched graph, built from the extraction
alone, is equal to the fresh scan.

Oracle fuzz (`tools/incremental_fuzz.py`, each update compared with a fresh copy's scan):

- During the work, runs on the five corpora found six differences, each fixed and then gone: a Python import of
  a module the batch did not hold (a file now "defines" its module stem and name); a Go struct whose package id
  collides with other files' references and is salted apart only when they are in the batch (per-file non-path
  ids in the ledger); a Java stub id that an edited file starts making and that then takes other files' import
  edges onto the class (those files join A); a Java class base changed onto such a shared stub (base targets in the
  ledger too); on this repository two rows with one id in the full extraction (the builder merges them in order;
  `build_rows` does, the splice keeps the order) and the nodes of missing files the full build prunes (the patch
  prunes them as well; before, the next update fell back because graph.json had been rewritten behind the
  ledger). One more difference was in a fallback full update, not the patch: the reconcile keeps an external stub
  after its last import is removed (the same class as the repository case above).
- Final run, the code as committed: 5 corpora (Python `orders_app`, TypeScript/JavaScript `ts_app`, Go `go_app`,
  Java `glow_mod`, Java/Kotlin `forge_mod`) x seeds 301-304 x 15 edits = 300 updates: 258 patched, 42 fell back
  (a Kotlin, JSON, mcfunction or Gradle file among the affected), 0 differences. Edits: 57 Markdown, 48 comment or
  docstring, 41 function added, 41 import changed, 35 function renamed, 29 call changed, 27 function removed,
  22 class base changed. Median update 1.17 s patched, 2.6 s falling back (in-process, small corpora).

## Limits

- Off by default. The final fuzz and the repository measurement were clean, but on by default every scan writes a
  ledger (45 MB on Verinoda's repository) and every update of an existing index changes path (`index_mode`
  `incremental`), which the whole test suite has to confirm; that run was not done here (only the test files
  named under Tests). Turning it on is a one-line change in `incremental.enabled` once it has.
- "Seconds" holds for the graph (12-14 s, against 85-110 s); the whole `update` still takes 37-39 s because the
  work after any graph build is unchanged: the receiver sidecar (7-10 s: the table and cross-service links are
  remade over the whole graph, their per-file facts reused), the lexicon (6 s) and the search index (3 s).
- Languages: an affected file in another language (Kotlin, C/C++, C#, Swift, Rust, Ruby, PHP, mcfunction, JSON,
  ...) falls back; their cross-file passes (partial classes, header pairs, extensions) were not fuzzed.
- Any file added, removed or renamed is a full build, and so is an edit to a file the corpus does not hold unless
  its suffix is an inert data one (`.txt`, `.csv`, images, ...): a `tsconfig.json`, `go.mod` or `package.json`
  edit is a full build.
- A batch over max(100, min(400, a quarter of the corpus)) files falls back: a definition named by most of the
  repository (a common function name) costs what the full build costs.
- The clustering is not redone: communities drift from what a full build would compute until the next full build
  (community is history to the oracle). GRAPH_REPORT.md describes the last full build.
- The closure is checked by the fuzz, not proven: the edits are the fuzz's kinds on small corpora and two edits on
  Verinoda's repository. A pass that reads something the closure does not list would show as an inequality.

## Upgrading note

Nothing changes by default. `VERINODA_INCREMENTAL=1` (or `"index": {"incremental": true}` in
`.verinoda/config.json`) makes `verinoda update` patch the graph when only existing files changed content: the
next full build (a `scan`, or an `update` that needs one) writes the ledger under `.verinoda/index/incremental/`,
and later updates say in `incremental` whether they patched and, if not, why. `tools/graph_equal.py` ignores
`community_name` as it ignores `community`.
