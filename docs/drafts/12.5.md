# Undocumented decisions (`verinoda decide undocumented`, `decide dismiss`)

## Why

Decision records only help when the choices that shape the code are recorded. Many are never written down:
storage that goes through one module, a library kept behind one file, configuration read in one place. The
code shows such a choice; nothing says it was one, and nothing keeps it. An ADR workflow that starts from what
the code already does lets the user record the choice (with a guard that keeps it) or say it is not one.

## Decisions

- A new `decide` subcommand pair, no new MCP tool: `decide undocumented [--decisions-dir DIR] [--json]` lists
  the candidates, `decide dismiss CANDIDATE --reason "..." [--undo]` records the user's dismissal. The core MCP
  profile and its menu are unchanged; the tool count is unchanged.
- The facts come from `decision_brief`'s probes, not new scanners: P1 storage sinks (the guard engine's bound
  connection calls plus `SINK_PATTERNS`, comments and docstrings not read; the probe now also keeps each site's
  needle as `facts["sink_sites"]` so the evidence re-checks), P2 environment reads, P3 declared dependencies,
  plus `_Probe.py_imports` (imports from the syntax tree).
- Three candidate kinds, the smallest set the row names ("a single storage path, an exclusive library") plus the
  configuration reader the same probes give for free:
  - `single_storage_path` (`storage:<file>`): every sink line of a kind in one product file; at least two sink
    lines or a database connection;
  - `exclusive_library` (`library:<name>`): a declared runtime Python dependency whose module is imported by
    exactly one product file; the guard's own pattern (`^\s*(?:import|from)\s+MODULE\b`) is re-run through
    `guards.exclusive_hits` (code with comments and strings removed) and must find no other product file; a
    module that another product file names in a string literal of its code (`importlib.import_module("mod")`,
    a table of module names) gives no candidate;
  - `single_config_reader` (`config:<file>`): every environment read (two variables or more) in one file.
- Each candidate carries the fact (`statically_verified`, `path:line` evidence with the needle each line must
  hold, and the scope counted) and is itself `weak_inference`: that the fact is a decision is a guess. It gives
  the guard spec that would keep it when a guard kind can check it (`only_in sink=db-connection allowed=FILE`,
  `only_in pattern=... allowed=FILE`; none for other sink kinds, whose `sink=` no engine checks), and the
  `decide record` and `decide dismiss` commands with placeholders for the user's own words. Nothing is recorded
  for the user.
- Coverage: a live record (status accepted or proposed, as for the decision reach of a review) or a hand-written
  ADR-like document (`decisions.adr_like_files`) covers a candidate when it names the candidate's file, the
  library (distribution or module name) or the database driver (`sqlite3`, `sqlite`) as text, or when a
  record's guard glob matches the file. Each covered candidate cites the matching `path:line`. Rejected,
  superseded and deprecated records cover nothing.
- Dismissals are local (`.verinoda/dismissed_decisions.json`, format 1, not committed): id, the user's reason,
  date, and the fact as it read then. Only a current candidate can be dismissed; a reason is required; a
  dismissal whose candidate has gone is listed with `current: false`; `--undo` removes one. An unreadable file
  is an error (exit 2), never an empty list.
- Fewer than three product code files give no candidate (one file holding everything is no choice).

## Measured

- On Verinoda itself (325 product .py files, no records in the worktree), before the load-by-name rule: 16
  candidates, all `exclusive_library` (numpy, starlette, graspologic-native and 13 tree-sitter grammars). A grep
  of import statements confirmed each "imported by one file" fact (16/16). But the grammars of Go, Rust, Kotlin
  and PHP are also loaded by name through the module tables in `anchors.py` and `index.py`, so "kept behind one
  file" was wrong for 4 of them. The rule added afterwards (another product file names the module in a string
  literal of its code: no candidate) drops those 4, and also starlette, whose name is in
  `decision_brief.SERVER_DEPS` (a conservative miss). A grep for quoted module names gives 11 candidates
  expected: numpy, graspologic-native and 9 grammars. The command was not re-run on the whole repository after
  the rule (the load limits of this build allow one scan). No storage or config candidate: sinks and environment
  reads are spread over many files. The grammars are true facts but one choice in the user's eyes; they are
  dismissed one by one.
- The test project: storage, library and config candidates found; a library imported in two product files, a
  test file's import and a commented import give none.

## Limits

- The candidate is a guess (weak_inference); only the fact under it is verified.
- Libraries: Python imports only; a module whose name differs from its distribution and is not in the small
  known list (`PY_MODULES`) is not matched; npm, Go, Cargo and JVM dependencies are not checked. Any string
  literal that equals the module name drops the candidate, even one that does not load it (a list of
  dependency names).
- Storage and environment facts are pattern-based (P1, P2): an ORM or reader the patterns do not know is not
  seen.
- Coverage is text: a record naming the file or library covers the candidate whatever it says; one describing
  the choice in other words does not. Broad documents (DESIGN.md, ARCHITECTURE.md) are not searched: they name
  nearly every file and would cover everything.
- Related candidates (a family of tree-sitter grammars) are listed and dismissed one by one.
- CLI only; not in any MCP profile.

## Upgrading note

`verinoda decide undocumented` lists structural choices no decision record covers - storage that goes through
one file, a Python library imported by one product file, the environment read in one file - each a
`weak_inference` candidate over a verified fact with `path:line` evidence, with the guard that would keep it and
the `decide record` command. `verinoda decide dismiss CANDIDATE --reason "..."` records the user's dismissal in
`.verinoda/dismissed_decisions.json` (local; `--undo` lists it again). No MCP tool was added: UPGRADING's tool
count does not change.

## Tests

`tests/test_undocumented.py` (8): the three kinds found on a small project, evidence that re-checks, guard specs
that `decide record` accepts, a two-file library, a test import and a commented import giving none; a library
loaded by name through `importlib` in another file giving none, while a comment naming it still does not; a record
(guard glob) and an ADR (names the library) covering candidates with the cited line; a rejected record covering
nothing; dismissal needing a reason and a current candidate, refusing a second dismissal, showing a dismissal
whose candidate is gone, `--undo`; an unreadable dismissal list is an error; a project under three files gives
nothing; the CLI's JSON and text output and exit 2 on an unknown id. Touched modules' tests: `test_decide.py`,
`test_decide_lifecycle.py`, `test_decide_review3.py`, `test_cli.py`, `test_docs.py`, `test_line_endings.py`.
