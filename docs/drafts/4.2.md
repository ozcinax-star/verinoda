# Draft: Hotspots (backlog 4.2)

For `docs/DESIGN.md` (a new section and a D-number at merge), `docs/UPGRADING.md` and `docs/BACKLOG.md` (delete
row 4.2 when merged). Code comments cite no id.

## Why

A change review and a first read of an unfamiliar project both have to choose where to look. Code that changes
often and is complex is where defects and misreadings concentrate (CodeScene, CodeCharta). Verinoda already had
both halves: `map --view history` counted the most changed files (last 30 commits, no weighting) and `health`
counted cyclomatic complexity per function. Nothing combined them, per file or per function, and `review` packed
`read_first` in the order it found ranges.

## Decisions

- **A map view, not a command or an MCP tool.** `verinoda map --view hotspots [--json]` and MCP `map_view`
  (`view: hotspots`, reached through `run_tool`). Like `dead`, it is in `architecture_map.VIEWS` but not in
  `DEFAULT_VIEWS`: plain `verinoda map` builds the same views as before. The core profile stays at five tools;
  the core menu grows by the word `|hotspots` in `run_tool`'s catalog (still under 4,500 characters).
- **Change frequency.** A file's changes are the non-merge commits among the last 1,000 (`git log --no-merges
  --no-renames --name-only`); a commit counts once whatever its size. Only files of the graph, with a grammar
  `health` reads, not test or support files, not under a detected copy or reference tree.
- **Complexity** is `health`'s cyclomatic complexity, counted on the current text: per function as is, per file
  the sum over its functions (module-level code is not weighed). Score = changes x complexity.
- **Per function**, for the top 20 files by score: `git log --topo-order -m --no-renames --full-index -U0` over
  those files, in the same window (`--since` the oldest commit of the file window, or the whole history). Each
  non-merge commit counts once for every function one of its new-side lines maps into; a pure deletion counts for
  the function holding the lines on both sides. Lines are carried to the current text through line maps keyed by
  (path, blob id): HEAD's blob is mapped to the working tree by `difflib` (after matching the lines both texts
  start and end with; a middle of more than 4 million line pairs uses difflib's popular-line heuristic, so a file
  of many repeated lines is not quadratic), then each diff maps its old blob from its new one. Both carry lines
  the same way: an unchanged line as its copy, a replaced line as the new line in its place (the i-th, or the
  last), a deleted line as the line before the deletion when both sides are in one function, else nowhere. A
  line edited in the working tree so keeps its history, which matters most in `review`, which ranks the
  functions being edited.
  Keying by blob rather than commit carries a side branch through the merge's diff to that parent (`-m` shows it),
  so branch commits count like the others and merges only carry maps. The log runs with `--no-ext-diff
  --no-textconv`: a configured text conversion would shift the hunks' line numbers (and run a program).
- **A project in a folder of its git repository** reads that folder only (`--relative`, pathspec `.`, `ls-tree`
  relative to the folder), as `history` does: the graph's paths are relative to the project, git's to the
  repository. A limit line says so.
- **A shallow clone** is not the whole history: its boundary commits (listed in `.git/shallow`, their diff adds
  every file) are not counted, `window.whole_history` is false, `window.shallow` true, and a limit line names
  `git fetch --unshallow`.
- **Statuses.** A file's change count and every complexity are read (`counts_status` / `cyclomatic_status`:
  `statically_verified`); a function's change count rests on the line carrying, and the ranking is a heuristic:
  each row is `strong_inference`. Rows carry `at` (`file:1-N` for a file, `file:start-end` for a function) and
  `last_change` (sha, date).
- **Skipping what cannot reach the top.** Parsing every changed file dominated the cost (121 s on this
  repository). Every unit of a Python function's cyclomatic complexity is one of the words `def`, `if`, `elif`,
  `for`, `while`, `except`, `case`, `and`, `or` in its text, so their count in the file bounds the file's
  complexity from above. Files are measured in order of that bound times their changes (files of other languages,
  which have no bound, first); once the bound is below the 20th best measured score the rest cannot enter the top
  and are counted as `below_top_not_measured` (the output is then `truncated`). The top of the list is the same
  as measuring everything. `files_changed` counts every candidate (changed code files of the graph); the text
  header reports that number. If the per-function git log fails or times out, `window.functions_not_measured`
  and a limit line say so.
- **`review` ranks `read_first` with it.** The kinds keep their order (changed code, first-hop call sites,
  finding lines); within a kind, ranges are ordered by the hotspot score of the function holding the range's
  line of interest (a changed definition's first line, the call of a call site, a finding's line, not the
  range's first line, which for a call near a function's top is in the function before), its changes among the
  last 500 commits touching the reviewed files x its cyclomatic complexity, then as before. Each such range gets
  `hotspot: {symbol, changes, cyclomatic, score, status}`; the character budget is filled in that order. No
  function: no `hotspot`. When the history cannot be read (no git history, git failed or timed out), the old
  order, no `hotspot`, and `coverage.not_checked` says so.

## Measured

On this repository (Windows, 392 non-merge commits, 322 changed code files of the graph):

- `verinoda map . --view hotspots`: 121 s before the bound, 28-31 s after (106 files measured, 93 of them with
  a nonzero complexity as rows, 216 skipped by the bound; the same top 13 files and top functions as measuring
  everything); the per-function pass over the top 20 files is a few seconds of git and
  diff parsing, the rest is `health` parsing the measured files.
- Top files: `verinoda/cli.py` (94 changes x 1,324), `verinoda/analysis.py`, `verinoda/review.py`; top functions:
  `search_index.py::analyze_query` (15 x 138), `analysis.py::_run_subquestion` (14 x 126).
- `hotspots.rank` for the ranges of one small file: 0.9 s; for `cli.py` and `review.py` together: 5.5 s (mostly
  parsing both files again), added to a `review` that touches them.

## Limits

- A change is a commit, whatever its size; renames are not followed (a renamed file's history starts at the
  rename); the window is the last 1,000 non-merge commits.
- Complexity is `health`'s cyclomatic count: module-level code and files without a grammar are not weighed.
- Line carrying is positional inside a hunk: a hunk spanning two functions can credit the wrong one; a line
  deleted outside one function no longer maps, so its earlier changes are lost. A working-tree diff of more
  than 4 million line pairs (after the common start and end) uses difflib's popular-line heuristic, which can
  match fewer lines and so carry more of them positionally.
- A shallow clone counts only the commits after its boundary.
- The per-function pass is for the top 20 files only (the view) or the reviewed files (review).
- `review` parses the reviewed files' functions a second time for the ranking.

## Upgrading note

`verinoda map --view hotspots` (and MCP `map_view` with `view: hotspots`) ranks code files and functions by
changes x cyclomatic complexity. `verinoda review` orders `read_first` within each kind by the same score and adds
`hotspot` to each range it could score; the kinds keep their order. No MCP tool was added: the tool count in
UPGRADING does not change.

holding the call, not the one before it; `map --view hotspots --json`
from the CLI; `review` reading the hotter changed function first although it comes later in the file; the Python
bound never below the complexity on Verinoda's own sources; a file whose bound cannot reach the top not measured.
