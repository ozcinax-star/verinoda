# Ranked repo map under a token budget

## Why

An agent that starts on a change needs to know which other files to read first. Reading every signature
of a project does not fit its context, and `map --view hierarchy` lists the symbols of each file without
saying which ones matter. Aider's repo map answers this with PageRank over the references between
files, weighted toward the files the user is working on, cut to a token budget. `map --view repo
--max-tokens N` gives the same answer from Verinoda's own graph, without a model and without the network.

## Decisions

- A new view of `architecture_map` (`repo_map`), registered in `VIEWS` next to dead, hotspots and
  sides. It is asked for by name and is not one of the default views.
- The graph is the cycles view's file-to-file dependencies (`_file_deps`: calls, imports, uses and
  inherits between files, with type-only and deferred imports, prose files and Python imports that load
  the standard library left out). The weight of an edge is the square root of its references, so one
  file that calls another fifty times does not outweigh everything else.
- PageRank runs by power iteration in the module (damping 0.85, at most 100 rounds, stops once it
  converges). It does not use `networkx.pagerank`, which needs scipy. 90% of the random jump lands on
  the files in play (split among them) and 10% on all files alike, a fixed share so that the focus
  weighs as much on a thousand files as on ten. Without files in play it is plain PageRank. A file
  without dependencies spreads its rank the way the jump does.
- The files in play are the `--target` files, or the git working-tree changes when none are given (the
  same default as the impact view, `--base` included). A `path::Name` target counts as its file; an
  absolute path inside the repository is made relative, and `.`/`..` are resolved. A target that is no
  file of the graph goes to `focus_unresolved` and is not used; as in the impact view, the CLI then exits
  2, and MCP adds a `next_step`. As in Aider, the files in play are left out of the map because the agent
  is already reading them.
- Each file's rank is shared among its outer symbols by the references other files make to each one,
  plus one so that no symbol gets zero. An outer symbol is a class, a method, or a module function: a
  symbol that no function or method holds. A helper nested in a function is left out.
- A signature is the symbol's definition line with its indentation kept, found past any decorators as the
  first line naming the symbol as a whole word, cut at 160 characters, and cited at `file:line` (entries are
  `at` and `text`; the text names the symbol). A symbol whose line is not found (the file changed since the
  scan) is not shown and is counted in `signatures_not_found`, outside `symbols_total`. Data files (json, toml, ini, cfg, yaml, properties, xml),
  whose keys the extractor emits as symbols, are left out.
- Budget: a line is estimated at (characters + 4) // 4 tokens, the newline counted. Symbols are taken in
  score order until the next one would pass `--max-tokens`, so everything shown outranks everything left
  out. The count covers exactly the lines the text output prints for the files, and a test holds it to
  that. The default budget is 1024 tokens (Aider's default). The CLI rejects `--max-tokens` below 1
  (exit 2).
- Status: each file row is `strong_inference`, because the ranking is a heuristic. The signature text is
  the source line at its `at`.
- Text output (`map_text._repo`) prints the map itself. The token budget bounds it, so `--max-lines` does
  not apply unless it is given.
- MCP: `repo` is added to the `map_view` view Literal and to `VIEWS`. `targets` gives the files in play
  (by default the working-tree changes; `focus_source` says which). No new MCP argument was added: the
  MCP call starts at the default budget and lowers it until the map's JSON fits three quarters of the
  response cap (`budget_note` says so), so `cap_response` does not cut files from it and the counts
  describe what is sent. To keep the core menu under 4,500
  characters, the gateway text of node_inspect and relation_trace was shortened ("a symbol's", "between
  symbols") by as much as "|repo" added.

## Measured

- examples/orders_app with `--target orders/api.py`: 17 of 17 signatures in 7 of 8 files, about 239 of
  1024 tokens. Order: config.py, repository.py, service.py, pricing.py, then the tests.
- The same with `--max-tokens 40`: 2 signatures (config.py `load_settings`, repository.py
  `OrderRepository`), 27 tokens. The next symbol did not fit.
- Naming api.py as in play raises service.py's rank above its unweighted rank.
- Core MCP menu JSON: 4,499 characters before, 4,498 after.
- Not measured: time and output on a large repository. This build must not scan the whole repository
  more than once, so none was scanned.
- Review round: on the main repository's existing index (879 ranked files, loaded, not rescanned), the
  first weighting (each file in play ten times any other file) left the map almost unchanged by the focus.
  With the fixed 90% share, focusing examples/orders_app/orders/api.py puts its config.py, repository.py,
  service.py and pricing.py first; focusing verinoda/cli.py puts paths.py, store.py, snapshot.py and
  index.py first. The default map's JSON there is about 9,300 characters, so MCP lowers the budget a
  little. A mistyped `--target` now exits 2, `--max-tokens 0` or below is rejected, a stale line that
  merely contains the name (`budget` for `get`) is no longer quoted as the signature, and entries lost
  `symbol`. Each has a test.

## Limits

- The ranking is `strong_inference`: it suggests what to read first, not what matters. Graph edges are
  extractions, not verification, and dynamic dispatch, reflection and DI containers are not resolved.
- Only the first line of a signature is shown. A multi-line parameter list is cut at that line.
- Dependents of the files in play rank only through what they use themselves. The impact view lists
  dependents.
- Unlike Aider, identifiers mentioned in the conversation carry no weight. Only files do.
- The token count is an estimate (four characters a token), not a tokenizer's count.
- The budget takes a prefix of the ranking. It does not skip one large line to fit smaller ones after it,
  so it can end a few tokens under the budget.

## Upgrading note

`verinoda map --view repo [--target FILE ...] [--max-tokens N]` prints a repo map: the files to read first,
ranked by PageRank over the file dependency graph toward the files in play (the targets, else the git
changes), and each class, function and method definition line at `file:line`, until the estimated tokens
reach N (default 1024). `--json` has the ranks (`strong_inference`) and the counts. The MCP `map_view`
takes `view: "repo"`, with `targets` as the files in play. The MCP tool count is unchanged, so UPGRADING's
tool count needs no change.

## Tests

- tests/test_repo_map.py (new):
  - ranking order, and each signature equal to its source line;
  - the files in play weighting the rank and left out of the map, and unresolved targets;
  - the budget keeping a prefix, with the token count equal to the rendered lines;
  - text output, the CLI `--json` and text, and MCP `map_view("repo", targets=...)`;
  - nested functions and decorators;
  - the focus outweighing a hub on a 903-file graph;
  - absolute and `..` targets, and an unknown `--target` exiting 2;
  - `--max-tokens 0` and `-3` rejected;
  - MCP lowering the budget under a small cap, with counts equal to what is sent;
  - a moved definition not quoted and counted in `signatures_not_found`.
- tests/test_architecture_map.py: `VIEWS` includes `repo`, and it states its method and limits.
- tests/test_mcp.py (unchanged): passes with the new Literal value and a core menu under 4,500 characters.
