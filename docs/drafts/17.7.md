# Crash diagnosis rules and suspect scoring

## Why

`verinoda trace-log` maps a log's stack traces onto the project, but a player's crash report is mostly about other
mods: sixty frames of the game with three of some storage mod in between, or no trace at all, only a loader line
saying a dependency is missing. Tools such as mclo.gs Codex, mc-crash-doctor and NotEnoughCrashes name the known
pattern and the mod to blame; `trace-log` said neither.

## Decisions

- **Rules are data** (`verinoda/crash_rules.py`, `RULES`): an id, the line patterns that show it, what it means.
  Six rules: `out_of_memory`, `watchdog` (the tick took too long; `Description: Watching Server`),
  `missing_dependency` (Fabric's "requires [version X or later | any version | any version between A and B] of ...
  which is missing / but only the wrong version", Forge's "Missing or unsupported mandatory dependencies" and its
  "Mod ID: ..., Requested by: ..." lines), `missing_class` (`NoClassDefFoundError` / `ClassNotFoundException`, but
  not on a line logged at WARN, INFO, DEBUG or TRACE, nor a Mixin "Error loading class:" warning: optional compat
  classes), `mixin_apply` ("Mixin apply for mod X failed", `MixinTransformerError`, `InvalidInjectionException`) and
  `wrong_java` (`UnsupportedClassVersionError`, ASM's "Unsupported class file major version NN", the launcher's
  "LinkageError occurred while loading main class"; the class file versions turned into Java releases: 65 -> 21).
- **A rule names its evidence**: the first matching log line (the logger's prefix stripped), how many lines matched,
  and what the pattern captured (`found`: the mod id, the Mixin and its target, the seconds of the tick, the Java
  versions; each value cut to 200 characters). A rule hit carries `status: strong_inference`: the line is
  observed, what it means is an interpretation. When the first line is a bare header (`Description: Watching Server`) and a later one names more, the
  later line's captures are kept with `found_at`.
- **A suspect** is the owner of frames outside the JDK, the game, the loaders and common libraries: a mod named by a
  Mixin handler's name (`handler$bfk000$lagfix$afterTick`, a mod id with a dash included) or by a modern Forge
  frame's module (`TRANSFORMER/bigstorage@2.4.1/...`), the mod jar a Forge frame names
  (`~[bigstorage-2.4.1.jar%23188!/:2.4.1]`), else the class's package (its first three parts). A class with no
  package (an obfuscated game class, `dzv.a(SourceFile:123)`) is never a suspect; a hidden lambda class
  (`Foo$$Lambda$12/0x...`) is its outer class. A mod named by a handler or module, its jar (the name before the
  version) and every package that has the mod id as a dotted part are one suspect, led by the jar, else the
  package; a mod id too common to tell (`core`, `api`, `common`, `client`, ...) ties nothing.
- **The score** is the sum of `1 / (1 + position)` over the suspect's frames, position 0 being the top of a trace or
  of a `Caused by` (the parser now records each frame's position, Forge jar and module). A crash report section's
  `Stacktrace:` (`-- Head --`, `-- Block entity being ticked --`, ...) whose frames are a run of an earlier trace's
  frames is not counted again, nor a trace printed twice (the same header and frames); another exception thrown
  at the same place is counted. The score is a heuristic:
  every suspect is `strong_inference`, with its inputs (frames, traces, positions, frames at the top, the first
  frame, how it was named, whether the project's own code). At most five suspects are shown.
- **Output**: `trace-log` (text and `--json`) gains `diagnosis` and `suspects` (with `score`, the formula once),
  each key present only when non-empty. A log with a diagnosis but no trace and no test result exits 0, not 2
  (nothing found). Fabric's own log lines (`[time] [main/ERROR] (FabricLoader) ...`, no colon) now lose their
  prefix too. No new command, no MCP change; nothing is stored beyond what `trace-log`
  already stored.

## Measured

Five hand-written fixtures in the shape of real logs (`tests/fixtures/crash/`): a Forge out-of-memory crash report
(rule `out_of_memory` at line 7; suspects `bigstorage-2.4.1.jar` 0.78 from positions 2, 3, 4 and
`tinyhud-1.0.3.jar` 0.1; the `-- Head --` repeat not counted), a Fabric watchdog report (rule `watchdog`, 60.00
seconds; suspect `dev.lagfix.chunk (mod lagfix)` 1.83 from two package frames and one Mixin handler), a Fabric
Mixin apply failure (rule `mixin_apply`: mod `guardmod`, `guardmod.mixins.json:LevelMixin` on
`net.minecraft.class_1937`; no suspect, every frame is the loader's), a missing `fabric-api` and a class file 65 run
on Java 17. Not measured on real players' logs.

Review round: a crash report's category sections (`-- Block entity being ticked --`) repeat a run of the main trace
and were counted again (a mod at position 2 scored 0.83 over 2 traces instead of 0.33): now skipped, and only
`Stacktrace:` sections are skipped as runs, so a second exception at the same place counts (2.5, was 1.5); the
check is indexed by frame (4,000 traces in 0.03 s; 2,000 took 0.76 s before, growing quadratically). A Mixin "Error
loading class" warning no longer comes first as `missing_class`; Fabric's "any version between" wording, the
Forge "Mod ID / Requested by" line, "Unsupported class file major version" and the launcher's LinkageError now
match; `found` values are capped; rule hits carry a status; `trace-log` exits 0 on a diagnosis alone; a dashed
Mixin handler mod id, a Forge module prefix, an obfuscated class with no package and a hidden lambda class are
handled; jar, module, handler and package rows of one mod merge, a generic mod id never does.

## Limits

- The rules match single lines; a message wrapped across lines matches only on its first line.
- Package attribution takes the first three parts: two mods sharing them (`com.example.a`, `com.example.b` at depth
  two) are one suspect, and one mod spread over packages that differ in the first three parts is several.
- `missing_class` is skipped on WARN / INFO / DEBUG / TRACE lines: a mod that logs a real missing class at WARN is
  missed (its stack trace's own `Caused by` line, which has no prefix, still matches).
- A module prefix with no `@version` is not read as a mod; a mod id that is not a dotted part of its packages
  (`big-storage` vs `com.bigstorage`) keeps the jar and package apart.
- Obfuscated or remapped frames are not named back to a mod beyond the Mixin handler's mod id; a Fabric mod list
  (`Fabric Mods:` in a crash report) is not read to turn a package into a mod id.
- A Mixin apply failure's mod is in the rule's `found`, not among the suspects (its frames are the loader's).
- No claim is stored for a rule or a suspect: they describe the run and the installed mods, not the project's code.

## Upgrading note

`verinoda trace-log` now names a known crash pattern (out of memory, the watchdog, a missing dependency or class, a
Mixin that failed to apply, the wrong Java) with its log line, and ranks the mods the stack frames point at by a
score (`strong_inference`, its inputs shown). Two new keys in `--json`: `diagnosis` and `suspects` (plus `score`,
the formula), and each rule hit a `status`. A log with only a crash pattern now exits 0. No index change; the MCP
tool count is unchanged.

## Tests

- `tests/test_crash_rules.py`: each rule on its fixture (first line, captures), a bare header taking a later line's
  captures, suspects by jar with their score and the `-- Head --` repeat skipped, a Mixin handler merged with its
  package, platform frames never suspects, `Caused by` restarting the position, a missing class and a clean log;
  crash report sections not counted again, another exception at the same place counted, a trace printed twice
  counted once and 2,000 traces fast, an optional class warning not a `missing_class`, the Fabric range and Forge
  dependency wordings, a dashed handler mod id, a generic mod id tying nothing, a Forge module tying its jar and
  package, obfuscated and hidden lambda classes, the other wrong-Java wordings, `found` capped and the status, a
  Fabric line's prefix stripped.
- `tests/test_trace_log.py`: the CLI (`--json` and text) names the rule and the suspect with its score, the project's
  own frames marked; a log without a crash pattern has no `diagnosis`; a log with only a missing-dependency line
  (in a folder with a non-ASCII name) exits 0 with that diagnosis.
