# Rationale nodes: WHY/NOTE comments and decision record citations attached to the code

## Why

An agent that inspects a symbol sees its source, its edges and the backlog items its comments cite, but not the
comments where the author says why the code is the way it is (`# WHY: ...`, `// NOTE: ...`, `HACK:`, a citation
of an ADR). Those comments are the shortest path to the reason, and an agent reading only the excerpt can miss one
that sits above the definition, or deep inside a long body past the excerpt's cut. Graphify and
codebase-memory-mcp turn such comments into graph nodes linked to the code; this decision gives Verinoda the same
reach without changing the graph.

## Decisions

- New module `verinoda/rationale.py`; a new CLI command `verinoda rationale [symbol|path] [--limit N] [--json]`;
  MCP `node_inspect` gains a `rationale` list. No new MCP tool, no new argument: the core menu is unchanged.
- What counts: a comment whose words start with `WHY:`, `NOTE:`, `NB:`/`N.B.:`, `HACK:`, `IMPORTANT:` or
  `RATIONALE:` (any case, an optional `(who)` before the colon, `@`-prefixed in Javadoc), with the comment
  lines right after it (up to 6, until a blank comment line or a new marker); and a comment that cites a decision
  record anywhere in it: `ADR-12` / `ADR 12`, a document (`.md`, `.rst`, `.txt`, `.adoc`) under `adr/`, `adrs/`,
  `decisions/` or `decision-records/` (a source file under a `decisions/` folder is not one),
  `<file>.md D50` (this repository's own form), or the words "decision record". The citations are listed in
  `cites`. "Note that ..." without a colon is prose, not a marker.
- Comments are found with `tokenize` for Python (a `#` inside a string is not a comment; trailing comments count)
  and line by line elsewhere (`//` and `/* ... */` blocks for C-family languages, `#` for shell, Ruby, YAML,
  TOML, `--` for Lua and SQL); only whole-line comments outside Python. Markdown and other prose are never read
  (a `# WHY` heading is not a comment).
- Attachment, by position: a comment directly above a definition (only comment, decorator or annotation lines
  between; a blank line breaks it) is `above` that definition; a comment between a decorator and its `def` is
  `above` it too; otherwise the innermost definition around it (`inside`); otherwise `module`. Definitions come
  from `anchors` facts (Python, TypeScript/JavaScript; graph symbols the TS/JS facts miss, such as
  `const f = () => ...`, are added from the graph's spans) and, for other languages, from the graph's symbol
  spans. A Python comment after a body's last statement (past the ast end) is `inside` the definition just above
  it whose `def` line is indented less than the comment. Lines are counted on `\n` only, as editors and git do.
- Side table, not graph nodes: nothing is stored. The comments are read from the file as it is when asked, so the
  index build, `graph.json` and the snapshot are unchanged and the quoted text is never stale. For a symbol the
  definition is found by the node's indexed line, so a symbol whose file changed since the index gets no rows
  (`node_inspect`: `rationale_note` says to run index_update; the CLI: status `stale`, exit 2). A file is parsed
  for its definitions only when its comments hold a marker (a cheap text check first, then the comment scan).
- Status: each row is `statically_verified` that the comment is at that `file:line` (the text is quoted as
  written); what it says is the author's statement and is not checked; which definition it explains is read
  from its position and has its own `attach_status`, `strong_inference`. The note says so in one sentence (`rationale_note` in `node_inspect`, `note` in the CLI).
- `node_inspect` adds `rationale` only when the node has some: at most 5 rows of `at`, `tag`, `text` (at most 200
  characters, ending in `...` when cut), `attach`, `status`, `attach_status`, plus `rationale_total` when there are more, so it stays far from the
  12,000-character cap. A file node gets the module-level rows.
- The CLI: a symbol (resolved as `backlog` and `node_inspect` resolve names) gives its rows; a file or folder,
  or nothing (the project's tracked and untracked-not-ignored files, `git ls-files -z`), gives every row there
  with counts per tag. A path is resolved against the repository (`.`, `./pkg`, an absolute path inside it); a
  path outside it is `not_found`. An index that exists but does not load is reported with its error. Exit 0 when something is
  found, 2 otherwise (none, not found, ambiguous with candidates).

## Measured

On this repository (2,666 listed files): 74 rationale comments (ADR citations 66, NOTE 7, IMPORTANT 1; 41 at
module level, 29 inside a definition, 4 above one) in about 13 s for the whole project on the loaded test PC
(a first version that parsed every Python file for its definitions took 41 s). Most hits are this repository's
`(docs/DESIGN.md Dnn)` citations; section-divider comments that cite a decision (`# -- decisions (docs/DESIGN.md
D33) ---`) attach to the module or to the definition right below them.

Review round: the project run now lists untracked files and non-ASCII names (2,669 files, 72 comments: ADR 64,
NOTE 7, IMPORTANT 1, in about 21 s on the loaded PC); two former ADR rows were source paths under a `decisions/`
folder. A 64 KB comment line of `a.a.a...` took 30.8 s in the citation regex before (a match could start after
every `.`); the citation patterns now start only at the start of a path, and the same line takes well under a
second (the test bounds it at 2 s).

## Limits

- Outside Python a comment after code on the same line (`x = 1; // NOTE: ...`) is not read.
- Docstrings are not comments: a `Note:` section of a Python docstring is not listed (the excerpt shows it).
- Attachment is by position only; a section-divider comment directly above a function is attached to that
  function.
- Without facts (Java, Kotlin, Go ...) the definitions are the graph's spans, which may be heuristic (next
  symbol, capped); a comment past a heuristic end is attached to the module.
- `node_inspect` on a Java/Kotlin node matches the node's own span; a comment above an annotated method is
  attached when only comment and annotation lines come between.
- A whole-project run reads every listed file; there is no cache.

## Upgrading note

New command `verinoda rationale [symbol|path]`: the WHY/NOTE/NB/HACK/IMPORTANT/RATIONALE comments and the
comments citing a decision record, each with its `file:line`, quoted, and attached to the definition it is above
or in. MCP `node_inspect` lists the ones of the node under `rationale` (at most 5). Nothing to rebuild: they are
read from the files when asked. The MCP tool count is unchanged.

## Tests

`tests/test_rationale.py`: markers, a continued block and an ADR path in Python; a trailing citation after code;
a `#` inside a string ignored; a comment above a decorated property and one between a decorator and its `def`
attached `above`; Javadoc past an `@Override` and a `//` line comment with a `DESIGN.md D50` citation, attached
with given spans; prose (`Note that`, a Markdown heading) skipped; `node_inspect` quoting the rows of a method and
none for a function without; a Java node through the graph's spans; the CLI for a symbol, a folder (`--json`), the
project with `--limit`, none and not found. Review round: an arrow-function constant in TypeScript gets the
comment above it (node_inspect and file); a stale file gives no rows (node_inspect note, CLI `stale`); rows carry
`attach_status`; a comment after a Python body's last statement is `inside`; a source folder named `decisions/`
is not a citation; a 64 KB comment line scans in under 2 s and cut text ends in `...`; U+2028 does not shift
line numbers; `.`, `./pkg`, an absolute folder and the project find a committed non-ASCII file and an untracked
one, a path outside the repository is not found; a broken index is reported with its error. Also run: `tests/test_mcp.py`, `tests/test_docs.py`,
`tests/test_line_endings.py`, `tests/test_backlog.py`, `tests/test_cli.py`, `tests/test_exact_and_fresh.py`.
