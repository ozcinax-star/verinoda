# 17.6 Undeclared symbols and naming rules

Row: objectives, teams, bossbars and tags used but never declared; naming conventions (Spyglass). Done when
`datapack` reports undeclared objectives.

## Why

A scoreboard objective, a team or a boss bar exists only after something declares it (`scoreboard objectives add`,
`team add`, `bossbar add`, or Java's `addObjective` / `addPlayerTeam`). A command that writes or tests one that
was never declared fails with an error the player rarely sees ("Unknown scoreboard objective"), and
`execute if score` on it is simply false. `verinoda datapack` already read objectives, but treated `objectives add`
and `objectives remove` alike and never asked whether a used name was declared. Teams and boss bars were not read
at all. Spyglass reports these as undeclared symbols and checks names against configured patterns.

## Decisions

- **Part of `datapack`, no new command or MCP tool.** The summary gains `objectives used but never declared (N)`
  (always shown), and `teams used but never declared (N)` / `boss bars used but never declared (N)` when there
  are any. In `--json`: `problems.objectives_used_never_declared`, `teams_used_never_declared`,
  `bossbars_used_never_declared`, each row `{name, status: "strong_inference", sites (first 10), uses}`. The
  counts line and `--json` carry `teams` and `bossbars`. `datapack team NAME` and `datapack bossbar ID` list every
  site like `tag` / `score`; those three lookups carry `declared` and the text says "never declared". The core MCP
  profile and its menu are unchanged.
- **Tags.** An entity tag is declared by being added; "tags checked but never added" (D52) already is the
  undeclared-tag check, so nothing new is added for tags.
- **What declares.** `scoreboard objectives add`, `team add`, `bossbar add` in mcfunction and in Java command
  strings; Java `addObjective(x, ...)`, `addPlayerTeam(x)` and Yarn's `addTeam(x)`, the first argument read
  through the constant binding of D70 (`_values`). A name Java builds (`"a_" + kind`) is a pattern: a used name it
  fits gets `maybe_declared_by` (as `maybe_added_by` for tags), never "declared". A macro declaration
  (`$team add $(t)`) is listed under `declared_by_macros`, never matched. `objectives remove` is now its own kind
  (`remove`), a use, not a declaration.
- **What uses.** Objectives: every existing read/write site, plus `scoreboard objectives modify` (modify),
  `setdisplay` (read) and `trigger` (write). Teams: `team join|modify|empty|list|remove NAME`, `team=`/`team=!` in
  selectors, Java `getPlayerTeam(x)`. Boss bars: `bossbar set|get|remove ID`, `execute store ... bossbar ID`; an id
  without a namespace is `minecraft:` as the game reads it.
- **Boss bars created in Java** (`getCustomBossEvents().create(...)`, Yarn's `getBossBarManager().add(...)`) take an
  identifier this reading does not resolve; the sites are listed (`bossbars_created_in_java`) so a reader knows a
  listed boss bar may be one of them.
- **Status.** `strong_inference`: the name is read as written, but another pack or a player's command can declare
  it in the world. The note of the summary says so.
- **Naming rules (opt-in).** `datapack.naming` in `.verinoda/config.json` maps a kind (`objective`, `team`,
  `bossbar`, `tag`, `function`; plurals accepted) to a regex that each name must match in full (a boss bar and a
  function by their whole `ns:path` id). None is set by default, as in Spyglass. Each name that breaks a rule is a
  `problems.naming` row `{kind, name, rule, at, status: "verified"}`, `at` being its declaring site (the add, or the
  function file) or its first site. An entry that is not a regex, or names an unknown kind, is listed under
  `naming_rules_unreadable` and not applied.

## Measured

- `examples/glow_mod`: 0 objectives, teams or boss bars undeclared (its one objective is declared); `datapack`
  1.9 s wall, as before (the new work is a few regexes per line and one Java regex per file).
- Fixture (`tests/test_datapack_symbols.py`): two functions and a Java class. Found: `a_ticks` (written and
  tested, never added) and `a_board` (shown in the sidebar; "maybe declared by" Java's `"a_" + kind`); teams
  `green` (modified), `purple` (joined from a Java command string) and `yellow` (Java `getPlayerTeam`); boss bar
  `minecraft:timer_old`. Not reported: objectives added in mcfunction or by Java through a constant, a team added
  by Java through a constant, `team=!blue`'s `blue`, the namespaced boss bar. With `team: "[a-z]{4,}"`, `red` is
  the one name reported, at its `team add` line.
- The private mod was not available in this worktree; its numbers are not measured.

## Limits

- Objectives and teams declared outside the repository (another datapack, a world's saved scoreboard, a command
  typed by hand) are reported; the note says a row is a lead.
- Boss bar ids Java creates are not read; storage ids (`data storage`), function tags (`#ns:x` without a tag
  file) and predicates or advancements referenced by id are not checked here.
- Only the first argument of `addObjective` / `addPlayerTeam` is read, as in the Mojang and Yarn signatures;
  a team handed around as an object (`addPlayerToTeam(name, team)`) is not a use by name.
- Naming rules apply to the names as spelled; names built at run time and macro names are not checked.

## Upgrading note

`verinoda datapack` lists objectives (and, when there are any, teams and boss bars) used but never declared, and
takes `team NAME` / `bossbar ID` lookups. Set `datapack.naming` in `.verinoda/config.json` to check names against
your conventions (off by default). In `--json`, an `objectives remove` site now has kind `remove` (it was
`define`). No MCP tool was added; the tool counts in UPGRADING do not change.
