# 1.1 Update proportional to the change - working plan (not a DESIGN draft yet)

Done when (BACKLOG.md): an update of one edited file on Verinoda's own repository takes seconds, and its graph equals a
full scan's node for node and edge for edge.

## What was measured (2026-10-01, understand workflow wf_80b560b4-96c)

Update after one appended function on a 2,760-file copy of the repo at d03ed2c: 98.8 s wall.
- graph extraction 32.1 s (AST cache loads 5.1, symbol resolution 5.8, language resolvers 3.8, python_cross /
  python_facts and other corpus passes 15.2)
- the rest of _rebuild_code ~43 s over the whole corpus: build_from_json 7.9, reconcile with the old graph 5.9,
  detect 6.5, two canonical compares 5.1, clustering 6.8, graph.json write 3.1, JSON/ignore/ctx 6.7
- Verinoda post-work 8.2 s (receiver sidecar 4.3, post-process 2.3, record 1.6)
- outside the build 15.6 s (lexicon 5.8, search 2.9, _derive load 1.7, snapshot 2.1, prune 1.65, ...)
So incremental extraction alone cannot reach seconds; the patch must bypass _rebuild_code.

## Baseline equality (tools/update_vs_scan.py, tools/graph_equal.py)

orders_app, one appended function: today's update graph == a fresh copy's scan graph (42 nodes, 76 edges) except
`_origin: semantic` left on 3 external stub nodes by the reconcile (history, not tree). Reference must always be a
FRESH COPY scan: `scan --force` still reads the AST cache and reconciles with the old graph.

## Design (critique of the three reports)

1. Ledger at every full build: per file F, its pre-resolution extraction (AST cache has it) and DEFINES(F) /
   USES(F) key sets (labels, callable markers, stub labels, ids before salting, stems/basenames, module paths,
   case-fold keys / raw_call callees, import targets, stub labels, markdown code spans, sourced scripts), with
   inverted indexes.
2. Edit of F: re-extract F; affected A = F + users of every changed key + colliding-id files + header/impl siblings;
   batch B = A + definers of every key A uses (so ambiguity counts match a full build); repeat to a fixpoint for
   re-export/barrel chains.
3. Run the unmodified vendored extract() over B (project_index is never hand-edited), keep rows A owns, splice into
   the stored extraction in path order.
4. Replace reconcile with replacement by owner; skip detect when no file was added/removed; a running digest instead
   of the two canonical compares; rerun build_from_json (later: patch per pair).
5. Leiden on the patched graph (~4 s) or deferred to the background.
6. Fall back to a full build: added/removed/renamed file, changed extraction stamp, A touching extractors that read
   other files (markdown links, mcfunction, XAML), tsconfig/workspace files, Swift extensions, C# partials, C/C++
   header pairs, or B larger than a cap.
7. Prerequisite: tie-break by id in index._visible_class and the Java class pickers (index.py:1649, 1850, 2303);
   edge collapse in build.py:1256-1263 is input-order dependent - the patch must feed edges in full-build order.

Hardest: proving DEFINES/USES complete for the ~20 cross-file passes. Plan: an oracle fuzz test - random edits
(add/rename/remove function, change a call, change an import, edit a docstring) on fixture corpora and on this repo,
patched update vs fresh-copy scan via tools/graph_equal.py; any difference is a bug or a missing fallback.

## Stages

- S0 (done here): oracle tools; baseline equal modulo `_origin` on externals.
- S1: cheap wins that keep the full build: skip detect with no added/removed files, digest instead of canonical
  compares, deferred clustering - measure, oracle stays equal.
- S2: the ledger and closure patch with fallbacks, behind a flag, oracle-fuzzed; then default on.
