# 8.6 Incremental re-review (draft for DESIGN.md; next free D-number)

## Why

An agent (or a CI job) reviews a change, fixes something, and reviews again: the second review repeats every
finding of the first, and the new one is hard to see. Bugbot and Ellipsis review only what changed since their
last review. Verinoda records each review already (the `analyses` table); `--since-last` compares with that.

## Decisions

- **`verinoda review --since-last`** and MCP `change_review` with `since_last=true` (the core gateway's one-line
  text names it; the core menu stays under its limit). Off by default: a plain `review` is unchanged.
- **Which review is "the last".** The latest recorded review of the same base commit, the same mode (working
  tree or staged), the same concerns and the same findings mode (each record now keeps this scope): a review that
  checked fewer concerns would make the others look gone. A planned change (`--target`) is not compared, and a review without a store has nothing to
  compare with; both say so in `since_last.note`.
- **A finding is itself wherever its lines moved, and only there.** Findings are matched by concern, rule, file,
  their text with line numbers masked (`path:12`, `line 12`, `@12`; other numbers, such as a metric that got
  worse, are kept) and their place: the definition holding the line and that line's code. An edit above a finding
  keeps all of these; the same risky call moved into another function is a new finding. Repeated findings are
  counted per key, so a second copy is new.
- **What is shown.** `concerns` holds only the findings the last review did not list; `since_last` gives the
  review it compared with, `repeated` (left out), `gone` (findings of the last review not found now: fixed or
  changed), `new_changes` (changed definitions, by symbol and kind, the last review did not have) and the
  method. `counts.findings_new` and `counts.findings_repeated` (also when there is no earlier review: every
  finding new); the summary is rebuilt from the new findings and says the rest in one sentence; the text output
  has a "Since the last review" section. The exit code stays the whole review's: findings still there still
  count, so `--since-last` never turns a gate green with nothing fixed.
- **Every finding, not the shown ones.** The comparison and the record use every finding before the per-concern
  cap of 25, so a new finding sorting after 25 repeated ones is shown, and one pushed past the cap is not "gone".
- **The record is complete.** The review is recorded with all its findings (each with its place) and its scope
  before the repeated ones are left out, so the next `--since-last` compares with everything this one found.
- In the capped MCP response, `since_last` is a kept key (it says what was left out).

## Measured

Tests on the orders example: a signature change gives 5 findings; reviewing again after an edit above it gives 0
new and 5 repeated; a new `os.system` call is the only new finding of the third review and its definition is
named as new; reverting the signature lists the 5 as gone.

Review round (two reviewers): fixed comparing only the 25 shown findings per concern, a new call in another
function taken for the old one, worse metrics hidden by masking every number, a gate turning green on an
unchanged tree, earlier reviews of other concerns or findings modes making findings look gone, and the summary
and counts disagreeing with the filtered list.

## Limits

- Reviews recorded before this change have no scope or places: they are not compared (the first `--since-last`
  after upgrading says every finding is new).
- A finding whose wording changes with the code (a different callee name in its text) counts as new.
- "The last review" is the last one recorded, whoever ran it (an agent's or the user's) on this machine's store.

## Upgrading note

New: `verinoda review --since-last` (MCP `change_review` with `since_last=true`) leaves out the findings the last
review of the same base and mode already listed, counts them and lists the ones gone. Without it, `review` is
unchanged. The MCP tool count is unchanged.

## Tests

`tests/test_review_since_last.py`: the first review says every finding is new; the same change again after an
edit above it shows none, counted as repeated; a new finding is the only one shown and its definition is named
new; findings gone after a revert are listed and rendered; the CLI `--since-last --json` and MCP `since_last`;
a call moved to a new function is new and the exit code still counts the old one; a review of other concerns is
not compared; findings past the per-concern cap are compared; in a project path with a space and non-ASCII. `tests/test_mcp.py` lists the new MCP argument.
