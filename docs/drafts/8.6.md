# 8.6 Incremental re-review (draft for DESIGN.md; next free D-number)

## Why

An agent (or a CI job) reviews a change, fixes something, and reviews again: the second review repeats every
finding of the first, and the new one is hard to see. Bugbot and Ellipsis review only what changed since their
last review. Verinoda records each review already (the `analyses` table); `--since-last` compares with that.

## Decisions

- **`verinoda review --since-last`** and MCP `change_review` with `since_last=true` (the core gateway's one-line
  text names it; the core menu stays under its limit). Off by default: a plain `review` is unchanged.
- **Which review is "the last".** The latest recorded review of the same base commit and the same mode (working
  tree or staged). A planned change (`--target`) is not compared, and a review without a store has nothing to
  compare with; both say so in `since_last.note`.
- **A finding is itself wherever its lines moved.** Findings are matched by concern, rule, file and their text
  with every number masked: an edit above a finding shifts its line numbers (in `at` and in the text) but not its
  words. Repeated findings are counted per key, so a second copy of the same finding is new.
- **What is shown.** `concerns` holds only the findings the last review did not list; `since_last` gives the
  review it compared with, `repeated` (left out), `gone` (findings of the last review not found now: fixed or
  changed), `new_changes` (changed definitions, by symbol and kind, the last review did not have) and the
  method. `counts.findings_new` and `counts.findings_repeated`; the summary says it in one sentence; the text
  output has a "Since the last review" section. The exit code counts only the new findings (unknowns and
  uncovered lines as before).
- **The record is complete.** The review is recorded with all its findings before the repeated ones are left
  out, so the next `--since-last` compares with everything this one found, not with what it showed.
- In the capped MCP response, `since_last` is a kept key (it says what was left out).

## Measured

Tests on the orders example: a signature change gives 5 findings; reviewing again after an edit above it gives 0
new and 5 repeated; a new `os.system` call is the only new finding of the third review and its definition is
named as new; reverting the signature lists the 5 as gone.

## Limits

- Two findings with the same rule, file and wording but different places are matched by count, not by place.
- A finding whose wording changes with the code (a different callee name in its text) counts as new.
- "The last review" is the last one recorded, whoever ran it (an agent's or the user's) on this machine's store.

## Upgrading note

New: `verinoda review --since-last` (MCP `change_review` with `since_last=true`) leaves out the findings the last
review of the same base and mode already listed, counts them and lists the ones gone. Without it, `review` is
unchanged. The MCP tool count is unchanged.

## Tests

`tests/test_review_since_last.py`: the first review says every finding is new; the same change again after an
edit above it shows none, counted as repeated; a new finding is the only one shown and its definition is named
new; findings gone after a revert are listed and rendered; the CLI `--since-last --json` and MCP `since_last`;
in a project path with a space and non-ASCII. `tests/test_mcp.py` lists the new MCP argument.
