# 4.5 Suggested reviewers and related changes (draft for DESIGN.md; next free D-number)

## Why

A review tool that finds what a change touches can also say who knows that code and what happened to it before:
the people who last changed the lines being modified, the owners the repository declares, and the earlier
commits (with their stated reasons) that changed the same definitions. Git already holds all three; CodeRabbit
and similar tools show them on a PR. Here they come from local git reads, as claims with their evidence.

## Decisions

- **Part of `review`**, a `reviewers` key (CLI `--json`, the text output's "Reviewers and related changes"
  section, MCP `change_review`), not a new command or MCP tool. The MCP response carries it compact (who, how
  many lines, which rule, which commits, with statuses; no claim texts or evidence) and not as a kept key, so the
  12,000-character cap cuts it before any finding; `review --json` has the full claims.
- **Suggested reviewers** come from `git blame -w` at the base commit over the base lines the change modifies or
  removes (`Change.old_changed`, or the definition's base span): the code as it was, not the new lines. Authors
  are ranked by those lines (mailmap applied by git); at most five are listed with the total. Each is a
  `strong_inference` claim ("X last changed N of the M base lines this change modifies ...; a likely reviewer"),
  evidence a `git blame -w -L<a>,<b> <base> -- <file>` command per range, with the uncertainty that blame
  credits whoever last touched a line; each evidence item says how many of that range's lines the author holds.
  A change that only inserts lines modifies no base line and names no one; a removed definition's base lines are
  all removed. Authors are keyed through git's mailmap, and rows with the same displayed name are one person.
  At most 20 ranges are blamed, taken one per file in turn; when the cap cuts, the claim says "N of the B blamed
  base lines of the M this change modifies" and a note says so.
- **The change's own author is left out** (`git config user.name`/`user.email` of the work tree, mapped through
  `git check-mailmap`) and said so in `excluded` with the lines they wrote: suggesting yourself as your reviewer
  is noise.
- **Declared owners**: the CODEOWNERS rule deciding each changed file, read with the ownership module's GitHub
  rules (`statically_verified` at the rule's line, which is its evidence; `strong_inference` when the file has
  GitLab sections).
- **Related changes**: `git log -L` from the base over each modified or removed definition's base lines (three
  commits per definition, eight definitions), through `history.symbol_commits` with a revision (new `rev`
  parameter: the lines are that commit's; `probe=False` skips its own rev-parse calls). Merged by commit, newest
  first by commit time, at most ten; each a `primary_source_verified` claim that the commit changed those
  definitions, with the evidence of each file it names.
- **Why a list is empty or partial** is always said: `not_checked` (a list, as `made_stale` has), `notes` (a
  shallow clone, a range that could not be blamed, the blame cap, definitions whose history was not read), in the
  JSON, the text output and the MCP block.
- **Not checked**: a planned change (`review --target`, no diff) and a tree that is not a git work tree say why.
  A shallow clone adds a limit, and blame's boundary commits in a shallow clone are not credited.

## Measured

Tests only (a three-author fixture): Alice's rewritten lines name Alice, the user's own line is left out, Bob's
tax change names Bob and quotes "The ledger stores cents."; CODEOWNERS and the related commits are listed.

Review round (two reviewers): fixed a pure insertion claimed as modifying a whole definition's lines, the user
suggested as their own reviewer when their address is mailmapped, the blame cap's totals (the claim counted only
blamed lines and the first files), one person split by two addresses, evidence excerpts that repeated the author's
total, declared owners without evidence, related commits citing only the first file, date-string ordering, about
36 redundant `rev-parse` calls per review, and silent empty lists.

## Limits

- Blame is a heuristic of knowledge: a reformat or moved block credits whoever made it.
- Only the lines the change modifies are blamed; the authors of nearby or calling code are not suggested.
- At most 20 line ranges blamed and eight definitions' histories read per review.
- `git log -L` stays within one file (a definition moved from another file starts where it arrived).

## Upgrading note

`review` (and MCP `change_review`) has a new `reviewers` key: suggested reviewers from `git blame` of the base
lines the change modifies (the change's own author left out), the CODEOWNERS owners of the changed files, and the
earlier commits that changed the same definitions with their messages. Nothing else in the output changes. The
MCP tool count is unchanged.

## Tests

`tests/test_reviewers.py`: the authors of the modified base lines ranked with counts and blame evidence; the
change's author left out; the CODEOWNERS rule; related commits limited to the definitions touched, with the
message body; added code and a planned change name no one; the text section and `--json`; a project path with a
space and non-ASCII.
