# 17.9 Client and server separation (draft for the next free D-number)

## Why

A Minecraft mod runs on the client and on a dedicated server. Code that exists only on the client (Loom's split
`src/client` source set, a class or method annotated `@Environment(EnvType.CLIENT)` or `@OnlyIn(Dist.CLIENT)`, the
game's `net.minecraft.client` packages) crashes a server that loads it, often only when a player first triggers
the path. Loom's split source sets catch a direct reference from `src/main` at compile time; they do not catch a
path through an annotated class, a Forge single source set, or a vanilla client class named in common code.
Verinoda had the pieces (JVM entry points from `framework_entries`, call edges, a `no_edge` guard for direct
edges between two globs) but no walk from the server side to client-only code.

## Decisions

- **A map view, not a command or an MCP tool.** `verinoda map --view sides [--json]` and MCP `map_view`
  (`view: sides`, behind `run_tool`). Like `dead` and `hotspots` it is in `architecture_map.VIEWS` but not in
  `DEFAULT_VIEWS`. The core profile stays at five tools; the core menu grows by `|sides` in `run_tool`'s
  catalog (the test's 4,500-character bound still holds).
- **Client-only symbols** (`sides._client_marks`), each with a `basis` and the line that makes it client-only:
  - `source_set`: every symbol of a file under a `src/client/` folder (cited at `file:1`);
  - `annotation`: a class or method whose declaration head (`architecture_map._decl_head`, comment- and
    string-free code) carries `@Environment(EnvType.CLIENT)`, `@OnlyIn(Dist.CLIENT)` (with `value =`, a
    qualified or statically imported constant) or `@EventBusSubscriber(... Dist.CLIENT)`; a class annotation
    covers every symbol declared inside the class span. `Dist.DEDICATED_SERVER` / `EnvType.SERVER` are not
    client marks.
  - Classes of `net.minecraft.client.`, `com.mojang.blaze3d.`, `net.fabricmc.fabric.api.client.`,
    `net.minecraftforge.client.` and `net.neoforged.neoforge.client.`: not graph nodes, so they are matched in
    the code lines of a reached method itself (lines of nested symbols excluded): an imported simple name (the
    import line is cited) or a fully qualified name. Wildcard imports are not expanded.
- **Server roots** are `architecture_map.framework_entries` (declared, framework, callback) minus the ones in
  client-only code and the ones whose reason names the client (`"client"` entrypoint, `ClientModInitializer`, a
  client tick event, a mixin into `net.minecraft.client...`, a `playToClient` handler). They are listed under
  `searched.entry_points`; the number left out is `summary.client_entry_points_left_out`. No root: `unknown`
  with the reason, no claims (never an empty "ok"). No Java or Kotlin file: a `note`.
- **The walk** is breadth-first from all roots at once (the shortest path from any root). A reached method or
  function follows `calls`, `uses`, `references`, `references_constant`, `instantiates`, `indirect_call`,
  `registers` and the supertype relations; a reached class follows only its supertypes (loading a class loads
  them; its methods run only when called). Test files and non-JVM targets are not entered. The walk stops at a
  client-only symbol: that crossing is the finding.
- **Claims.** `kind: client_symbol_reached` or `client_class_use`; `subject` (`Owner.method`, a class, or the
  fully qualified client class); `at` (the crossing line); `entry` (symbol, at, basis); `path` (every hop:
  from, to, relation, `file:line`, confidence); `client_only` (the reason and its line); `evidence_at` (the
  entry, every hop, the reason line); a sentence naming all of it. Status `strong_inference` (reachability
  over extracted edges from heuristic entry points), `weak_inference` when a hop is an INFERRED edge.
- **Unreached crossings.** An edge from common code into client-only code that no server root reaches is
  listed under `unreached_crossings` (capped at 20, counted in the summary), not claimed: under split source
  sets it is a compile error, otherwise dead or client-guarded code.
- **Text output**: the counts, then per path one line with status, subject, crossing line and reason line, and
  one `entry -> ... -> target` line; then the unreached crossings.

## Measured

On the test fixture (8 Java files, Fabric and Forge annotations mixed): 5 paths (source-set method, class
annotation, method annotation, `Dist.CLIENT` event subscriber, `MinecraftClient` named in a reached method), a
commented-out use and a `Dist.DEDICATED_SERVER` method not reported, 3 client entry points left out, 2
unreached crossings. The view costs one `framework_entries` pass plus one read of each annotated file and of
each reached method's file; not measured on a real mod corpus in this branch.

## Limits

- Entry points are the dataflow view's JVM heuristics; a server root they miss (a reflective registry, a
  lambda stored and run later) hides its paths. The "names the client" filter is a word match on the reason.
- A guarded use (`if (world.isClient)`, `DistExecutor`, an `EnvType` check, `FabricLoader.getEnvironmentType()`)
  is still reported: the guard is not read. The claim is about reachability, not a crash.
- Calls the extractor did not resolve (dynamic dispatch through an interface or a superclass method) are not
  followed; a reached class's field types and static initialiser are not walked.
- `client` mixin arrays in `*.mixins.json`, `@Environment` on fields and `EnvironmentInterface` are not read;
  `src/client` is the only source-set name recognised (Architectury `client` modules are not).
- Client-package classes are matched by name in the method's code lines; a simple name shadowed by a local
  class of the same name is still counted.

## Upgrading note

`verinoda map --view sides` (and MCP `map_view` with `view: sides`, through `run_tool`) lists client-only code
(the `src/client` source set, `@Environment(EnvType.CLIENT)` / `@OnlyIn(Dist.CLIENT)` classes and methods,
`net.minecraft.client` classes) that the mod's server-side entry points reach, each path a `strong_inference`
claim with every hop at `file:line`. Plain `verinoda map` is unchanged. No new MCP tool: the tool counts in
UPGRADING, README and ARCHITECTURE do not change.

## Tests

`tests/test_sides.py`: a Fabric/Forge fixture where `Mod.onInitialize` (a `main` entrypoint) calls
`Helper.setup`, which calls a `src/client` method, a method of an `@Environment(EnvType.CLIENT)` class, an
`@OnlyIn(Dist.CLIENT)` method, a `Dist.DEDICATED_SERVER` method, a method of an `@EventBusSubscriber(value =
Dist.CLIENT)` class, and a helper naming `MinecraftClient`. Checked: each path with every hop and line, the
reason line (source set, class and method annotation, event subscriber, import), the server-only method and
the commented use not reported, client entry points (source set, `ClientModInitializer` in `src/main`, a client
event subscriber) left out, unreached crossings listed (`Helper.never`, `MainClientInit`) and client-to-client
calls not; an INFERRED hop (`new Annot()`) giving `weak_inference`; no server root giving `unknown`; a Python
project giving the note; the text renderer; view registration (not a default view); `map --view sides --json`
through the CLI. `tests/test_mcp.py::test_map_view_equals_core` covers `sides` through MCP.
