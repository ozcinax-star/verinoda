# Guards written as programs (script guards)

## Why

The guard kinds of a decision record (`only_in`, `no_edge`, `layers`, `allow_edges`, `public`, `dependency`)
cover the rules that fit one line of `key=value`. A team's rule often does not: "every handler in `api/` that
writes calls `audit()` first", "no module under `core/` reads a setting that is not in `settings.py`". Archgate
lets an ADR carry its check as a small program with access to the code. Here the same thing runs inside
`decide check`, so its result sits beside the other guards' (file:line, exit codes, baseline, waivers, SARIF,
`--changed`), instead of in a separate CI step nobody connects to the decision.

## Decisions

- **A new guard kind `script path=FILE.py [timeout=SECONDS]`.** The file is a Python file inside the repository
  (relative, no `..`; `decide record` / `decide guard` also want it to exist) that defines `check(guard)`.
  `timeout` is 1-600 seconds, default 60. The spec is checked again when a record is read, so a hand edit
  that points it at `/etc/x.py` or gives `timeout: true` makes the record unreadable (not enforced, reported),
  never a guard that runs something else.
- **What the script gets** (`GuardAPI`, read-only): `repo`, `spec`, `files()`, `nodes(file=None)`, `node(id)`,
  `edges(relations=None, from_file=None, to_file=None)` - each edge in its true direction with the file and
  line the index cites -, `claims(status=None, limit=1000)` - the stored claims, newest first, with their
  supporting evidence as `path:line` -, and `read(path)`. It reports with `guard.violation(path, line, why)`
  and `guard.possible(path, line, why)`; the return value is not read. The graph is `.verinoda/index/graph.json`
  as the index last wrote it; `decide check` refreshes the index first when a script guard is enforced, as it
  does for edge guards.
- **Its result is evidence like the other guards'.** Every finding must cite a line of a file of the
  repository: the file is read again and the line must exist; the line's text is shown as for any guard, and
  the path is the file's own spelling (`APP/VIEWS.PY` on Windows is cited as `app/views.py`). A citation
  outside the repository (a link or junction that leads out of it too), past the end of the file, without a line or of a missing file is listed
  under `unknown` (so the check exits 3), never dropped and never counted as a violation. A VIOLATED of a
  script guard has the status `strong_inference`, not `statically_verified`: the script's own logic is not
  verified here, only its citation. A POSSIBLE is `weak_inference`. A finding counts as new under `--changed`
  / `--base` when its file or the script changed.
- **A script that does not end well is `unknown`, never ok.** An exception (with its type, message and the
  script's line), `sys.exit` (any code, 0 too), `os._exit`, no `check` function, a syntax error, a timeout,
  a child that prints no result: each is `unknown` with the reason, and `decide check` exits 3. An ok means the
  script ran `check` to its end; its scope is `{"script_runs": 1}` and its limits say what that does not
  prove. What the script printed is kept (its last 2,000 characters; 400 in the limits).
- **Where it runs.** Only from the CLI's `decide check` and `decide baseline` (`guards.check(run_scripts=True)`);
  `update`'s summary line, `what-if` and MCP `decision_check` report a script guard as `unknown` ("runs only
  from the CLI"). MCP `decision_record` refuses to record or add a script guard (a script guard runs code: the
  user adds it in a terminal). `decide ask` does not apply script guards (they say nothing about one
  dependency).
- **Only in a project the user trusts.** A script guard runs the project's own code, so it follows the trust
  rule of the test runs: in a project not marked with `verinoda trust` (stored outside every repository) it is
  not run and is `unknown`, with the next step for the user and "an agent must never run it for them". A CI
  job that should run script guards trusts its checkout itself (`verinoda trust . --yes`).
- **Isolation it has.** A child process of Verinoda's own interpreter (`sys.executable`), never the project's
  `.venv`, started with `-I -B -X utf8`: no `PYTHON*` variables, no user site-packages, neither the script's
  folder nor the working folder on `sys.path`, no bytecode written, and `open()` reads UTF-8 whatever the
  machine's code page. The environment is the test runs' short allowlist
  (`PATH`, `SYSTEMROOT`, `LANG`, ...: no tokens or keys) with `HOME`/`USERPROFILE`/`TMP`/`TEMP`/`TMPDIR` set to a
  fresh folder that is deleted afterwards. The working folder is the project root; the request goes on stdin
  (no paths on the command line, so spaces and non-ASCII letters need nothing). The timeout kills the child.
  Before the script is read, the child opens the claims store read-only (`mode=ro`, `query_only`) and installs
  a Python audit hook that refuses: socket creation, connect, bind and name lookups (`urllib`, `http.client`
  too); process creation (`subprocess`, `os.system`, `exec*`, `spawn*`, `posix_spawn`, `startfile`, `fork`,
  `kill`); `ctypes` libraries and calls; new `sqlite3` connections and extensions; adding another audit hook
  (CPython then drops it silently); opening a file for writing, appending, creating or truncating, and remove,
  rename, mkdir, rmdir, chmod, chown, link, symlink, utime and the `shutil` copy/move/rmtree calls. A refused
  call raises `PermissionError` in the script ("refused in a script guard: socket.connect ..."), so the guard is
  `unknown` unless the script handles it.
- **Isolation it does not have** (said in each result's limits). This is not a sandbox. Audit hooks are not a
  security boundary (CPython's documentation says so): an extension module the script imports runs native
  code that raises no audit event, and `mmap` or a handle opened before the hook is not checked. Reads are
  not limited: the script can read every file the user can and print it (the output is shown back, cut).
  Memory and CPU are limited only by the timeout; on a timeout only the child is killed (it cannot start
  processes through the Python calls above, but native code could). The point is that a trusted project's
  own rule does not quietly reach the network, start programs or change files; an untrusted project's script
  does not run at all.
- **Pre-commit.** No hook ran `decide check` before (`verinoda hooks` re-indexes after commits, checkouts and
  merges). `.pre-commit-hooks.yaml` now offers `verinoda-decide-check` for the pre-commit framework:
  `verinoda decide check --changed`, no file names, always run; violations new or touched since HEAD stop the
  commit (exit 1), and so does a guard that could not be checked (exit 3). A script guard runs there like in
  any `decide check`.

## Measured

Windows 11, Python 3.13, the worktree on a loaded machine:

- An empty script in a folder whose name has spaces and non-ASCII letters: 0.26-0.37 s per run (five runs),
  the child's start included.
- Loading this repository's graph in the child (`graph.json`, 36 MB, 30,971 nodes, 73,325 edges): 0.96 s, done
  only when the script asks for the graph.
- The audit hook, tried from a script: a TCP connect, `getaddrinfo`, `subprocess.run`, `os.system`, `open(...,
  "w")`, `open(..., "a")`, `os.remove`, `os.mkdir`, `ctypes` (on Windows importing `ctypes` itself fails) and a
  second audit hook are all refused; reading a file works; no file was created, changed or removed.

## Limits

- Not a sandbox (above). Native code, reads and memory are not confined.
- The script runs with Verinoda's interpreter and its installed packages, not the project's environment: a
  script that imports the project's dependencies fails unless they are installed there too. Helper modules
  next to the script are not importable (its folder is not on `sys.path`).
- The graph is the index's file (`graph.json`); the receiver-call edges `index.load` adds in memory are not in
  it. With no index, `guard.edges()` raises and the guard is `unknown`.
- A script that starts threads which never end runs until the timeout.
- A script that reports more than 500 findings: the rest are counted under `unknown`.
- The pre-commit hook installs Verinoda in the framework's own environment; trust is still per user and path.

## Upgrading note

A decision record may now carry a `script path=FILE.py [timeout=SECONDS]` guard: a Python file in the repository
that defines `check(guard)` and reports `guard.violation(path, line, why)` or `guard.possible(...)`, reading the
graph and the stored claims through `guard`. `verinoda decide check` and `decide baseline` run it only in a
project you trust (`verinoda trust`), in a child process with a scrubbed environment, a timeout and an audit
hook that refuses network, new processes, ctypes and file writes; this is not a sandbox. Through MCP, in
`update` and in `what-if` a script guard is `unknown`, and MCP does not record one. A script that raises, exits
or times out makes the check exit 3. `guards.check` has a new keyword `run_scripts` (default False).
`.pre-commit-hooks.yaml` offers the `verinoda-decide-check` hook for the pre-commit framework.

## Tests

`tests/test_script_guards.py` (18 tests): a violation at a cited line with the line's text and
`strong_inference`; a clean script is ok with its scope, its printed output and its limits; a raise (with the
script's line), `sys.exit(0)`, no `check`, a syntax error and `os._exit(0)` are each `unknown` and exit 3; a
script past `timeout=1` is stopped and `unknown`; the audit hook refuses network, lookups, processes,
`os.system`, writes, appends, removal, mkdir, ctypes and a second audit hook, and the files are unchanged;
citations outside the repository, absolute, past the end, without a line and of a missing file are `unknown`
while `.\app\db.py:5` is accepted; a citation through a junction out of the repository is `unknown` and an
upper-case citation is given the file's spelling; a script named `guards/kural ğ.py` (quoted in the spec)
reads a UTF-8 file with Turkish letters through plain `open()`; the spec rules (paths, `.py`, existence, timeout range, unknown keys, a
hand-edited record); a script reached through a junction or link outside the repository is not run; without
`run_scripts` (and through MCP `decision_check`) and in an untrusted project the guard is `unknown` with the
reason; MCP refuses to record one; `decide check --json` runs it on a scanned project with the graph and the
claims, and `decide baseline --record` then lets `decide check` pass; the pre-commit hook's entry parses as
`decide check`. All in a project folder whose name has a space and non-ASCII letters.
