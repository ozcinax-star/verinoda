# Guards written as programs (script guards)

## Why

The guard kinds of a decision record (`only_in`, `no_edge`, `layers`, `allow_edges`, `public`, `dependency`)
cover the rules that fit one line of `key=value`. A team's rule often does not: "every handler in `api/` that
writes calls `audit()` first", "no module under `core/` reads a setting that is not in `settings.py`". Archgate
lets an ADR carry its check as a small program with access to the code. Here the same thing runs inside
`decide check`, so its result sits beside the other guards' (file:line, exit codes, baseline, waivers, SARIF,
`--changed`), instead of in a separate CI step nobody connects to the decision.

## Decisions

- **A new guard kind `script path=FILE.py [timeout=SECONDS]`.** The file is a Python file inside the repository
  (relative, no `..`; `decide record` / `decide guard` also want it to exist) that defines `check(guard)`.
  `timeout` is 1-600 seconds, default 60. The spec is checked again when a record is read, so a hand edit
  that points it at `/etc/x.py` or gives `timeout: true` makes the record unreadable (not enforced, reported),
  never a guard that runs something else.
- **What the script gets** (`GuardAPI`, read-only): `repo`, `spec`, `files()`, `nodes(file=None)`, `node(id)`,
  `edges(relations=None, from_file=None, to_file=None)` - each edge in its true direction with the file and
  line the index cites -, `claims(status=None, limit=1000)` - the stored claims, newest first, with their
  supporting evidence as `path:line` -, and `read(path)`. It reports with `guard.violation(path, line, why)`
  and `guard.possible(path, line, why)`; the return value is not read. The graph is `.verinoda/index/graph.json`
  as the index last wrote it, without the receiver-call edges `index.load` adds from `receiver_calls.json`
  (said in `GuardAPI.edges`, the README and each result's limits); `decide check` refreshes the index first
  when a script guard is enforced, as it does for edge guards. The file filters of `nodes` and `edges` are
  exact strings (`/`-separated, case-sensitive on Windows too). The claims are read by Verinoda before the
  child starts - the newest 20,000, with a limit naming how many older ones were left out - and handed to it
  as data: the child has no database connection.
- **Its result is evidence like the other guards'.** Every finding must cite a line of a file of the
  repository: the file is read again and the line must exist; the line's text is shown as for any guard, and
  the path is the file's own spelling (`APP/VIEWS.PY` on Windows is cited as `app/views.py`). A citation
  outside the repository (a link or junction that leads out of it too), past the end of the file, without a
  line or of a missing file is listed under `unknown` (so the check exits 3), never dropped and never counted
  as a violation. A VIOLATED of a script guard has the status `strong_inference`, not `statically_verified`:
  the script's own logic is not verified here, only its citation. A POSSIBLE is `weak_inference`. A finding
  counts as new under `--changed` / `--base` when its file or the script changed; a pre-existing one says
  "pre-existing: FILE and the guard's script SCRIPT unchanged since REF". The first 500 findings are listed,
  the rest counted under `unknown`. `decide check`'s text output prints a script finding's limits under it.
- **A script that does not end well is `unknown`, never ok.** An exception (with its type, message and the
  script's line), `sys.exit` (any code, 0 too), `os._exit`, no `check` function, a syntax error, a timeout,
  a child that prints no result: each is `unknown` with the reason, and `decide check` exits 3. An ok means the
  script ran `check` to its end; its scope is `{"script_runs": 1}` and its limits say what that does not
  prove. What the script printed is kept (its last 2,000 characters; 400 in the limits).
- **The result channel.** Before the script loads, the child reads the whole request from stdin (nothing is
  left there to read again), takes the per-run nonce out of it, keeps a private copy of the stdout pipe
  (`os.dup(1)`), points file descriptor 1 at the null device and `sys.stdout` / `sys.__stdout__` /
  `sys.stderr` at the in-memory tail of what the script prints. The result is written only to the private
  copy and carries the nonce; the parent takes the line with this run's nonce. A script that prints a fake
  result line, writes it to `sys.__stdout__` or `os.write(1, ...)` and calls `os._exit(0)` leaves no result
  (`unknown`); one that writes result-like lines to every descriptor, the private one included, makes the
  run an error even when the real result says ok.
- **Where it runs.** Only from the CLI's `decide check` and `decide baseline` (`guards.check(run_scripts=True)`);
  `update`'s summary line, `what-if` and MCP `decision_check` report a script guard as `unknown` ("runs only
  from the CLI"). `update` counts them on their own ("1 script guard(s): `decide check` runs them"), not as
  "not checked" on every update. MCP `decision_record` refuses to record or add a script guard, and refuses
  `accept` when one of the chosen guards is a script guard (a proposed one written into a record by hand is
  accepted in a terminal). The refusal splits the spec as `parse_guard` does (`s""cript`, `'scr'ipt`,
  `sc"ri"pt` are the kind `script` there too), and `record`, `add_guards` and `accept` check the parsed kind
  again (`allow_scripts=False` from MCP). MCP `import` proposes only `only_in` guards; `supersede`, `link` and
  `waive` activate no guard. `decide ask` does not apply script guards (they say nothing about one dependency).
- **Trust is the boundary.** A script guard runs the project's own code with the user's privileges, exactly
  like the project's tests under `experiment run` in a trusted project. In a project not marked with
  `verinoda trust` (stored outside every repository) it is not run and is `unknown`, with the next step for
  the user and "an agent must never run it for them". A CI job that should run script guards trusts its
  checkout itself (`verinoda trust . --yes`). A record edited by hand by anyone who can write the repository
  can carry an accepted script guard: trusting a project means trusting its content, as for its tests.
- **What the child process gives.** A child process of Verinoda's own interpreter (`sys.executable`), never
  the project's `.venv`, started with `-I -B -X utf8`: no `PYTHON*` variables, no user site-packages, neither
  the script's folder nor the working folder on `sys.path`, no bytecode written, and `open()` reads UTF-8
  whatever the machine's code page. The environment is the test runs' short allowlist (`PATH`, `SYSTEMROOT`,
  `LANG`, ...: no tokens or keys) with `HOME`/`USERPROFILE`/`TMP`/`TEMP`/`TMPDIR` set to a fresh folder that is
  deleted afterwards. The working folder is the project root; the request goes on stdin (no paths on the
  command line, so spaces and non-ASCII letters need nothing). The timeout kills the child.
- **The audit hook is a tripwire, not a sandbox.** Installed before the script is read, it refuses: socket
  creation, connect, bind and name lookups (`urllib`, `http.client` too); process creation (`subprocess`,
  `os.system`, `exec*`, `spawn*`, `posix_spawn`, `startfile`, `fork`, `kill`); `ctypes` libraries and calls;
  `sqlite3` connections and extensions; adding another audit hook (CPython then drops it silently); opening a
  file for writing, appending, creating or truncating, and remove, rename, mkdir, rmdir, chmod, chown, link,
  symlink, utime, mkfifo, mknod and the `shutil` copy/move/rmtree calls; an `mmap` of a file with write access
  (`ACCESS_DEFAULT`, `ACCESS_WRITE`; `ACCESS_READ`, `ACCESS_COPY` and anonymous memory stay allowed). On
  Windows also `_winapi.CreateFile`, `CreateJunction`, `CreateNamedPipe`, `CreatePipe`, `OpenProcess` and
  `TerminateProcess`, `msvcrt.open_osfhandle`, the registry writes (`winreg.CreateKey`, `SetValue` /
  `SetValueEx`, `DeleteKey`, `DeleteValue`, `SaveKey`, `LoadKey`, `ConnectRegistry`, the reflection calls,
  `OpenKey` with write access; reads stay allowed), and `open` / `os.listdir` / `os.scandir` / `os.chdir` of a
  UNC or device path (`\\server\share`, `//server/share`, `\\.\pipe\...`; `\\?\C:\...` is local and allowed).
  A refused call raises `PermissionError` in the script ("refused in a script guard: socket.connect ..."), so
  the guard is `unknown` unless the script handles it.
- **What gets past it** (said in each result's limits, the module docstring and the README). Audit hooks are
  not a security boundary (CPython's documentation says so). Calls that raise no audit event: `os.stat` and the
  `exists()` / `is_file()` family (which reach a UNC path or a mapped network drive too), `_winapi.WriteFile`
  and `CreateFileMapping` on a handle the process already has, named anonymous `mmap` memory, a drive letter
  mapped to a network share. Native code (an extension module the script imports). Handles opened before the
  hook (the inherited standard streams). A script that digs through the interpreter - frames, `gc`,
  monkeypatching `json` or `os` - can find the nonce or change the result before it is written: the nonce
  stops a stray or naive fake result, not a determined script. Reads are not limited: the script can read
  every file the user can and print it (the output is shown back, cut). Memory and CPU are limited only by the
  timeout; on a timeout only the child is killed (it cannot start processes through the calls above, but
  native code could). An untrusted project's script does not run at all.
- **Pre-commit.** No hook ran `decide check` before (`verinoda hooks` re-indexes after commits, checkouts and
  merges). `.pre-commit-hooks.yaml` now offers `verinoda-decide-check` for the pre-commit framework (3.2.0 or
  later, `stages: [pre-commit]`): `verinoda decide check --changed`, no file names, always run; violations new
  or touched since HEAD stop the commit (exit 1), and so does a guard that could not be checked (exit 3). A
  script guard runs there like in any `decide check`, so a collaborator who has not run `verinoda trust` on
  their checkout gets exit 3 (script guards unknown) on every commit; the file's comment and the README say so.

## Measured

Windows 11, Python 3.13, the worktree on a loaded machine:

- An empty script in a folder whose name has spaces and non-ASCII letters: 0.26-0.37 s per run (five runs),
  the child's start included.
- Loading this repository's graph in the child (`graph.json`, 36 MB, 30,971 nodes, 73,325 edges): 0.96 s, done
  only when the script asks for the graph.
- The audit hook, tried from a script: a TCP connect, `getaddrinfo`, `subprocess.run`, `os.system`, `open(...,
  "w")`, `open(..., "a")`, `os.remove`, `os.mkdir`, `ctypes` (on Windows importing `ctypes` itself fails) and a
  second audit hook are all refused; reading a file works; no file was created, changed or removed.

Review round. Two reviews found an MCP refusal that split the spec on spaces while `parse_guard` uses shlex
(`s""cript path=g.py` was recorded), MCP `accept` activating a proposed script guard, the read-only claims
connection reachable from the script (`guard._conn`: `PRAGMA query_only=OFF`, `VACUUM INTO` and `ATTACH
'file:X?mode=rwc'` wrote files outside the repository), Windows calls the hook let through (`_winapi`,
`winreg`, `msvcrt.open_osfhandle`, a writable `mmap`, UNC paths), and a result a script could forge by
printing a result line and calling `os._exit(0)`. All fixed as described above, each with a test; the audit
events were checked by name on this machine (`_winapi.WriteFile` and `CreateFileMapping` raise none and are
listed as gaps). An empty script now runs in 0.29-0.43 s (five runs). Reading the claims in the parent:
0.65 s and 4.5 MB of JSON for 20,000 claims of a synthetic 25,000-claim store, every run; this repository's
own store holds 6.

## Limits

- Not a sandbox (above): calls with no audit event, native code, handles opened before the hook, reads and
  memory are not confined, and a script that digs through the interpreter can forge its result. Trust is the
  boundary.
- The script runs with Verinoda's interpreter and its installed packages, not the project's environment: a
  script that imports the project's dependencies fails unless they are installed there too. Helper modules
  next to the script are not importable (its folder is not on `sys.path`).
- The graph is the index's file (`graph.json`); the receiver-call edges `index.load` adds in memory are not in
  it. With no index, `guard.edges()` raises and the guard is `unknown`.
- `guard.claims()` sees the newest 20,000 stored claims; the claims are read again for every script guard run
  (0.65 s for 20,000).
- A script that starts threads which never end runs until the timeout.
- A script that reports more than 500 findings: the rest are counted under `unknown`.
- The pre-commit hook installs Verinoda in the framework's own environment; trust is still per user and path,
  so an untrusted checkout gets exit 3 on every commit while an accepted script guard is enforced.

## Upgrading note

A decision record may now carry a `script path=FILE.py [timeout=SECONDS]` guard: a Python file in the repository
that defines `check(guard)` and reports `guard.violation(path, line, why)` or `guard.possible(...)`, reading the
graph and the stored claims through `guard`. It runs the project's own code with your privileges, like the
project's tests: `verinoda decide check` and `decide baseline` run it only in a project you trust (`verinoda
trust`), in a child process with a scrubbed environment, a timeout and an audit hook that is a tripwire against
accidental network, processes and file writes, not a sandbox. Through MCP, in `update` and in `what-if` a script
guard is `unknown`, and MCP neither records nor accepts one. A script that raises, exits or times out makes the
check exit 3. `guards.check` has a new keyword `run_scripts` (default False); `decisions.record`, `add_guards`
and `accept` have `allow_scripts` (default True). `.pre-commit-hooks.yaml` offers the `verinoda-decide-check`
hook for the pre-commit framework (3.2.0 or later).

## Tests

`tests/test_script_guards.py` (26 tests): a violation at a cited line with the line's text and
`strong_inference`; a clean script is ok with its scope, its printed output and its limits; a raise (with the
script's line), `sys.exit(0)`, no `check`, a syntax error and `os._exit(0)` are each `unknown` and exit 3; a
script past `timeout=1` is stopped and `unknown`; the audit hook refuses network, lookups, processes,
`os.system`, writes, appends, removal, mkdir, ctypes and a second audit hook, and the files are unchanged; on
Windows it refuses `_winapi` CreateFile, CreateJunction, CreateNamedPipe, CreatePipe, OpenProcess and
TerminateProcess, `msvcrt.open_osfhandle`, `winreg` CreateKey, SetValueEx, DeleteValue, OpenKey with
`KEY_SET_VALUE` and ConnectRegistry, a writable `mmap`, UNC `open` / `listdir` / `scandir` / `chdir` and a
`\\.\pipe` path, while a registry read, a read-only `mmap` and a `\\?\C:\` path work, and no file, junction or
registry value is left behind; the child has no sqlite connection (none in `gc`, `sqlite3.connect` refused)
and gets the claims as data; a fake result line on `print`, `sys.__stdout__` and `os.write(1)` followed by
`os._exit(0)` is `unknown` ("without a result"), and the same written to every descriptor followed by a normal
end is `unknown` ("wrote to the result channel"); citations outside the repository, absolute, past the end,

the spec rules (paths, `.py`, existence, timeout range, unknown keys, a hand-edited record); a script reached

`claims(status=...)`), the text output shows the script finding's limits (the receiver-call edges among them),
