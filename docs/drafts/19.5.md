## Why

`review --observe` ran the selected tests once, on the working tree, and said which changed functions they
reached. What the change did at run time was left to the reader: a query that now runs in a loop, a library call
the code did not make before, an exception type that changed, a route no longer reached. AppMap compares two
recorded runs for this; Verinoda had the recordings (the call tracer, D28; SQL and stacks, D147) but only ever
one run.

## Decisions

- `observe(ref=...)` runs the tests on the files of a commit: the experiment runner's commit copy (`git cat-file`,
  the user's tree and index untouched), the same isolation and policy as any run. A run of a commit is filed
  under no snapshot and does not update the test map (it describes the working tree's tests); its edge flags and
  the flaws' loop search read that commit's files (`_Sources(commit=)`), and its header names `ref` and the traced
  files that differ from the working tree. Graph nodes are still the working tree's graph.
- New module `runtime/rundiff.py`. `observe_pair` runs the head (or takes a head run already made), then the same
  test ids at the base, leaving out ids whose file does not exist there (`tests_new_in_head`); `compare` reads
  the two stored runs. Keys leave lines out, so a function that moved inside its file is not a change:
  - calls: (caller file, caller qualified name, callee file, callee qualified name), calls into test code left
    out;
  - library calls: (project caller, the library callable's name), callers in test code left out;
  - SQL: the normalised statement (D147), its executions summed; a statement in both runs is "changed" when its
    larger count is at least 1.5 times the smaller and they differ by at least 3; the N+1 groups of each run are compared by statement;
  - routes: the current code's route table (`verinoda routes`, D146) mapped to the handlers each run reached;
  - exceptions: (file, qualified name, exception type) of raises in project code;
  - test outcomes: the phase outcome and the exception that ended a failed phase.
- The call tracer records raises: a `RAISE` callback (`sys.monitoring`; it cannot be disabled per code object, so
  every raise reaches it - once in each frame the exception passes through - and only the project frame where it
  starts is kept: the one whose traceback has no further entry), at most 5,000 distinct (site, type), written as
  `raise` records and kept in the run's header (2,000 project sites, test code left out, most hit first). A `pytest_runtest_makereport` wrapper records the
  type of a failed phase's exception and the innermost project frame it passed through. The setprofile tracer
  (Python < 3.12) records no raises: the comparison says so instead of reporting none.
- Statuses: an item is `observed` - present in one run, absent from the other run of the same tests - only when
  the run it is absent from is complete; otherwise `unknown` (that run may have made it). An item made only by
  tests the other run did not have is marked `new_tests_only`. Nothing says what always happens; a flaky test can
  make a difference, which the limits say.
- Review round: a selected test new in a file the base already had made the base run collect nothing (pytest exit
  4) and every head item `unknown`; a test id is now checked at the base by its class and function names (a
  parametrize suffix is not), and a comparison where no test ran in both runs is an error. The RAISE callback named
  every frame an exception passed through as raising it; only the frame where it starts is kept now. A test that
  failed the same way in both runs was a change when the exception's line moved: outcomes compare type, file and
  function. N+1 groups that appeared or went count in `changed`. `observe --compare` ran the base with the default
  tracer mode and thresholds: both runs now take the same. The base run, filed after the head, became "the latest
  run" that a later `review` reads as the working tree's: runs of another commit are left out of that query
  (`trace.latest_run`, review's observed tests). A raise list cut at its cap (or with sites dropped by the
  plugin) makes the exceptions missing from that run `unknown`. Minor: SQL items sort by executions, the raise
  line is cached per (code, offset), `observe --compare` exits 3 when the comparison failed, the test line shows
  both sides' exceptions, `review` catches any failure of the comparison.
- `review --observe` traces with the flaws recorder and, when the review has a base commit (not a planned change),
  adds `tests.observe.runtime_diff`; the text lists it under the observe line. `observe --compare REF` does the
  same from the command line. A ref that names no commit, a base run that fails, or a run that was not recorded
  is an `error` in the block, never a crash of `review`. No MCP change: the tool count stays 40.

## Measured

Windows 11, Python 3.13.

- The end-to-end fixture (a sqlite project, 3 tests, the head with an N+1 replaced by one query, a new call and
  library call, a changed exception type): both runs and the comparison in about 6-7 s (the module fixture of
  `tests/test_runtime_diff.py`; the whole file, 14 tests with a `review --observe`, 25-29 s).
- The raise hook, the same project and plugin otherwise: a test raising and catching `ValueError` in project
  code 200,000 times took 0.80 s with the previous tracer and 1.32 s with this one (median of 5), about 2.6 us per
  raise; a test with no raise took 0.020 s with both. Raises in library code reach the callback too and are
  dropped after one dictionary lookup (not measured separately).

## Limits

- One run of each side: a flaky test or nondeterministic code makes differences that the change did not cause.
- Calls are matched by file and qualified name: a function that moved to another file or was renamed shows as
  removed and added. Lambdas and comprehensions are matched by their `<lambda>`/`<genexpr>` names.
- Graph nodes and routes come from the current code: a route only the base served is not named.
- Raises are recorded with `sys.monitoring` only (Python 3.12+); child processes are not traced, as before.
- `review --observe` now runs the selected tests twice (base and head) and with the SQL recorder: about twice the
  time it took.
- Library calls are recorded once per call site (D28): a library call made from a new site in a function that
  already made it elsewhere is a change of site, not counted twice.

## Upgrading note

`verinoda observe` gains `--compare REF`: the same tests are also run at commit REF and the result gains
`runtime_diff` (calls, library calls, SQL, routes, exceptions raised, test outcomes added, removed or changed).
`review --observe` runs the selected tests at the review's base too (runs of another commit are never taken as the
latest run) and adds `tests.observe.runtime_diff`; it also
records SQL now (the flaws recorder), so it takes about twice as long. Runs gain `raise` records (Python 3.12+) and
per-test `exc`; `runtime.trace.observe()` takes `ref=`. Nothing to migrate; the MCP tools are unchanged.
