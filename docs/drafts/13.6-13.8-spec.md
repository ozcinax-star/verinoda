## 1. Question types, engines, answer shapes and status ceilings

Common rules for all types:
- **Names:** resolved with `naming.resolve` (verinoda/naming.py:448), accepting only `EXACT` results. Overloads count as one name and the answer covers all of them. A scored (fuzzy) match is never used.
  - Ambiguous name: `unknown`, plus up to 3 candidates.
  - Not found: `unknown`, plus next step `pass path/file.py::symbol`.
  - `not_indexed`: `unknown`, plus next step `index_update`.
- **Status:** the answer's status is the lower of the engine's own status and the type's ceiling. Order: `claims.ORDER` (verinoda/claims.py:74). tq never raises a status.
- **One engine per type.** `retrieval.trace` is not mixed in.

| type (line form) | engine (file:line) | answer | highest status |
|---|---|---|---|
| `exists NAME` | naming.resolve :448. Definition line re-read with `entail.def_around` (entail.py:1436). For a library name: `codecheck.api` (codecheck.py:4153); its `found`/`decided` are used as given. | `yes`/`no`/`?` + definition `file:line`, or candidates | yes: `statically_verified` (definition line re-read, file not stale), otherwise `strong_inference`. no: `strong_inference` at most (an index absence, or `found:false` for a closed container). Library `decided: unknown`/`not_installed` → `?` with next `pass env` / install. |
| `which NAME in A\|B\|C` | `naming.exact_nodes(g, name, fallback=False)` (naming.py:290), files compared with the options; `def_around` re-read | the options that hold (none, one or several) + `file:line` each; `other:` up to 3 definitions outside the options | each option: `statically_verified`. "none": `strong_inference`. |
| `calls A B [depth=1..10]` (default 1) | `graphquery.run` (graphquery.py:1135) with a Query **object** (see build step 1). With verify: `_verify_row` (:1296) → `entail.call_site` (entail.py:1293). | `callers F` | graphquery.run `(c)-[calls\|indirect_call]->(x) return count(c)` | `>=N` (always `bound: at_least`) + up to 3 call sites | `strong_inference` at most (q never re-reads counts, D155); `weak_inference` if any counted edge is INFERRED. |
| `taint S K [in=path,...]` | `taint.run` (taint.py:816), once per distinct scope in a batch; findings filtered by source/sink name or kind | yes/no/? + source line > sink line, number of steps, rule `taint/<kind>` | yes: `strong_inference` (taint's own maximum). `none_found` (:862) → no at `weak_inference`, with the taint scope and depth and taint.LIMITS (:68). A QueryError becomes `invalid` for that question only. |

Left out on purpose:
- `claim_holds`: `workflow.verify` writes claim statuses, and tq is read-only. Use `claim_inspect`.
- `depends_on` (a slice question): scope. It is reachable later through the `q` type or its own item.
- `precise.resolve_call`: offered as a `next` step, never as a new way to raise a status.

**The object form** of a question is `{id?, type, ...fields}`. **The line form** is `type operand... key=value`, with `"..."` for operands that contain spaces. The parser is hand-written in the style of graphquery's tokenizer (graphquery.py:122), with no eval. Ids default to q1..qn.

## 2. CLI and MCP surface; menu impact (measured)

**Name.** The name is `tq` (typed questions), not `ask`: `verinoda decide ask` (cli.py:4943) and `dependency_ask` already exist. `facts` is also taken (verinoda/facts.py, named derived facts).

**CLI:** `verinoda tq "calls create_order_handler place_order" "callers place_order" ...`, or `-f FILE` (one question per line, or JSONL objects, or `-` for stdin). Registered next to `q` (cli.py:5300, `cmd_q` :3602).
- Flags: `--verify` (default on; `--no-verify` exists), `--need inference|verified`, `--json`, `--timeout S` (default 30 for the batch), `--max-expansions`.
- Exit codes:
  - 0: every answer is decided.
  - 1: some answer is unknown, or one question is invalid.
  - 2: the batch itself is invalid (no questions, more than 20, unreadable JSON).
  - 3: a budget cut the batch.

**MCP:**
- New method `AtlasTools.tq(questions: list[str|dict], verify=True, need="inference", format="text")`, wrapped in `self._run(..., need="graph")` like `node_inspect` (server.py:917). Registered with `@register("tq")`.
- Added to `TOOL_NAMES` (40 → 41; README and docs updated) and to `CORE_TOOLS` (14 → 15; test_mcp.py:337 updated).
- Not added to `CORE_DIRECT`, so the core menu still lists 5 tools. In the core profile it is reached through `run_tool` and its `validate_call`. The full profile lists it directly.
- On a bad question, the tool returns that row as `invalid` together with the type grammar (at most 600 characters), as q's errors already do (D61).

**Menu arithmetic.** Measured now on an orders_app copy at 229b11a:
- core menu: **4,449** characters (limit < 4,500, test_mcp.py:354)
- decision-records menu: **4,598** (limit < 4,600, test_mcp.py:370). This is the limit that binds: only 1 character is free.
- core instructions: **1,303** (limit < 1,400)

To make room, I computed these changes against the current strings with the repo's own `gateway_description`:
- New `GATEWAY_CATALOG` entry (84 chars as JSON): `tq {questions}: typed questions (calls, reaches, callers, which...), many per call`

- Shorter `history_search` entry (166 → 100): `history_search {text|symbol|message|base, ...}: when text came/went, its commits, commits, compare`. Its arguments still come back in the run_tool `invalid_arguments` hint, which lists every parameter.

## 3. Output format (samples are from real `verinoda q` rows on orders_app)

**MCP text** (the default, like project_query's plain text, D60):
- one header line
- one line per answer, without echoing the question
- `format="json"` for programs

**CLI text** echoes each question after its id.

```
tq 5 questions, index fresh, 0.21 s. no = absent from the static graph; >=N = lower bound
q1 calls create_order_handler place_order = yes | statically_verified | orders/api.py:18
q2 reaches create_order_handler OrderRepository.save = yes | weak_inference | orders/api.py:18>orders/service.py:22 | why: INFERRED edge orders/service.py:22 | enough: no | next: verinoda resolve-call orders/service.py:22 save
q3 callers place_order = >=3 | strong_inference | orders/api.py:18, tests/test_service.py:9, tests/test_service.py:15
q4 writes OrderRepository.save orders = yes | weak_inference | orders/repository.py:17 | why: INFERRED writes_table edge | enough: no
q5 tested tests/test_service.py::test_place_and_fetch_roundtrip place_order = ? | unknown | why: test never traced | next: verinoda observe -k test_place_and_fetch_roundtrip
```

Rows q1–q4 come from real `verinoda q --verify` runs on the scratch copy:
- q1: `statically_verified`, confirmed at api.py:18.
- q2: `weak_inference`; the hop at service.py:22 is INFERRED.
- q3: `count(c) = 3` at `strong_inference`.
- q4: `.save -writes_table?-> orders` at repository.py:17, `weak_inference`.

q5 is the expected unknown on a store with no traced run.

**JSON** (`verinoda.tq/1`), with empty fields left out:

```
{"schema":"verinoda.tq/1","answers":[{"id":"q1","answer":true,"status":"statically_verified","at":["orders/api.py:18"]},{"id":"q2","answer":true,"status":"weak_inference","at":["orders/api.py:18","orders/service.py:22"],"why":"INFERRED edge orders/service.py:22","enough":false,"next":"verinoda resolve-call orders/service.py:22 save"},{"id":"q3","answer":3,"bound":"at_least","status":"strong_inference","at":["orders/api.py:18","tests/test_service.py:9","tests/test_service.py:15"]},{"id":"q4","answer":true,"status":"weak_inference","at":["orders/repository.py:17"],"why":"INFERRED writes_table edge","enough":false},{"id":"q5","answer":null,"status":"unknown","why":"test never traced","next":"verinoda observe -k test_place_and_fetch_roundtrip"}],"complete":true,"stale_files":0,"seconds":0.21}
```

## 4. Evidence and unknown rules

1. tq adds no status of its own. Every status comes from an engine and is combined only with min() over `claims.ORDER`. A graph edge alone is never above `strong_inference` (EXTRACTED) or `weak_inference` (INFERRED). `statically_verified` requires the q `--verify` re-read.
2. A "no" is an absence. It is never verified and always carries `why` (what is unseen) and `next` (the experiment that could show the opposite).
   - `strong_inference` only in two cases: a depth-1 `calls` (Python, no AST call, name absent from the text), and an index absence for `exists`/`which`.
   - `tested` no: `strong_inference` and run-scoped.
   - Everything else: `weak_inference`.
3. Counts are always `>=N` and at most `strong_inference`.
4. Freshness: `freshness.check` runs once per batch. An answer that cites a stale file becomes `?` with next `index_update`. The batch reports `stale_files`.
5. Unknown always has `why` and `next`. The reasons:
   - unresolved name → `pass path/file.py::symbol`
   - ambiguous name → candidates; tq never picks one
   - not_indexed or stale → `index_update`
   - budget → `ask again: q7,q9`; a budget cut is never "no"
   - not_installed → `pass env`
   - no route match → the existing routes
   - never traced → `verinoda observe -k T`
   - non-Python call site → the answer stays `strong_inference`, with next `verinoda resolve-call`
6. One failing question never fails the batch. It becomes `invalid` or `?` with its own reason.
7. `need` (`inference` by default, or `verified`, per call or per question) sets `enough:false` on any answer below the bar. `inference` means `strong_inference` or better. This is the instructions' rule "never state weak_inference or unknown as fact", turned into a field.
8. Answers are not stored as claims (q stores none either). To keep one, the agent passes it to analyze or the claim tools.
9. Determinism: no model, no network, no randomness; questions run in a fixed order with no threads.
   - The expansion budget is deterministic. The wall-clock budget is only a safety net: when it cuts, the answer is `?`, never a different value.
   - Output is byte-identical across runs except `seconds`.
10. CONFIDENCE_CAP numbers (claims.py:78) are never printed on tq answers.

## 5. Calibration against the benchmark gold sets

**Gold set.** Built and frozen before any tq code: `benchmarks/tq_gold/{dev,held_out}.json` plus `MANIFEST.json` with sha256 (the review_fixtures protocol). The builder `benchmarks/tq_gold/build.py` draws from:
- the negative relation triples already in `verinoda/benchmark/questions/*.json` (the judges counted roughly 41–53 distinct)
- facts with `at` locators in the callers/flow/where categories, each conversion checked by hand
- verdict_audit `met_is_wrong` traps (`benchmarks/verdict_audit/cases.json`), with gold `?` or no
- mutation pairs on copies of orders_app, forge_mod and glow_mod. Each mutation flips the gold answer: add or delete a call, rename a definition, add getattr dispatch, add or remove a SQL write, move a route.
- the D155 q fixture (self-recursion, a mutual pair that is not an edge, a 3-cycle)
- the D154 taint fixtures and the D158 schema fixtures
- a test-map fixture with four traced tests: one passed, one that failed early, one sharing a fixture, one with an incomplete trace
- this repository at a pinned commit (its read-only index)

Targets: at least 450 dev and at least 300 held-out cases, with **at least 30 held-out cases per type**. Mutation pairs make that reachable.

**Runner.** `verinoda benchmark tq-audit --split dev|held_out`, next to verdict_audit (verinoda/benchmark/verdict_audit.py). It scores `at` with `metrics.parse_locator` (:110) and `extract_locators` (:120). It writes:
- `benchmarks/results/tq-<date>/report.json`
- `verinoda/data/tq_calibration.json`: `{gold_sha, commit, engine_sha:{graphquery.py, tq.py, taint.py, testmap.py, dataschema.py, entail.py, naming.py}, cells:[{type, status, polarity, n, correct, wilson_lo, wilson_hi}]}`, held-out only.

**Display.** `measured: k/n held-out @gold` appears only when all three hold:
- the cell has n ≥ 30;
- dev precision lies inside the held-out Wilson interval;
- the `engine_sha` values equal the installed sources, checked at runtime, so a stale table is never shown. A unit test with a doctored hash covers this.

The number is always a frequency, never a probability.

**CONFIDENCE_CAP report.** The report puts the observed precision per status next to CONFIDENCE_CAP (DESIGN line 50: the caps were never recalibrated). It recommends changes only; there is **no automatic change in either direction**. Changing a cap is its own reviewed decision, because it affects analyze and every stored claim.

## 6. Optional host-filled intent on analyze

- **On tq (ships with 13.6):** `need` is the intent gate. It costs nothing in the menu.
- **On analyze (item 13.8):** an optional `intent` argument, in the full profile and `verinoda analyze --intent` only. The core analyze stays `{question, budget_seconds}`, as test_mcp.py:349 requires.
  - Allowed values: the keys of `question_plan.DEFAULT_DONE` (question_plan.py:97).
  - The value is compared with `intents_for` (:603) through `question_plan.check(..., source="host")` (:2252).
  - If they agree, the intent orders the sub-questions and picks done_when.
  - If they disagree, the result carries `intent_check {given, read_as, agrees:false}` (the same shape as `intent_divergence`, :2287), and Verinoda's own reading is used.
  - A choice question (`asks_for_choice`, :463) stays the user's.
  - The intent never changes a status.
  - It is promoted to core only if verdict_audit `wrong_met` or the number of turns drops by more than its schema characters cost.

## 7. Measuring before shipping (sets, metrics, pass bars)

**A. Correctness** (tq_gold held-out, verify on and off):
- Hard gate: **0 wrong answers at `statically_verified` or `observed`**, on dev and held-out.
- Precision at `strong_inference` ≥ 0.70 for every type with n ≥ 30. A cell below that is a rule bug and blocks shipping.
- 0 dynamic-dispatch trap cases answered "no" above `weak_inference`, except the documented depth-1 `calls` rule; trap misses are reported per case.
- `next` present on 100% of unknowns.
- Locator hit ≥ 95% (the gold line is in `at` for true answers).
- Unknown rate ≤ 25% on non-trap cases (over-refusal).
- 0 budget cuts reported as "no".

**B. Offline size:** about 40 facts from `questions/*.json`, written in typed form. tq output is compared with project_query, analyze, relation_trace and `q --verify` on the same facts, in characters / 4 (benchmarks/token_multiplier.py), and reported as facts per 1k tokens. Bar: the median tq answer is ≤ 1/5 of the cheapest existing tool's answer.

**C. Determinism:** the same batch run twice gives byte-identical JSON apart from `seconds` (a test).

**D. Menu:** test_mcp.py:354 < 4,500 and :370 < 4,600 still pass. The before and after numbers go into section 132 (computed target: 4,441 / 4,590).

**E. Latency and sharing:**
- A warm 20-question batch on this repo's index takes < 10 s, measured 3 runs as in D155.
- A 10-question batch on orders_app takes < 1 s.
- A test counts `freshness.check` and `cross_service.collect` calls: once per batch each.

**F. Agent study** (pre-registered, D62 style, on the frozen build). It decides only the instructions sentence (`Several yes/no or count facts: run_tool tq.`, about 44 characters, which fits within 1,400).
- Design: ≥ 24 paired tasks over 4 repositories, each needing 4–10 closed facts, one model in the loop.
- Measured:
  - total input tokens over all turns, raw and cache-weighted, reported separately
  - number of turns
  - share of tq calls with ≥ 2 questions
  - fact recall (the fastbench facts scorer)
  - count of weak or unknown answers stated as fact
- The sentence goes in only if all of these hold:
  - fact recall equal or higher (≤ 1 fact lost per set)
  - median paired cache-weighted cost down ≥ 10%, bootstrap 95% CI excluding 0
  - turns do not rise
  - over-trust count does not rise

## 9. Risks and out of scope

**Risks**
- **Menu headroom.** After this change the records menu has 9 characters to spare. Any future gateway entry has to pay for itself the same way.
- **A typed "no" read as fact.** Mitigated by the absence ceilings, `why`, `enough:false` and `next` on every no. The study counts over-trust directly.
- **Calibration from the same author.** The person who writes the rules also writes the gold labels. Mitigated by freezing the held-out split by hash before any code, mutation pairs, n ≥ 30, a frequency rather than a probability, and the runtime engine-hash check.
- **Name resolution is the most common failure.** It comes back as unknown with candidates, and fixing it costs a turn.
- **Python bias.** `statically_verified` call sites exist only for Python. JVM answers stay at `strong_inference`; forge_mod and glow_mod measure them.
- **Latency on large graphs** (D155 measured 0.8–2.1 s per deep query on 37k nodes). Mitigated by per-question shares and budget unknowns; the shared ctx removes the per-question freshness walks and route collection.
- **Scope creep toward a second query language.** New shapes go through the `q` type. A new named type needs gold-set evidence that it is common.
- **Adoption.** Agents may not batch, or may not call tq at all. Study F measures the share of calls with ≥ 2 questions. Without the sentence, tq's cost is −8 menu characters, so it costs nothing to ship.

**Out of scope**
- Any network call, hosted model, embedding or LLM.
- Generated text.
- Per-answer probabilities (`p=`).
- Automatic CONFIDENCE_CAP changes.
- Storing answers as claims.
- `claim_holds` (it writes) and `depends_on`.
- Chained questions (a question that uses another's answer; that is a program, and q covers it).
- An intent field on the core analyze.
- Adding tq to the listed core menu.
