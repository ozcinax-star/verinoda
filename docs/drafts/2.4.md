## Why

`verinoda check` reads names: Python (jedi, D32), Java and Kotlin (D43, D45), and for TypeScript and JavaScript
only the imports (D46). The mistake an agent makes most often in TypeScript after an invented import is a member
that is not there (`svc.sendd()`), a call with the wrong number or type of arguments, or a value of the wrong
type - and those need the compiler, so such a file stayed under `not_checked` and the exit was 4. Every
TypeScript project already has the compiler, and many Python projects have pyright or mypy configured;
narsil-mcp and common practice run that checker. Done when: `check` on TypeScript reports members and calls, not
only imports.

## Decisions

- **Opt-in, CLI only: `verinoda check ... --checker tsc|pyright|mypy|auto [--checker-timeout SECONDS]`**
  (module `verinoda/codecheck_external.py`, called from `codecheck.check(checker=..., checker_timeout=...)`).
  It starts a program of the project (the checker, and through it the plugins its configuration names), so the
  MCP server never calls it: `code_check` keeps its arguments and its rule that nothing the checked repository
  supplies is started. No config key either: a `.verinoda/config.json` that arrives with a repository must not
  turn on running its programs. No MCP tool or argument changes (40 tools; the core menu is unchanged).
- **The project's own checker, never installed or downloaded.** tsc: `node_modules/.bin/tsc` from the
  `tsconfig.json` folder up to the repository, else `tsc` on PATH. pyright: `node_modules/.bin/pyright`, the
  project's virtual environment (`--env`, `.venv`, `venv`, `env`), else PATH. mypy: the virtual environment, else
  PATH. PATH is searched in its absolute folders only, never the current directory. No `npx` (it installs on a
  miss) and no `pip`. pyright's PyPI wrapper (a launcher whose script imports `pyright.cli`, read from its bytes or
  its appended zip) is refused with the reason: on first use it downloads Node.js and pyright's npm package, and
  it looks for a newer version on each start.
- **The project's configuration.** tsc runs as `tsc -p tsconfig.json --noEmit --pretty false --listFiles` in the
  folder of each target file's nearest `tsconfig.json` (at most 4 per check; a file with none above it in the
  repository is not compiled - tsc without the project's options would judge other code - and said so). The
  whole program is compiled; `--listFiles` says which files were in it. pyright (`--outputjson`) and mypy run from
  the repository root on the Python files being checked (the top folders instead when the command line would pass
  24,000 characters), so each reads its own configuration as it would there. `auto`: tsc for TypeScript and
  JavaScript; for Python the checker the project configures (`pyrightconfig.json` or `[tool.pyright]`;
  `mypy.ini`, `.mypy.ini`, `[tool.mypy]`, a `setup.cfg` `[mypy]` section), else the installed one, pyright first.
  The configuration used is named in each site and in the run's header.
- **Machine-readable output.** tsc's `file(line,col): error TSnnnn: message` lines with their indented
  continuation lines, its global `error TSnnnn:` lines and the `--listFiles` paths; pyright's JSON report
  (0-based lines and characters); mypy's `-O json` lines from 1.11 (decided from `mypy --version`), else the text
  form with `--show-column-numbers --show-error-codes --no-error-summary --no-pretty --no-color-output`. A mypy
  note is added to the error before it. A line that is none of these is counted (`unparsed_lines`), never read as a
  diagnostic, and makes the check incomplete (exit 4 when nothing is absent): a diagnostic may be among them.
  tsc's stderr (Node's own warnings) is shown only when the run fails.
- **Sites.** Each error of the run on a file being checked, and with `--diff` on a changed line, becomes a site
  with `status` `observed`, `source` `checker` and `checker` {tool, version, config, code}; the message ends with
  the citation (`TS2339: Property 'sendd' does not exist on type 'Service'. (tsc 5.4.5, tsconfig.json)`). Kinds:
  `name`, `member`, `import`, `call`, `type`, by diagnostic code (tsc TS codes, mypy error codes, pyright rules)
  and by message when there is no code. Verdicts: a name, member or import the checker did not find is `absent`
  (an import of a module that is not relative: `not_installed`; a module without stubs: `unknown`); a call or type
  that does not fit is the new verdict `mismatch`. Both make the exit 3 (`status` `absent` or `mismatch`). Only
  errors become sites; warnings and the errors outside the scope are counted in the run's header. At most 1,000
  sites per run, the rest counted.
- **One site per finding.** A checker error on the line of an `absent` site of the same name (Verinoda's own
  closed-world answer) is not listed again: that site gets `confirmed_by` (`mypy 1.11.2 attr-defined`).
- **What the compiler read is checked.** A TypeScript file in tsc's program leaves `not_checked` (it was imports
  only); a JavaScript file only when its tsconfig sets `checkJs` or the file starts with `// @ts-check` (an
  `extends` chain is not followed). A file not in the program stays imports only, with a note.
- **Never a silent pass.** A checker that is not found, could not be started, ran past the timeout (300 s by
  default; the process tree is stopped: `taskkill /T` on Windows, the process group elsewhere), exited with a code
  it does not use for findings, or printed output that is not its report is a run with `status` `not_found`,
  `timeout` or `failed`, a note and a `next_step`, and the exit is 4 when nothing is absent. A tsc global error
  with no program (`TS18003 No inputs were found`) is a failure; with a program it is noted. A snippet (`--stdin`)
  is not on disk, so it is not given to a checker (exit 4, said).
- **Bounded.** Output goes to temporary files (a process the checker leaves behind cannot hold a pipe open) and
  16 MB of each are read; a cut makes the check incomplete. Arguments of a `.cmd`/`.bat` launcher holding a character cmd.exe
  interprets (`" & | < > ^ % !`) are not passed: the run is `not_run` with the reason.
- **Not cached.** A checker's answer depends on every file of its program and on its configuration; hashing
  those would cost about what the run does.
- **SARIF.** `check/mismatch/<kind>` and `check/absent/<kind>` results from a checker carry the status
  `observed` (an error); the rest of `check --sarif` is unchanged.

## Measured

No real tsc, pyright or mypy is installed on the machine this was built on, and nothing was installed for it,
so nothing was measured against a real checker. With the fake checkers of the tests (Windows, Python 3.13): a
`check --checker tsc` of two TypeScript files 0.9 s end to end (the fake answers at once; the time is the check
and starting the launcher twice, `--version` and the run); a checker told to sleep 60 s with `--checker-timeout 1.5` stopped, and the check
returned, in 2.1 s; the 19 tests of `tests/test_type_checkers.py` 20.5 s.

## Limits

- CLI only: MCP `code_check` never runs a checker.
- The checker is trusted as configured: it, and the plugins its configuration names (mypy plugins, TypeScript
  language service plugins are not loaded by tsc), run with the user's rights.
- tsc compiles the whole program of each tsconfig, also for a `--diff` of one line; a solution-style tsconfig
  (`files: []` with `references`) holds no file, so its files stay imports only (`tsc -b` is not run). At most 4
  tsconfig files per check.
- tsc may write a `.tsbuildinfo` when the tsconfig asks for incremental builds; mypy writes its usual cache.
- pyright's PyPI wrapper is not started; basedpyright and other checkers are not run.
- pyright and mypy are given the files being checked: a configuration that lists other files or excludes these
  is overridden as each tool does for files on its command line.
- Classification of a diagnostic into name, member, call, import or type is a table of codes and message
  patterns; an unknown code is `type` (verdict `mismatch`). The name is read from the message's quotes and can be
  empty.
- The parsers are tested against output written in the tools' documented formats (tsc 5.x `--pretty false`,
  pyright's `--outputjson`, mypy's text form and its 1.11 `-O json`), not against output captured from real runs:
  no checker was available here. A release that changes its format is a `failed` run or unparsed lines, never a
  pass.

## Upgrading note

`verinoda check` gains `--checker tsc|pyright|mypy|auto` and `--checker-timeout SECONDS`: the project's own type
checker is run (never installed or downloaded) and its errors on the lines in scope are sites with `status`
`observed` and a `checker` field {tool, version, config, code}; a TypeScript file it compiled is no longer listed
under `not_checked`. A new verdict `mismatch` (a call or type that does not fit; exit 3) appears in `summary` of
every `check` result (0 without `--checker`), and the result gains `checker` (one entry per run) when the option
is given. A checker not found, timed out or failing is exit 4 with the next step. Without the option `check` is
unchanged. No MCP tool changes; MCP `code_check` never runs a checker.
