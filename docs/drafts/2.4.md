## Why

`verinoda check` reads names: Python (jedi, D32), Java and Kotlin (D43, D45), and for TypeScript and JavaScript
only the imports (D46). The mistake an agent makes most often in TypeScript after an invented import is a member
that is not there (`svc.sendd()`), a call with the wrong number or type of arguments, or a value of the wrong
type - and those need the compiler, so such a file stayed under `not_checked` and the exit was 4. Every
TypeScript project already has the compiler, and many Python projects have pyright or mypy configured;
narsil-mcp and common practice run that checker. Done when: `check` on TypeScript reports members and calls, not
only imports.

## Decisions

- **Opt-in, CLI only: `verinoda check ... --checker tsc|pyright|mypy|auto [--checker-timeout SECONDS]`**
  (module `verinoda/codecheck_external.py`, called from `codecheck.check(checker=..., checker_timeout=...)`).
  The timeout is a finite number of seconds above 0 (default 300; anything else is exit 2). The MCP server never
  calls it: `code_check` keeps its arguments and its rule that nothing the checked repository supplies is
  started. No config key either: a `.verinoda/config.json` that arrives with a repository must not turn on
  running programs. No MCP tool or argument changes (40 tools; the core menu is unchanged).
- **Trust is the boundary** (`verinoda.paths.is_trusted`, as for tests and script guards). In a project the user
  has not trusted (`verinoda trust`), nothing the repository supplies is started: a checker found inside it
  (`node_modules/.bin`, a virtual environment in it, a PATH folder in it) is not run, only one on PATH outside
  it; pyright is not run at all (it starts a Python interpreter it looks up itself, which may be the
  repository's); mypy is not run when `mypy.ini`, `.mypy.ini`, `setup.cfg` or `pyproject.toml` sets `plugins` or
  `python_executable` (both run code). Such a run is `not_run` with the step "ask the user: if they trust this
  project's code, they run `verinoda trust PATH` themselves; an agent must never run it for them", and the exit
  is 4. `auto` skips a checker the gate refuses. Every checker runs with `NoDefaultCurrentDirectoryInExePath=1`,
  so a Windows launcher (`tsc.cmd` calling `node`) never picks a program from the project folder it runs in.
- **The project's own checker, never installed or downloaded.** tsc: `node_modules/.bin/tsc` from the
  `tsconfig.json` folder up to the repository, else `tsc` on PATH. pyright: `node_modules/.bin/pyright`, the
  project's virtual environment (`--env`, `.venv`, `venv`, `env`), else PATH. mypy: the virtual environment, else
  PATH. PATH is searched in its absolute folders only, never the current directory. No `npx` (it installs on a
  miss) and no `pip`. pyright's PyPI wrapper (a launcher whose script imports `pyright.cli`, found in its first
  8 MB, its last 2 MB or the zip appended there) is refused with the reason: on first use it downloads Node.js
  and pyright's npm package, and it looks for a newer version on each start.
- **The project's configuration.** tsc runs as `tsc -p tsconfig.json --noEmit --pretty false --listFiles` in the
  folder of each target file's nearest `tsconfig.json` (at most 4 per check; a file with none above it in the
  repository is not compiled - tsc without the project's options would judge other code - and said so). The
  whole program is compiled; `--listFiles` says which files were in it. pyright (`--outputjson`) and mypy run from
  the repository root on the Python files being checked, each passed as `./path` (mypy also after `--`), so a file
  named like an option (`--python-executable=evil.py`) stays a file; the top folders, also as `./folder`, when the
  command line would pass 24,000 characters. `auto`: tsc for TypeScript and JavaScript; for Python the checker the
  project configures (`pyrightconfig.json` or `[tool.pyright]`; `mypy.ini`, `.mypy.ini`, `[tool.mypy]`, a
  `setup.cfg` `[mypy]` section), else the installed one, pyright first. The configuration used is named in each
  site and in the run's header.
- **Machine-readable output.** tsc's `file(line,col): error TSnnnn: message` lines with their indented
  continuation lines, its global `error TSnnnn:` lines and the `--listFiles` paths; pyright's JSON report
  (0-based lines and characters); mypy's `-O json` lines from 1.11 (decided from `mypy --version`), else the text
  form with `--show-column-numbers --show-error-codes --no-error-summary --no-pretty --no-color-output`. A mypy
  note is joined to the error before it on the same line; another note is left out, and a context line
  (`file: note: In function "f":`) is read as such. A line that is none of these is counted (`unparsed_lines`),
  never read as a diagnostic, and makes the check incomplete (exit 4 when nothing is absent): a diagnostic may be
  among them. tsc's stderr (Node's own warnings) is shown only when the run fails.
- **Sites.** Each error of the run on a file being checked, and with `--diff` on a changed line, becomes a site
  with `status` `observed`, `source` `checker` and `checker` {tool, version, config, code}; the message ends with
  the citation (`TS2339: Property 'sendd' does not exist on type 'Service'. (tsc 5.4.5, tsconfig.json)`). Kinds:
  `name`, `member`, `import`, `call`, `type`, by diagnostic code (tsc TS codes, mypy error codes, pyright rules)
  and by message when there is no code. Verdicts: a name, member or import the checker did not find is `absent`;
  a call or type that does not fit is the new verdict `mismatch`; both make the exit 3 (`status` `absent` or
  `mismatch`). An import is judged further: tsc's `TS2307` for a name a tsconfig `paths` pattern maps is `absent`
  when no file it maps to is there and `unknown` when one is; for any other bare name `unknown` when `baseUrl` is
  set (it may be the project's), else `not_installed`; mypy's `import-not-found` and pyright's
  `reportMissingImports` are `absent` when the top package is the project's and the module is not in it,
  `unknown` when the module is in the project (the checker's search path missed it), else `not_installed`; a
  module without types (`TS7016`, `import-untyped`, `reportMissingModuleSource`) is `unknown`. tsc's "Cannot find
  name 'require'. Do you need to install type definitions" (`TS2580`-`TS2593`) is `not_installed`, naming the
  `@types` package. A possibly-`None` receiver (`union-attr`, `reportOptionalMemberAccess`) and an attribute that
  is there but read-only ("Cannot assign to attribute") are `type`, so `mismatch`, never `absent`.
  `not_installed` and `unknown` sites do not make the exit 3, as for Verinoda's own. Only errors become sites;
  warnings and the errors outside the scope are counted in the run's header. At most 1,000 sites per run, the
  rest counted.
- **Syntax errors are no sites.** tsc's `TS1xxx` errors in a target file (anywhere in it) mean the file was not
  type-checked as written: it stays under `not_checked` and the check is incomplete, naming the line and code.
  mypy's exit 2 (a blocking error: a syntax error in any file it reads, a duplicate module) means it stopped
  before type-checking: the run is `failed`, its note quotes the blocking error, exit 4.
- **One site per finding.** A checker error of kind import, name or member on the line of Verinoda's own site
  of the same family (imports with imports, matched by the module spec - `./nope` - or the imported name; names
  and members by name) joins that site: the same verdict confirms it (`confirmed_by`, `tsc 5.4.5 TS2307`); a
  Verinoda `unknown` gives way to the checker's `absent` or `not_installed` (`own_verdict` keeps it); a different
  verdict leaves Verinoda's site with `checker_says` (`import yaml`: Verinoda's `not_installed`, the checker's
  `unknown`). Calls and types are never joined, nor a site Verinoda found to exist: the disagreement is listed.
- **What the compiler read is checked.** A TypeScript file in tsc's program leaves `not_checked` (it was imports
  only), unless it starts with `// @ts-nocheck`; a JavaScript file only with `// @ts-check` or `"checkJs": true`
  in its own tsconfig, read as JSON with comments (a commented-out `// "checkJs": true` is a comment; an
  `extends` chain is not followed). A file not in the program stays imports only, with a note.
- **Never a silent pass.** A checker that is not found, not run (trust, a launcher path), could not be started,
  ran past the timeout (the process tree is stopped: `taskkill /T` on Windows, the process group elsewhere),
  stopped on a blocking error, exited with a code it does not use for findings, or printed output that is not its
  report is a run with `status` `not_found`, `not_run`, `timeout` or `failed`, a note and a `next_step`, and the
  exit is 4 when nothing is absent. A tsc global error with no program (`TS18003 No inputs were found`) is a
  failure; with a program (`TS5083` a missing `extends` base) the run stands and the check is incomplete. A
  snippet (`--stdin`) is not on disk, so it is not given to a checker (exit 4, said).
- **Bounded.** Output goes to temporary files (a process the checker leaves behind cannot hold a pipe open); a
  stream that passes 16 MB stops the run and makes the check incomplete. A `.cmd`/`.bat` launcher is run by
  cmd.exe, which splits a command line at `&` and the like: when its path or an argument holds one of
  `" & | < > ^ % ! ( )` it is not started (`not_run`, with the reason).
- **Not cached.** A checker's answer depends on every file of its program and on its configuration; hashing
  those would cost about what the run does.
- **SARIF.** A checker's `absent` and `mismatch` sites carry the status `observed` (level error); its
  `not_installed` is `strong_inference` (warning) and `unknown` `unknown` (note), as for Verinoda's own.
- **Review round** (one reviewer, ten confirmed defects and five minor ones, all fixed with tests using fake
  checkers): programs of an untrusted repository were started (a `.venv` `mypy.cmd`; mypy `plugins` from the
  repository's `mypy.ini`) - now the trust gate above; repository file names were passed as options - now `./`
  and `--`; mypy's exit 2 counted as a complete run - now `failed`, and syntax errors (tsc `TS1xxx`, mypy
  `syntax`) are their own kind and never a `mismatch`; `checkJs` was found by a pattern that matched comments,
  and `@ts-nocheck` TypeScript files counted as checked - now JSON with comments and `@ts-nocheck` for every
  suffix; imports were listed twice (only `absent` was joined, by a dotted name that never matched `./nope`, kinds
  not compared) - now the joining above; `TS7016`, a `paths` alias, a project module, `union-attr`,
  `reportOptionalMemberAccess`, a read-only attribute and `TS2580` had the wrong verdicts - now as above; the help
  said a checker error makes the exit 3 while `not_installed` did not - the wording now names absent and
  mismatch; SARIF marked a checker's `not_installed` as an error; cmd.exe metacharacters in a launcher's path
  split its command line; `--checker-timeout inf` crashed and `nan` passed. Minor: `mismatch` sorts with `absent`;
  a tsc global error with a program makes the check incomplete; a runaway checker is stopped at 16 MB written,
  not only read; the PyPI wrapper test reads a bounded head and tail; mypy notes join only an error of their line.

## Measured

No real tsc, pyright or mypy is installed on the machine this was built on, and nothing was installed for it,
so nothing was measured against a real checker. With the fake checkers of the tests (Windows, Python 3.13): a
`check --checker tsc` of two TypeScript files 0.9 s end to end (the fake answers at once; the time is the check
and starting the launcher twice, `--version` and the run); a checker told to sleep 60 s with
`--checker-timeout 1.5` stopped, and the check returned, in 2.1 s; the 39 tests of `tests/test_type_checkers.py`
27.3 s.

## Limits

- CLI only: MCP `code_check` never runs a checker.
- In a trusted project the checker runs as configured: it, and the plugins its configuration names (mypy
  plugins; tsc loads no language-service plugins), run with the user's rights. In an untrusted one, pyright never
  runs, mypy only without `plugins`/`python_executable` in the repository's configuration files, and only checkers
  outside the repository; mypy also reads a user-level configuration, which is the user's.
- tsc compiles the whole program of each tsconfig, also for a `--diff` of one line; a solution-style tsconfig
  (`files: []` with `references`) holds no file, so its files stay imports only (`tsc -b` is not run). At most 4
  tsconfig files per check.
- tsc may write a `.tsbuildinfo` when the tsconfig asks for incremental builds; mypy writes its usual cache.
- pyright's PyPI wrapper is not started; basedpyright and other checkers are not run.
- pyright and mypy are given the files being checked: a configuration that lists other files or excludes these
  is overridden as each tool does for files on its command line. pyright is given `./path` rather than `--`
  (whether its CLI takes `--` could not be checked here).
- Classification of a diagnostic into name, member, call, import, type or syntax is a table of codes and message
  patterns; an unknown code is `type` (verdict `mismatch`). The name is read from the message's quotes and can be
  empty. A `paths` alias or `baseUrl` is read from the target's own tsconfig (no `extends`). pyright's syntax
  errors have no rule and are not told apart.
- The parsers are tested against output written in the tools' documented formats (tsc 5.x `--pretty false`,
  pyright's `--outputjson`, mypy's text form and its 1.11 `-O json`), not against output captured from real runs:
  no checker was available here. A release that changes its format is a `failed` run or unparsed lines, never a
  pass.

## Upgrading note

`verinoda check` gains `--checker tsc|pyright|mypy|auto` and `--checker-timeout SECONDS`: the project's own type
checker is run (never installed or downloaded; in a project not trusted with `verinoda trust`, only a checker
outside the repository, never pyright, and mypy only without `plugins`/`python_executable`) and its errors on the
lines in scope are sites with `status` `observed` and a `checker` field {tool, version, config, code}; a
TypeScript file it compiled is no longer listed under `not_checked`. A new verdict `mismatch` (a call or type that
does not fit; exit 3) appears in `summary` of every `check` result (0 without `--checker`) and sorts with
`absent`; the result gains `checker` (one entry per run) when the option is given, and a site Verinoda and the
checker both report may carry `confirmed_by`, `checker_says` or `own_verdict`. A checker not found, not run,
timed out or failing is exit 4 with the next step. Without the option `check` is unchanged. No MCP tool changes;
MCP `code_check` never runs a checker.
