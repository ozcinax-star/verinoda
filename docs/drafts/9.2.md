# Persistent test-to-code map and affected tests

## Why

The review already listed tests that statically reach a change and, from the tracer's single latest run, the
tests observed reaching it. Nothing remembered across runs which code each test runs, so "run only these tests"
needed a fresh traced run of the whole suite or fell back on static reach, which over-selects (orders_app: the
graph says `test_empty_order_rejected` reaches `apply_discount`; it never does). pytest-testmon and Datadog Test
Impact Analysis keep a per-test map updated on every run and select from it. This decision keeps that map
locally, from the traces Verinoda already makes, and has `review` print the command that runs the affected tests.

## Decisions

- **Where the map comes from.** Every traced pytest run updates it right after the trace is ingested:
  `runtime.trace.observe` (so `verinoda observe`, `analyze --observe`, `review --observe`, MCP `runtime_observe`)
  and the debug ledger's traced attempts (`debug.py` `_trace_summary`). No new command, flag or MCP tool.
- **What is stored** (`verinoda/testmap.py`, schema v8 in `store.py`): `test_map_tests` - per test whose call
  phase ran: the run, its commit, whether the trace was complete, the outcome, the number of functions;
  `test_map` - per (test, file, function) it ran in any phase (setup, call, teardown), the file's content id
  (`treestate.content_id`, from `experiments.run(file_ids=...)`, i.e. the copy that actually ran) as its
  fingerprint. Functions are named as the review names them (`outer.<locals>.inner` -> `outer.inner`); module
  bodies and library code are left out.
- **Update rule.** A complete trace replaces a test's rows (what it runs now); an incomplete one (a budget stopped
  it) only adds rows, since a function it did not record may still have run. Both tables are a derived cache of
  the append-only `runtime_calls` (no delete/update triggers), like `file_stat`.
- **Selection in `review`** (`tests.affected`): `observed` - tests the map shows running a changed function
  (`body`, `signature`, `removed` Python definitions; a method counts for its changed class; the parameter sets
  of one test are one entry); `changed` - test functions the change edits; `static` - the existing static reach,
  as the fallback for tests the map has no current, complete record of. A static candidate is left out only when
  its every mapping is complete and **current** (each recorded file now has its base or working content) and ran
  none of the changed functions; those are listed (`not_reached_when_observed`) and counted. Observed hits whose
  files changed since are kept and say so (`current: false`). Each entry is `strong_inference` with the test's
  `path:line` (`at`); the list is a heuristic, never "these are the only tests that matter".
- **The command.** `tests.affected.command` is one `python -m pytest -q <ids>` line (parameters dropped: the base
  id runs every set; an id that reads as an option and non-Python tests are left out); past 40 ids it names the
  test files (`by: file`, runs more than listed). The text output prints `run them: ...` under Tests.
- **MCP.** `change_review` drops `tests.affected` and adds one compact top-level key, `affected_tests`
  (`n`, `observed`, `changed`, `static`, `command`, `by`), the command at most 600 characters (by file when the
  ids do not fit, cut with `truncated` past that). It is in the `keep` list, so the cap cuts other lists first.
  No MCP argument changed; the core menu is unchanged.
- Changed tests whose definitions the snapshot does not hold and non-Python changes keep their existing static
  handling; module-level statements, config and data files are matched by static reach only.

## Measured

- End to end (`tests/test_testmap.py`): a copy of `examples/orders_app`, `observe` of the whole suite maps 5
  tests; `apply_discount` changed: the review lists exactly the four gold tests as observed (current, with
  `path:line`), leaves out `test_empty_order_rejected` (static reach) as `not_reached_when_observed`, and prints
  `python -m pytest -q tests/test_pricing.py::test_compute_total ... tests/test_service.py::test_place_and_fetch_roundtrip`;
  MCP `affected_tests` carries the same command. The whole test takes about 13 s on this machine under load.
- Synthetic store (scratch script): 2,000 tests x ~71 functions each (142,858 map rows) recorded from one run in
  1.4 s; `affected` for two changed functions with 200 static candidates: 0.14 s (571 observed tests).
- Not measured: selection precision on a real project's history (how often a left-out test would have failed).

## Limits

- The map is run-scoped: a test that did not run a function when it was observed may run it after the change
  (a new call path, other data). Leaving such a test out is the heuristic's risk; `current` only checks that the
  files it ran are unchanged, not files it did not run.
- Only pytest runs traced by Verinoda update it; child processes, other runners and untraced `--run-tests` runs
  are not seen. A debug-ledger run on another commit (`bisect`, `differential`) also updates the map; its
  fingerprints then differ from the working tree, so those tests are not trusted to be unaffected.
- A test renamed or removed keeps its old rows until it runs again under that id; nothing prunes them (they
  are only read for changed functions and static candidates).
- `test_empty_order_rejected`-style exclusions need the candidate's complete mapping; an incomplete trace never
  excludes a test.
- The command uses `python`; run it with the project's interpreter.

## Upgrading note

Schema v8: `atlas.db` gains `test_map` and `test_map_tests` (migrated on first open; an older Verinoda refuses
the database as written by a newer one). Every traced run (`observe`, `analyze --observe`, `review --observe`,
the debug ledger's traced attempts) now updates the test-to-code map; `review` lists the affected tests (observed
first, static reach as the fallback, each labelled) and prints one pytest command that runs them (`review --json`:
`tests.affected`); `observe --json` gains `test_map` (tests and functions recorded); MCP `change_review` gains
the compact `affected_tests` key. No MCP tool added; the tool count is unchanged.
