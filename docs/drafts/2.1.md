# 2.1 LSP-backed navigation (opt-in): `verinoda lsp`, `resolve-call --lsp`

## Why

Verinoda's graph call edges outside Python are read from the text: a TypeScript or Java call line that names its
target is `strong_inference` at most, because which definition the name binds to is checked for Python only (jedi,
D29) or from a SCIP index the user supplies. A language server already knows the binding: it is what the editor's
"go to definition" asks. Serena, mcp-language-server, Octocode and JetBrains' IDE server put that behind an agent's
tools. The backlog row: definition, references, hover, diagnostics, call and type hierarchy, implementations from an
installed language server, used for verification rather than extraction; done when a Java or TypeScript call edge
confirmed by the language server is `statically_verified`.

Done here with a fake server written for the tests: a TypeScript edge (`run()` calls `helper()`, `src/app.ts:4`)
and a Java edge (`Main.run()` calls `.helper()` on a local `Util u`, whose method carries an annotation) become
`statically_verified` claims with the server's answer as their verifying evidence; a definition elsewhere makes the
claim `contradicted`.

## Decisions

- **A client of its own, standard library only** (`verinoda/lsp.py`). `Client` starts the server with its stdin
  and stdout as pipes, frames JSON-RPC with `Content-Length` headers, and reads on a thread: answers go to the
  waiting request, `textDocument/publishDiagnostics` is kept per file, and every request the server sends is
  answered (`workspace/configuration` with one `null` per item, `workspace/workspaceFolders` with the project,
  anything else `null`), so a server that waits for its configuration does not stall. `initialize` names the
  project as root URI and workspace folder and asks for UTF-16 positions (the default every server supports);
  columns are converted from and to characters with the file's line. `didOpen` is sent once per file. stderr is
  drained into a 4 KB tail shown when the server fails.
- **Questions:** `textDocument/definition`, `references` (without the declaration), `hover`,
  `prepareCallHierarchy` + `callHierarchy/outgoingCalls` and `incomingCalls`, `implementation`,
  `prepareTypeHierarchy` + `supertypes` and `subtypes`. Each only when the server advertises its provider;
  otherwise the answer is `unknown`, "does not advertise ...". Location and LocationLink are both read (the link's
  `targetSelectionRange` is the name, its `targetRange` the declaration). At most 200 locations per answer, the
  rest counted.
- **Which server.** `lsp.servers` in the config (`{"java": ["/opt/jdtls/bin/jdtls", "-data", "/tmp/ws"]}`), else
  the known default looked up in the absolute folders of PATH (never the current folder):
  `typescript-language-server --stdio` (TypeScript and JavaScript), `jdtls`, `gopls`, `pyright-langserver
  --stdio`, `rust-analyzer`, `clangd`. Nothing found is `unknown`, `not_found`, with the next step naming what to
  install (`npm install -g typescript-language-server typescript`, `rustup component add rust-analyzer`, ...) and
  "Verinoda never installs one". A `.cmd`/`.bat` launcher whose path or arguments hold a character cmd.exe would
  interpret is not started (the type-checker rule, D152). One server per language per command (`Session`),
  started on first use; its workspace root is the project.
- **Trust.** Starting a language server runs third-party code over the project: tsserver loads the plugins
  `tsconfig.json` names, jdtls imports Gradle and Maven builds, rust-analyzer runs build scripts and procedural
  macros, gopls runs `go list`. So the gate is stricter than the type checkers' (D152, which still run a `tsc`
  from PATH in an untrusted project): in a project the user has not trusted (`verinoda trust`), no server is
  started at all, wherever it is installed; the answer is `unknown`, `not_run`, with D152's step ("ask the user
  ... an agent must never run it for them"). `lsp` is a protected setting (`paths.PROTECTED_SETTINGS`): a
  repository's own `.verinoda/config.json` names a server only when the project is trusted; the user config can
  always. The server runs with `NoDefaultCurrentDirectoryInExePath=1` in its own process group.
- **Never a silent pass, nothing left running.** Exit of the server, output that is not LSP (a header line that is
  not `Name: value`, no `Content-Length`, a body that is not a JSON object, a header block over 8 KB or a body over
  64 MB) and a reply missing past the timeout (default 30 s per question, `--timeout`; 60 s for `initialize`)
  each break the client with the reason; the question is `unknown`, the same server is not asked again in that
  command, and `$/cancelRequest` is sent for the request that timed out. Closing sends `shutdown` and `exit` (3 s
  each) unless the client is broken, then stops the process tree whatever happened, also when the server itself
  has already exited: on Windows the server runs in a job object that kills every process in it when it is closed
  (`taskkill /T` when the system refuses a job), elsewhere its own process group gets `SIGKILL`.
- **Resolution in jedi's shape.** `lsp.resolve_call` answers like `precise.resolve_call`: the call tokens of the
  name on the line (followed by `(`, `?.(` or generic arguments, or after `new`; at most 3 per line), a definition
  request for each, then `definitive` (one location in the project), `ambiguous` (several), `external` (outside
  the project or under `node_modules`, a virtual environment, `.gradle`, `target`), `dynamic` (the name is only
  referenced on the line) or `unresolved`. `tool` is the server's `serverInfo` name and version
  (`typescript-language-server 4.3.3`). With a target the verdict: `confirms` when the location is the target's
  file and the node's line, or the node's line opens the declaration whose name the server points at (at most 12
  lines of annotations and decorators, their arguments, comments, attributes, blank lines, modifiers and type
  words in between; never a line that declares or calls something itself or holds the name) or the link's full
  range starts on it; a node without a line is `undetermined`;
  otherwise the definition's implementations are asked first, and when the target is one of them the answer is
  `dynamic`, never a refutation (an interface method, an overridable method: the runtime class decides);
  else `refutes`.
- **Through the claim machinery, not beside it.** `lsp verify [PATH ...]` takes the graph's `calls` edges whose
  call site is in a file a known server serves (under PATH; at most `--max-edges`, default 100), and runs each
  through the analysis loop's own `analysis._edge_claim` with the session on the recorder (`_Recorder.lsp`,
  `None` everywhere else). `_precise` asks the session instead of jedi or SCIP for files it serves; the answer
  becomes `static_resolution` evidence by `precise.resolution_evidence` (the server's name and version in
  `meta.tool` and the locator). A `confirms` is supporting evidence entail grades `full`, and the claim rules
  make the claim `statically_verified`; the "checked for Python only" uncertainty of a non-Python call line is
  dropped once a resolver confirmed the binding (also for SCIP). A `refutes` is a definitive refutation, the claim
  is `contradicted`, and its uncertainty names both: `fake-ls 1.2.3: the call at src/app.ts:5 binds to
  src/alt.ts:1, not src/lib.ts:5`. A claim of the same text already recorded in the snapshot (by a question or an
  earlier verify) is reused, as the analysis loop does; the server's answer is attached to it and the status
  requested, rule-checked (a refused request is recorded in its history). An edge the server could not answer
  gets no claim and is listed `unknown` with the reason. Edges from one call site to same-named targets
  (overloads) share one claim text: the one the server confirms settles it, and an edge to another of them is
  listed `refutes` with `shared_with` naming the confirmed target, without contradicting the shared claim (counted
  as `refuted_same_name`).
- **Budget like precise.** A `precise.Budget` per command, `budget.lsp_sites` (200) and `budget.lsp_seconds`
  (120 s; the server's start counts) in the config; edges past it are counted as not checked (budget). No cache:
  a server's answer depends on the whole project and its configuration.
- **CLI only.** `lsp definition|references|hover|calls|implementations|types FILE:LINE[:COL] [NAME]`,
  `lsp verify`, `resolve-call ... --lsp`. Exit 0 with an answer, 3 without (`verify`: 1 when an edge is
  contradicted, 3 when no edge was answered, 2 without a graph). No MCP tool: an agent's tool call would start a
  third-party program over the project, which D152 kept off the MCP server for the type checkers; the tool count
  stays 44 and the core menu is unchanged.
- **Review round.** A reviewer drove the client with fakes of their own and found five defects, all fixed with a
  regression test each. (1) The header rule read a neighbouring declaration as the header of the named one: a
  graph edge to `run(int)` on the line above the `run(String)` the server named was confirmed and became
  `statically_verified` (also TypeScript overload signatures and one-line methods), because every line starting
  with a modifier passed. Now a gap line passes only when it is a comment, attribute, annotation or decorator
  (arguments over several lines included), blank, or modifiers and type words with no `(` after a name, no `=`,
  no `;`/`{`/`}` at its end and not the name itself; the wrong edge is refuted (and `contradicted` when it is the
  only edge of its claim). (2) A server that exited while a process it started held its stdout open was reported
  as a hang after the full timeout, and the child survived `close()` (the tree was only stopped while the server
  ran). A waiting request now checks every 0.5 s whether the server exited and fails with "the server exited
  (exit code N)"; the tree is stopped whatever the server's state (job object on Windows, `killpg` elsewhere),
  which also ends the reader threads at once. (3) Diagnostics published under another spelling of the file's URI
  (vscode-uri's `file:///c%3A/...`) were dropped: they are keyed by the file's real path now. (4) `path_of_uri`
  decoded percent escapes twice (`url2pathname` already decodes), so `x%41.ts` became `xA.ts`: one decode now.
  (5) Lines were split with `str.splitlines`, which also splits at form feeds, vertical tabs, U+001C to
  U+001E, U+0085 and U+2028/2029, so every call after a form feed was on the wrong line: only CR LF, CR and LF split now.
  Minors fixed: array `params` from the server no longer kill the reader thread (and any unexpected message now
  breaks the client with its reason instead of ending the reader silently); a graph node without a line no longer
  matches any location of its file. Overstatements corrected here: "nothing left running" held only while the
  server itself ran; the confirmation rule was looser than "annotations, modifiers and comments" suggested.

## Measured

Windows 11, Python 3.13, 2026-10-02, against the fake server of the tests (`tests/fixtures/lsp/fake_lsp.py`, a
Python process); 5 sessions, scratch script, not in the suite.

| step | median | p95 |
|---|---|---|
| start and `initialize` (Python interpreter start of the fake included) | 250 ms | 289 ms |
| one `textDocument/definition` round trip on the raw client | 0.21 ms | 0.30 ms |
| `navigate` definition (site, position, locations) | 0.38 ms | 0.49 ms |
| `resolve_call` uncached (call tokens, definition, verdict) | 0.40 ms | 0.52 ms |
| `shutdown` + `exit` + wait | 21 ms | 22 ms |
| parsing one framed definition answer in-process | 9 us | |

- The client's own cost per question is about 0.2 ms over the round trip (0.38 against 0.21 ms); a first version
  resolved real paths for every location and cost 1.1 ms, now cached per session.
- `lsp verify` on the test project (4 call edges, 2 TypeScript, 2 Java): 0.57-1.07 s per run inside
  `verify_edges` (0.25-0.48 s of it the fake's start), 0.81-1.34 s wall with the snapshot check and graph load;
  3 edges `statically_verified`, `new Util()` (no answer in the fake's table) `strong_inference`.
- A real server's cost is its own: tsserver and jdtls take seconds to load a project and their first answers are
  slower than later ones. Not measured: no real server was available.

## Limits

- **No real language server was available to test against.** The machine has no pyright, pylsp, gopls,
  typescript-language-server, rust-analyzer, jdtls or clangd, and nothing was installed. Everything above is
  measured against a fake that answers from a table; how each real server answers (jdtls's workspace `-data`
  folder, tsserver's project loading, a server that needs `didChangeConfiguration` or sends progress before
  answering, position encodings other than UTF-16) is untested. The first real server may need a fix.
- Diagnostics are what the server published by the time the answer came; a server that publishes later is not
  waited for, and there is no `pull` diagnostics request.
- A server that answers slowly while it indexes the project may hit the 30 s timeout on its first question; then
  that command gets `unknown` for the language (raise `--timeout`).
- One server per language per command; nothing is kept warm between commands, so every command pays the start.
- The confirmation compares the location with the graph node's file and line (or the header above the name).
  A graph node whose line is neither, or a server that points at a declaration file (`.d.ts`) instead of the
  source, is a refutation unless an implementation matches.
- Only call edges whose call site the server serves are checked; `ask` and MCP analyses never start a server.
- The process tree on Windows is the job object's: a process the server starts in the instant between its own
  start and its assignment to the job (before the server's code runs, in practice) is outside it, and is stopped
  by `taskkill /T` only while the server still runs. The POSIX path (`killpg` of the session's group) is not
  exercised on this machine.
- A claim's text names the caller, the target's name and the call line, not the overload: two edges of one call
  to same-named targets share one claim, which the confirmed edge settles.
- The header rule is textual: a declaration whose modifier or type lines hold `=` or a call (a default value in a
  C++ attribute, a Kotlin annotation without `@`) is not read as one header and is refuted unless the server's
  location is the node's own line or its full range starts there.
- A claim that a server confirmed and a later server refuted keeps both pieces of evidence; its status is the
  later answer's.

## Upgrading note

New, opt-in: `verinoda lsp definition|references|hover|calls|implementations|types FILE:LINE[:COL] [NAME]`,
`verinoda lsp verify [PATH ...]` and `resolve-call ... --lsp`. Nothing changes for an existing project until a
command is run with them. Language servers are started only in trusted projects (`verinoda trust`); `lsp` joins
the protected settings, so a repository's own `.verinoda/config.json` names a server only once the project is
trusted (the user config always can). New config keys: `lsp.servers` (`{language: [argv ...]}`) and
`budget.lsp_sites` / `budget.lsp_seconds`. When a resolver (jedi, SCIP or a language server) confirms a call edge
outside Python, the claim no longer carries the "checked for Python only" uncertainty. No schema change; MCP
tools unchanged (44).

## Tests

`tests/test_lsp.py` (29 tests), every one driving the real client against `tests/fixtures/lsp/fake_lsp.py`:
framing and garbage detection; UTF-16 columns and call tokens; definition, references, hover and the published
diagnostics, with the server's `workspace/configuration` request answered, each file opened once and
`shutdown`/`exit` sent; call hierarchy, and type hierarchy and implementations when not advertised and when
advertised; `resolve_call` confirms, refutes, defers to implementations (an interface method), matches a Java
node on its annotation line, reports a missing call and caches; crash, garbage and hang (the hang with a child
process, its server ignoring `shutdown` and `exit`) are `unknown` with the reason and leave no process; a server
that crashes or hangs during `initialize` is `unknown` and not started twice; an untrusted project starts no
server (and its config's `lsp.servers` is ignored); no server on PATH is `unknown` with the next step for
TypeScript and Java; the default found on PATH through a `.cmd` launcher; `lsp verify` makes a TypeScript and a
Java edge `statically_verified` with the server's name and version in the evidence, a disagreeing server makes
a reused claim `contradicted` (exit 1) and a fresh one names both locations; a crashing server during `verify`
records no claims; the CLI commands and their exit codes. From the review round: an adjacent Java overload is
refuted (resolve level), refuted against the shared claim end to end, and a lone neighbouring declaration the
server names makes the edge `contradicted`; header lines (TypeScript overloads, a multi-line annotation, a
Javadoc comment, GNU-style C, a one-line method, a Python decorator); a target without a line is `undetermined`;
a server that exits while its child holds stdout is "exited" in well under the timeout and leaves neither
process; diagnostics under vscode-uri's spelling; array `params` from the server; URIs with `%`, spaces and
Turkish letters decoded once; lines split at CR LF, CR and LF only (a call after a form feed resolves).
