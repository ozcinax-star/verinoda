## Why

`slice` (D150) answers where one line's values come from. The question security review asks is the reverse and
across the whole project: can a value a user sends reach a SQL string, a shell, `eval` or a file path without a
check, and along which path? CodeQL, Semgrep Pro, Pysa, Joern and Code Pathfinder answer it with sources, sinks
and sanitizers declared as data and every result shown with its path. Verinoda had the data dependence (reaching
definitions per function, callers through the index) but no notion of untrusted input.

## Decisions

- New command `verinoda taint [PATH ...] [--local] [--depth N] [--no-builtin] [--tests] [--json] [--sarif]`, module
  `taint.py`, Python only. Exit 3 when a path is found, 0 when none, 2 on an error (bad rules, a path outside the
  project, a depth outside 0-3). No MCP tool: the core menu keeps its five.
- Library behaviour is data, `verinoda/data/taint_python.json`: 18 sources (Flask, Django, Starlette/FastAPI
  request data; `input()`, `sys.argv`, `os.environ`, `os.getenv()`), 30 sinks with the argument that matters and a
  kind (sql, command, code, deserialization, path, template, xss, redirect, request), 12 sanitizers (`int()`,
  `shlex.quote()`, `html.escape()`, `secure_filename()` ...). A pattern `a.b` matches a name or attribute chain
  ending in `.a.b`, `a.b()` a call of it, `*.m` any receiver's method; a sink may hold only with a keyword
  (`subprocess.run(..., shell=True)`; `shell=False` or no `shell` is not a sink). The project adds its own in
  `[taint]` of `verinoda.toml` (or `[tool.verinoda.taint]` of `pyproject.toml`) - committed, so CI sees them - or
  replaces the library's with `builtin = false`; a malformed table is an error, never ignored.
- Threats: each library source is `remote` (request data) or `local` (argv, the environment, `input()`). Only remote
  ones are used unless `--local`, as CodeQL's default threat model: on Verinoda's own code every one of the 12
  paths found with `--local` is the user's environment reaching `open()` (a cache folder, an artifacts folder),
  which is the design of a command-line tool. The project's own sources are always used.
- Route handler parameters taken from the request are sources: `<name>` in a Flask path (not with an `int`, `float`
  or `uuid` converter, which the framework parses), `{name}` in a FastAPI/Starlette path, and for a FastAPI-style
  `@x.get/post/put/patch/delete` handler a parameter annotated `str`, `bytes` or `Any` (or not annotated) without a
  `Depends(...)` default.
- The search runs backward from each sink argument over data dependence only: `slicing.CFG` and its reaching
  definitions (the control dependence a slice also computes is not built). For a definition, only the part of a
  tuple assignment that defines the name is followed (`a, b = src, "c"`: `b` is clean); an update (`x.a = v`,
  `items.append(v)`) carries what the object held before too; names inside a sanitizer call are not followed. At a
  parameter: a route source, else the argument each caller passes (calls edges, at most 8 callers, `--depth`
  calls up, default 2; `*args`/`**kwargs` that may carry it is a note). At a call of a project function (by the
  calls edge at that line, else the one function of that name in the file): what its `return` statements are made
  of, two levels down, memoised per function. A library call's result is taken to depend on its arguments.
- Each finding is `strong_inference` with `rule` `taint/<kind>`, the sink (call, match, kind, origin), the source
  (match, kind, origin: the library, `verinoda.toml [taint]` or the route) and the path source first, every step at
  `file:line` with its line and what happens there (`source request.args -> who`, `passes who as name of
  find_user (EXTRACTED call edge)`, `defines q`, `get_cmd returns it`, `sink *.execute (sql)`) and the number of
  hops between functions. One finding per source site and sink. `--sarif` writes one SARIF result per path at the
  sink with its steps as a `codeFlows` thread flow (a `warning`), through `sarif.from_taint`.
- Cost: each file is parsed once with its functions and the calls on each line, and each function's graph is
  built once per run; a search visits at most 20,000 states per sink and a function over `slicing.MAX_NODES`
  statements is a note (a source in the sink's own argument is still found).

## Measured

Windows 11, Python 3.13, Verinoda's own checkout (indexed), the analysis without the graph load (1.6 s):

- 369 Python files (tests left out), 329 sink calls: 31.6 s with remote sources (no path found: Verinoda serves no
  Flask/FastAPI routes), 31.1 s with `--local` (12 paths: 11 `taint/path`, 1 `taint/sql`, all from `os.environ`).
  Before the files and functions were indexed once per run (each lookup walked the whole tree) and the control
  dependence was left out, the same run took 249.9 s.
- The longest path found has 18 steps (an environment value through `experiments.run`'s result dictionary into a
  trace file's path, in a copy of Verinoda kept under `benchmarks/corpora`): the dictionary is one value to this
  analysis, so the path is real data dependence but not a real flow - the heap approximation the limits name.
- `tests/test_taint.py`: 20 tests in 8-16 s.

## Limits

- Python only; data dependence only (a branch on a tainted value is an implicit flow and is not followed).
- The heap is approximated: an attribute or item update taints its object, a dictionary or list is one value, and
  aliasing and globals changed elsewhere are not seen.
- A library call's result depends on its arguments; a project function's result is followed into its `return`s
  (two levels), not through its own parameters from that call site.
- Callers come from the index's calls edges (INFERRED ones are a resolver's guess) and are matched by name; at
  most 8 per parameter. Without an index callers are not followed and calls are resolved in their own file only.
- Sources, sinks and sanitizers are names: a sink reached through a variable, `functools.partial` or a wrapper is
  not seen, and a check written as an `if` (not a sanitizer call) does not clear a value.
- A path found is not proof of a vulnerability; no path found is not proof of safety.

## Upgrading note

New command `verinoda taint` (exit 3 when a path is found) and the library data `verinoda/data/taint_python.json`.
A project may add a `[taint]` table to `verinoda.toml` (`sources`, `sinks = [{match, arg, kind}]`, `sanitizers`,
`builtin`). `sarif.export(res, "taint")` is new. No MCP change; nothing to migrate.

## Tests

`tests/test_taint.py` (20): a scanned Flask/FastAPI project: a source reaching an SQL sink through a caller with
every step in order, no caller hop without an index, sanitizers (`int()`, `shlex.quote()`) stopping the path, a
Flask route parameter as a source and an `<int:...>` one not, a value returned by a project function, a
`subprocess.run` without `shell=True` not a sink, a source in the sink's own argument, only the tuple part that
defines the name, an `append` carrying the taint, a FastAPI query parameter as a source and a `Depends` one not,
the counts and rules of a run, local sources only with `local`, the project's own `[taint]` rules and
`builtin = false`, five malformed rule tables, the CLI's text, JSON, SARIF code flows and exit codes (3, 0, 2), and
a function over the size limit giving a note.
