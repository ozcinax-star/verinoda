# 1.3 Git hooks for re-indexing (draft for DESIGN.md; next free D-number)

## Why

After a commit, a branch switch or a merge, the files behind the index change without anyone running `verinoda
update`, and the next answer starts from a stale graph (or pays for the update then). Git can run a command
after each of those events. Graphify and code-review-graph install such hooks; here they run Verinoda's own
incremental update.

## Decisions

- **`verinoda hooks install | uninstall | status`** (`--dry-run`; `install --print` shows the lines; `uninstall
  --gone`), and `verinoda setup --hooks`. A CLI step the user takes; not an MCP tool (an agent does not install
  hooks).
- **Four hooks**: `post-commit` (not while a rebase is in progress: its picks are intermediate states),
  `post-checkout` only when git passes `$3 = 1` (a branch checkout; a file checkout changes what the user asked
  for, not the branch), `post-merge`, and `post-rewrite` (once at the end of a rebase or an amend). Each starts
  `<the interpreter that installed it> -P -m verinoda update <project>` in a subshell, detached, output discarded:
  git never waits for it. The update is incremental and has its own build lock.
- **The project's code never runs.** Git runs hooks from the top of the work tree, and `python -m` puts the
  current folder first on `sys.path`: a project with its own `verinoda/` folder (this repository) would have run
  that instead of the installed package. `-P` (Python 3.11+; `-I` before) keeps it off, as the agent launcher
  already does. Git's hook variables (`GIT_DIR`, `GIT_INDEX_FILE`, ...) are unset for the update.
- **Only for this project's work tree, only while it exists.** Every worktree of a repository shares the hooks
  folder, so the block runs only when `git rev-parse --show-toplevel` is the project's work tree, and only while
  the project's `.verinoda/` exists: a removed worktree's block does nothing (it no longer recreates the folder).
  `VERINODA_NO_HOOK=1` skips it for one git command.
- **Nothing that is there is overwritten.** A marked block (`# >>> verinoda update >>> <project>` ... `# <<<
  verinoda update <<< <project>`) goes right after the hook's `#!` line, so an `exit 0` further down cannot skip
  it; it is keyed by the project's path, so two projects of one repository each have theirs. A shell script is
  one whose `#!` program, or `env` argument, is sh, bash, dash, zsh, ksh or ash; any other hook, a symbolic link
  (a hook shared with other repositories), a block whose end marker was edited by hand, and a file that cannot be
  written are left alone and reported. `uninstall` removes exactly the block, giving the hook back byte for byte
  (CRLF hooks and a `#!` line without a line end included), and deletes a file Verinoda created that holds
  nothing else. Installing twice changes nothing.
- **Hooks another tool owns are not touched.** When `core.hooksPath` points outside the repository's git folder
  (husky, pre-commit, a shared folder), `install` writes nothing (exit 2) and prints the lines to add there, and
  `uninstall` edits nothing there either.
- **Blocks of moved or removed projects.** `status` lists the other projects' blocks in the hooks and those whose
  folder is gone; `uninstall --gone` removes the latter.
- **No merge driver.** The graph is in `.verinoda/`, which git ignores, so it is never merged; a merge changes
  source files, and `post-merge` re-reads them.

## Measured

Tests only: on Windows, with Git for Windows' `sh`, the hook runs after `git commit`, `git checkout -b` and
`git commit --amend`, not after `git checkout -- file`, nor with `VERINODA_NO_HOOK=1`, nor in another worktree.

Review round (two reviewers): fixed the project's own `verinoda/` package running from the hook (no `-P`), a
missing end marker wiping the rest of a hook, `/sh` matched anywhere in a `#!` path, write errors raised as
tracebacks, symbolic links written through, blocks of moved projects invisible, `status` matching path prefixes,
`uninstall` editing a hook manager's folder, a `#!`-only hook given back with a line end, worktrees updating
another worktree's project (and recreating a removed one's `.verinoda/`), and a rebase firing one update per
pick (now `post-rewrite` once at its end).

## Limits

- The interpreter path is written into the hook; after a reinstall of Verinoda into another environment, run
  `verinoda hooks install` again (it replaces the block).
- A hook manager's own hooks are not edited; the user adds the printed lines there.

## Upgrading note

New: `verinoda hooks install` (and `setup --hooks`) adds post-commit, post-checkout and post-merge hooks that
run `verinoda update` in the background; `verinoda hooks uninstall` removes exactly what it added. Nothing
changes unless you run it. The MCP tool count is unchanged.

## Tests

`tests/test_githooks.py`: four hooks created and removed; an existing hook kept with the block after its `#!`
line and restored byte for byte; a non-shell hook left alone; the hook really runs after a commit and a branch
switch and an amend, not after a file checkout or with `VERINODA_NO_HOOK=1`, not without `.verinoda/`; the
project's own `verinoda/` package never runs; CRLF and `#!`-only hooks restored byte for byte; a non-shell hook
(a `#!` path containing `shared`) and a hand-edited block left alone; `core.hooksPath` outside the git folder refused
with the lines to add and not edited by `uninstall`, inside it accepted; projects sharing hooks, a prefix path,
blocks of a folder that is gone and `--gone`; a worktree's block runs only for its own work tree; the CLI (`status`, `--print`,
`--dry-run`, outside git), in a repository path with a space and non-ASCII.
