# 1.3 Git hooks for re-indexing (draft for DESIGN.md; next free D-number)

## Why

After a commit, a branch switch or a merge, the files behind the index change without anyone running `verinoda
update`, and the next answer starts from a stale graph (or pays for the update then). Git can run a command
after each of those events. Graphify and code-review-graph install such hooks; here they run Verinoda's own
incremental update.

## Decisions

- **`verinoda hooks install | uninstall | status`** (`--dry-run`, and `install --print` to see the lines), and
  `verinoda setup --hooks`. A CLI step the user takes; not an MCP tool (an agent does not install hooks).
- **Three hooks**: `post-commit`, `post-checkout` only when git passes `$3 = 1` (a branch checkout; a file
  checkout changes what the user asked for, not the branch) and `post-merge`. Each starts
  `<the interpreter that installed it> -m verinoda update <project>` in a subshell, detached, output discarded:
  git never waits for it. The update is incremental and has its own build lock, so hooks that fire together do
  not build twice at once. `VERINODA_NO_HOOK=1` skips it for one git command.
- **Nothing that is there is overwritten.** A marked block (`# >>> verinoda update >>> <project>` ... `# <<<
  verinoda update <<< <project>`) goes right after the hook's `#!` line, so an `exit 0` further down cannot skip
  it; it is keyed by the project's path, so two projects of one repository each have theirs. A hook that is not
  a shell script (another interpreter, a binary, not UTF-8) is left alone and reported. `uninstall` removes
  exactly the block, restoring a hook byte for byte, and deletes a file Verinoda created that holds nothing
  else. Installing twice changes nothing.
- **Hooks another tool owns are not written.** The hooks folder is `git rev-parse --git-path hooks`; when
  `core.hooksPath` points outside the repository's git folder (husky, pre-commit, a shared folder), `install`
  writes nothing, exits 2, and prints the lines to add there.
- **No merge driver.** The graph is in `.verinoda/`, which git ignores, so it is never merged; a merge changes
  source files, and `post-merge` re-reads them.

## Measured

Tests only: on Windows, with Git for Windows' `sh`, the hook runs after `git commit` and `git checkout -b`, not
after `git checkout -- file` nor with `VERINODA_NO_HOOK=1`.

## Limits

- The interpreter path is written into the hook; after a reinstall of Verinoda into another environment, run
  `verinoda hooks install` again (it replaces the block).
- `post-rewrite` (rebase, amend) is not hooked: an amend is followed by the next commit's update, a rebase by
  its `post-checkout`.
- A hook manager's own hooks are not edited; the user adds the printed lines there.

## Upgrading note

New: `verinoda hooks install` (and `setup --hooks`) adds post-commit, post-checkout and post-merge hooks that
run `verinoda update` in the background; `verinoda hooks uninstall` removes exactly what it added. Nothing
changes unless you run it. The MCP tool count is unchanged.

## Tests

`tests/test_githooks.py`: three hooks created and removed; an existing hook kept with the block after its `#!`
line and restored byte for byte; a non-shell hook left alone; the hook really runs after a commit and a branch
switch, not after a file checkout or with `VERINODA_NO_HOOK=1`; `core.hooksPath` outside the git folder refused
with the lines to add, inside it accepted; two projects of one repository; the CLI (`status`, `--print`,
`--dry-run`, outside git), in a repository path with a space and non-ASCII.
