# Error and trace import: Sentry events and OpenTelemetry spans from a file

## Why

`trace-log` maps the stack traces of a log onto the code, but production errors usually live in an error tracker
or a tracing backend, not in a log on disk. Sentry's event JSON and an OpenTelemetry trace in OTLP JSON carry the
same thing in a structured form: frames with a file, a line and a function. Reading them from an exported file
gives the same kind of evidence - what one run recorded - without a network call or an account.

## Decisions

- No new command: `verinoda trace-log FILE` reads a JSON export as well as a log. A file whose text starts with
  `{` or `[` and parses - as one document, or as JSON lines where most lines parse or only the last one does not -
  and holds a Sentry event or a span with frames is an export. A file named `.json` / `.jsonl` / `.ndjson` that
  does not parse, or holds no event or span, is refused (exit 1) with the line and column; any other file that
  does not parse (`{main} starting`, `[14:02:08] [Server thread/INFO] ...`, a JSON log line followed by a
  traceback) or holds no event (a structured log) goes to the log reader as before. `--json` says which with
  `mode`: `export` or `log`.
- Formats: a Sentry event (`exception.values[].stacktrace.frames`, the API's `entries` form, a list of events,
  `{"data": [...]}`, JSON lines) and OTLP JSON (`resourceSpans` / `scopeSpans` or the older
  `instrumentationLibrarySpans` / `spans`). From a span: its `code.filepath` / `code.lineno` / `code.function`
  (and the newer `code.file.path` / `code.line.number` / `code.function.name`; with only `code.namespace`, the path
  is built from the class or module and the row says so - a namespace without a package, such as `Foo` or `a.`,
  builds none and the frame is "not in the repository") and the `exception.stacktrace` text of its `exception`
  events, read for Python, JVM and Node frames with the failure-signature reader's patterns. Frames are kept
  innermost last for every source; a JVM text's `Caused by:` blocks are each reversed on their own, so the root
  cause's throwing frame comes last. A line number is at most 9 ASCII digits; a text frame with anything else is
  skipped, a structured one has no line.
- Paths: whole-suffix matching over the indexed files, the rule `failsig.PathResolver.resolve` already used.
  `PathResolver.matches()` now returns every file that ties for the longest suffix, so an ambiguity is reported
  with its candidates (and the ones whose function fits the line) instead of silently giving nothing; `resolve()`
  keeps its behaviour. Backslash Windows paths, `file://` URLs and the repository's own absolute root are handled
  there; a Windows path that matches nothing as written is compared again with case folded. A Sentry JVM frame
  (`Foo.java` with `module: com.example.Foo`) is matched as `com/example/Foo.java` only, never as any other
  `Foo.java` of the project.
- A frame is `mapped` only when the file exists, the line is inside it, a recorded `context_line` equals the
  current line, and the frame's function is one of the definitions the index puts around that line (lambdas,
  `Object.handle`, `lambda$tick$2`, Go's `.func1`, `<init>` are reduced to the name compared; a name over 512
  characters is not compared). What a mapped frame was not compared on is named in `not_checked`: `source line`
  when the frame records none, `function name` when it has no name to compare (`<anonymous>`, `?`) or the file has
  no indexed definitions. A frame checked on nothing but its line's range says so on its row ("only the line's
  range was checked") and in the stored claim's text. Otherwise the row is `stale` (file missing on disk, line
  beyond the end, the recorded source line differs, the function name is not at that line - with what is there),
  `ambiguous`, or `not_in_repo` (no indexed file ends with the path: "file missing" for an `in_app` frame, "origin
  unknown" for a frame the export does not mark, which includes every frame of an OTLP export).
- Library frames are folded into a count with the first and last name: `in_app: false`, or a `site-packages` /
  `node_modules` / stdlib path on a frame the export does not mark `in_app: true`. A frame marked `in_app: true` is
  matched whatever its path looks like (a Go project's `internal/`, a checkout under `/lib/python...`).
- A mapped row carries `status: observed` and the event's scope: what that event recorded, not what always
  happens. `store()` records one claim per mapped frame (at most 50 a run) whose evidence is the frame as read,
  kept under `.verinoda/logs/<name>-<hash>.frames.json`. Only the frames are kept, redacted, not the export: a
  Sentry event also carries request headers, the user and local variables. The same export imported again adds
  no claim: one with the same kept file, event and frame that is not stale is reported as `existing`. `--json`
  carries a `claims_note`: a stored claim's evidence never verifies.
- Limits are applied while reading: at most 200 events (an OTLP document stops building spans at the limit), the
  innermost 200 frames of each, 5,000 lines of one `exception.stacktrace` text.

## Measured

- The fixtures (`tests/fixtures/trace_import/`): a two-event Sentry export (Python and JVM, the `entries` form)
  gives 3 mapped, 3 stale (line beyond the end, another function at that line, a changed source line),
  1 ambiguous, 1 not in the repository, 2 library frames; an OTLP export with two spans gives 5 mapped frames and
  one JDK frame (`java/lang/Thread.java`) reported as not in the repository, origin unknown.
- A 5,000-frame event reads the innermost 200 frames and says so (tested with three such events).
- Review round: a `{`-led log that is not JSON was refused; it is read as a log again unless named as JSON. A
  5,000-digit line number or a superscript `2` aborted the run; such a text frame is now skipped and a structured
  one has no line. Function-name reduction used two backtracking patterns (the reviewers timed 27 s and 2.9 s on
  long names); it is string operations on a name capped at 512 characters, and the test bounds pathological names to
  under 0.5 s. A frame checked on nothing but its line's range was reported like a checked one; it is labelled.
  Unmatched frames of unknown origin were folded as library frames, and `in_app: true` was overridden by a
  library-looking path; both fixed. A small JSON-lines export whose only other line was cut was refused; it is read.
  A repeated import duplicated its claims. JVM `Caused by:` blocks were reversed as one list. `code.namespace`
  values without a package built paths that matched any file of that name. An OTLP document built every span before
  the event limit applied.

## Limits

- Stored claims have the status the claim rules allow for evidence Verinoda did not produce (`agent_report`
  never verifies): in practice `weak_inference`, as for `trace-log`. The report's rows are `observed` for their
  event; the stored claim does not claim more than its evidence allows, and the command and `claims_note` say so.
- A mapped frame without a `context_line` (every OTLP frame) was not compared with the source line, only placed
  inside the file and, when it has a name, inside a definition of that name.
- Path matching is case-sensitive except for a Windows-looking path (a drive letter or backslashes) that matches
  nothing as written: it is compared again with case folded. A macOS path in another case is not.
- Only the indexed files are candidates: a frame in a file the index does not hold is "not in the repository".
- `exception.stacktrace` text is read for Python, JVM and Node frames; Go, Rust, .NET and Ruby text stacks are
  not (their span `code.*` attributes are).
- A file over 32 MB is refused when named `.json` / `.jsonl` / `.ndjson`, otherwise read as a log; at most 200
  events, the innermost 200 frames of each and 50 stored claims a run. Nothing is fetched from Sentry or a
  collector: the export must be on disk.
- A JSON-lines file where half the lines or more do not parse is not JSON lines, unless the only line that fails
  is the last one.
- Frames are not linked to the callers and callees in the graph, nor to GameTests (`trace-log`'s log path does
  that for JVM logs).

## Upgrading note

`verinoda trace-log FILE` also reads a Sentry event export or an OpenTelemetry trace in OTLP JSON from a local
file: each frame is mapped onto the repository or reported as stale, ambiguous or not in the repository, and a
mapped frame is recorded as a claim scoped to its event. A file named `.json` / `.jsonl` / `.ndjson` is read as
JSON and refused if it does not parse; any other file is read as an export only when it parses and holds an event
or span, and as a log otherwise, as before.

## Tests

`tests/test_trace_import.py`: telling an export from a log (JSON lines with a cut last line, a single event and a
cut line, UTF-16, bytes that are not UTF-8, broken and deeply nested JSON, a `{`-led log and a JSON log line
followed by a traceback read as logs, a named file with half its lines broken refused); line numbers that are not
numbers (a superscript `2`, 5,000 digits in Python, JVM and Node text) skipped without aborting; function-name
reduction in
bounded time on pathological names; JVM `Caused by:` order; `code.namespace` without a package; the OTLP event
limit applied while reading; `PathResolver.matches()` naming every file of a shared suffix while `resolve()` still
picks none; the Sentry fixture's mapped, stale, ambiguous, missing and library frames (a Windows absolute path, the
`entries` form, a JVM frame); the OTLP fixture's `code.*` attributes and Python and JVM `exception.stacktrace`,
its JDK frame of unknown origin; the CLI storing one claim per mapped frame with only the frames kept, `mode` and
`claims_note` in `--json`, and a repeated import adding none; the CLI refusing broken or empty named exports and
leaving a structured log and a `{`-led log to the log reader (`mode: log`); hostile frames (a `site-packages` path
whose tail is a project file, a library class sharing a project file name reported as not in the repository, a
Windows path in another case, an `in_app` frame under `/lib/python` mapped, a frame checked on nothing but its
line's range labelled, an unmarked unmatched frame not folded, line 0, a boolean line, a non-object frame, 5,000
frames).
