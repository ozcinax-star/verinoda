# Verinoda architecture

Verinoda answers questions about a codebase as **claims backed by evidence**
and keeps those claims honest over time: facet-level stale invalidation,
anchored re-checks, critique, and user corrections handled as hypotheses. The
knowledge graph comes from the Graphify-derived `project_index`. Everything
else is Verinoda's own.

The design decisions (D1-D40) and their implementation status are in
[DESIGN.md](DESIGN.md). Measured results are in [BENCHMARKS.md](BENCHMARKS.md).

```
             verinoda CLI (cli.py)              MCP server (mcp/server.py, 36 tools)
                         \                        /
                          \   same core functions /
  workflow.py (init / scan / update / verify)    analysis.py (budgeted loop per question plan)
     |                                               |
     |  derived, disposable indexes                  |  per sub-question
     |  index.py -> project_index/ (Graphify)        |  question_plan.py <- lexicon.py, textnorm.py
     |  search_index.py (search.db)                  |  retrieval.py     <- search_index.py
     |  lexicon.py (lexicon.json)                    |  architecture_map.py (views)
     |  anchors.py (file_facts)                      |  precise.py / scip_reader.py (optional)
     |                                               |  codecheck.py (check / api; optional, jedi)
     |                                               |  runtime/ (optional test observation)
     v                                               |  references/ (offline pinning)
  snapshot.py (stat-cached hashes, git state)        v
                                   claims.py <- entail.py, evidence.py, anchors.py
                                   critique.py (probes, definitive vs heuristic refutation)
                                   store.py (SQLite atlas.db, schema v6, append-only)
  research.py / feedback.py / memory.py / experiments.py
  debug.py (ledger) <- looprules.py, failsig.py (+ runtime/failsig_plugin.py), treestate.py
  review.py (change review) <- review_rules.py, anchors.py, treestate.py, guards.py, architecture_map.py
  probe.py (behaviour probe) <- probe_inputs.py, probe_gate.py (+ runtime/probe_plugin.py), experiments.py
```

## Module responsibilities

### Graph and indexes

| Module | Role |
|---|---|
| `project_index/` | Graphify at a pinned commit: file detection, tree-sitter extraction, graph build, clustering, report/HTML, and the upstream CLI (`verinoda index -- ...`, installer and `~/.graphify` writers blocked). Read-only for Verinoda; see [UPSTREAM.md](UPSTREAM.md). |
| `index.py` | The only door into `project_index`. `build()` does a full or changed-paths rebuild (AST only) and installs the path-identity memo (a monkeypatch; the vendored file is unchanged); for the length of the build `Path.resolve` and the re-anchoring of cached source paths answer once per path. Afterwards graph.json is read once and written at most once: ids made portable (`portable_ids.py`) and, for `scan`/`update`, the nodes of files that do not exist dropped in the same rewrite; the counts come from that data. That rewrite makes the upstream "topology unchanged" fast path miss on every build of a repository whose ids carry the root or whose code names files it does not have. There, when the pipeline builds exactly the graph of the last full rebuild (a hash of every node, edge and neighbour list; same commit and code) and graph.json, the labels and their signatures are as that build left them, the fast path is let fire (`_keep_unchanged_graph`, `rebuild_record.json`): graph.json is kept, and GRAPH_REPORT.md and the dated backup are written with the upstream functions as the full path writes them on such a repository (it always writes them there). A build is recorded only when it rewrote graph.json and a full rebuild of the same graph would number its communities the same way again, and a record is neither written nor used by a process whose code on disk changed after it was loaded (the MCP server while Verinoda is edited or upgraded). When graph.json is the pipeline's own output, the upstream comparison decides alone, as before: a kept graph leaves GRAPH_REPORT.md and the backups as they are. Data-shaped `.json` files, which the upstream JSON extractor skips and its cache never keeps, are remembered by path and bytes (`empty_json.json`) and not parsed again; a result is kept only when the file holds the same bytes after extraction as before, and `scan --force` replays none. On Windows, what is left to extract is extracted in the process rather than by a process pool when it is small: fewer than 64 files and at most 256 KiB (the upstream contract for a one-worker pool); a larger batch goes to the pool as before. `load()` returns a `Graph` with true edge direction. Symbol spans come from one pass per file: Python `ast` end lines, tree-sitter `end_point` for other languages, Markdown sections; the capped next-symbol rule is a labelled fallback (`span_basis`). A per-file interval index answers "which symbol encloses line N". The Python receiver-call pass (`param.method()` on annotated parameters, `x = Cls()` locals) runs at build time and is stored in the `receiver_calls.json` sidecar; `load()` only applies it. Those edges are `INFERRED` with `derived_by=verinoda.receiver`. The class a receiver's type names is the one the calling file can see (`_visible_class`): its own file, then a file it imports, then a class under a top-level folder it imports from or lives in; a class across the boundary of a detected copy or reference tree (either way) is never linked (sidecar v3; an older sidecar's per-file facts are reused, its edges are not). The Java/Kotlin call pass (`java_call_edges`) stores its edges in the same sidecar: `Cls.method(...)` and `var.method(...)` on a declared type, where the class is bound the way javac binds it for the file (explicit import, own package, `pkg.*` import); an ambiguous or foreign class gets no edge (`derived_by=verinoda.java_calls`). |
| `search_index.py` | Persistent passage index in `.verinoda/index/search.db` (D17-D19, D22). Units are symbols (own lines only), module-level blocks and prose sections. Passages are 12-line windows with stride 6. The tokenizer is identifier-aware (whole compound and camel/snake parts, light stemming, Turkish folding). Ranking is BM25F (name, path, body fields; idf per unit; unit = best passage), plus an exact-identifier override and a personalised-PageRank prior by local push. Text files the graph has no nodes for (data packs, JSON/yml/toml configs, shaders, skipped sources) are indexed as `data` units (yml/toml split by top-level section); the files it skips are listed in an `unindexed` table with the reason. A `refs` table stores the resource ids each line names (see `resources.py`); ranking gives linked units a bonus, ranks byte-identical copies once and multiplies units under config `index.reference` trees by 0.6 unless the question names them; generic data files (neither configuration nor a pack resource) count 0.6x unless the question names the file; a data unit takes half the PageRank prior of a code unit linked to it. An inflected Turkish word also searches its longest indexed stem ("bıçağının" -> bicagi: weight 0.8, or 0.5 when the inflected form is itself an indexed word); a word the index does not know also searches corpus terms through its stem, the more narrowly the shorter the stem (`_stem_terms`: 5+ letters, the three most frequent terms it begins, "projenin" -> `project`; 4 letters, the stem inflected, for a name its first part, snake_case or camelCase, `WispSpawner` but not `paragraph` for "paraları"; 3 letters, the stem itself when it is a name part, `sil`, so "sayıyor" no longer reaches `sayfa`). In a Turkish question an English word that is a name part of some indexed unit (symbol, test, heading, data key; `update`, `graph`) takes from the lexicon only the pairs that carry it (`_part_carries`: the repository's translation pairs, a name built on the word, `deduplicate`, and one the seed dictionary translates to it, `baslat` for `start`), not the other names it co-occurs with; a term reached by several routes keeps the highest weight. A code file whose symbols no longer start where the graph says (it changed while the index was built) is stored as changed since indexing, so queries report it and the next `update` rebuilds it. Incremental per changed file; a schema or tokenizer version change rebuilds it. `Handle.pinned()` lets one thread's reads share a connection for a batch of lookups (the UI export). |
| `resources.py` | Resource ids that connect code and data files (game data/resource packs, Minecraft layout): `ns:path` names `data/<ns>/<type>/<path>.<ext>` or `assets/<ns>/...`. `resource_keys` lists the ids a file defines; `refs_in_line` finds `function ns:x`, quoted `"ns:path"`, translation keys `"item.ns.x"`, unquoted ids in data files and bare quoted names; `KeyMap.resolve` maps a reference to the defining files (a bare name only when one namespace defines it). Links are ranking leads; a claim built from one cites the naming line, and a bare-name link is labelled an inference. |
| `textnorm.py` | Shared TR/EN normalisation (D5): length-preserving Turkish folding (`İndirim` -> `indirim`), apostrophe-suffix splitting, stopwords, a short-technical-term keep-list, `tr_stem` confirmed by the repository vocabulary with a 5-character prefix fallback, light English stemming, Turkish case suffix -> role, language detection. |
| `python_facts.py` | During `index.build`, replaces the upstream Python symbol facts pass with one that keeps, per file and keyed by a hash of its bytes, what the two walks over its tree find (`from ... import` statements; calls in top-level functions) in `.verinoda/index/python_facts.json`. Where an import points is still worked out on every build (it depends on which other files exist). Same facts in the same order as the upstream pass (`tests/test_python_facts.py`); the kept file is dropped when the upstream module, the Python grammar or this module's own walk changes, and `scan --force` neither reads nor keeps it; one of another shape counts as empty and is written again, and a save that fails leaves the previous file and no temporary one. No file under `project_index` is edited. |
| `python_cross.py` | During `index.build`, the cross-file import pass (`_resolve_cross_file_imports`) walks a kept *pruned tree* per unchanged `.py` file instead of parsing it: the file's `from ... import` statements, its class and function definitions, and the identifiers inside a definition that one of those imports binds (the only nodes that walk can use), kept in `.verinoda/index/python_cross.json` keyed by a hash of the file. Only the parse is replaced (`_parse_python_tree`, for the length of the pass); the upstream function runs unchanged, so where imports point and which edges are added or repointed are worked out on every build. A file 400 or more levels deep gets its full tree. The loop that repoints type references, which scanned every edge once per importing file, is given only the edges it can change (references, inherits, implements, extends); the stub prune after it, the one step that reads every edge, runs on a scratch copy of the nodes and is redone over every edge. Used only while the vendored function's source matches a pinned digest (otherwise the pass runs as upstream and `tests/test_python_cross.py` fails until the pruning is checked again); the kept file is dropped when tree-sitter, the Python grammar, the upstream parse, the pass or this module's pruning change, and `scan --force` neither reads nor keeps it. A damaged entry is parsed again, a kept file of another shape counts as empty and is written again, and a save that fails leaves the previous file and no temporary one. Same output, element by element and in order (`tests/test_python_cross.py`). |
| `lexicon.py` | Repo-learned lexicon in `.verinoda/index/lexicon.json` (D6). Associates words from docstrings, comments, string literals and backticked doc lines with identifier parts (Dunning G² >= 10.83, support >= 2, up to 3 `file:line` sites per pair). It also holds a packaged TR->EN seed dictionary (`verinoda/data/seed_lexicon_tr_en.json`), used only when the English target occurs in the repository; `seed_translates` answers whether an identifier part is a key for a given English word (`baslat` for `start`). Parallel locale files (`lang/en_us.json` + `lang/tr_tr.json`, `locales/en.json` + `locales/tr.json`) add translation pairs: Turkish word -> the English word at the same position, and the Turkish value -> the key's identifier (`via: translation`). Lexicon output is candidates only, never evidence. |
| `snapshot.py` | Commit, branch and dirty flag from one `git status --porcelain=v2 --branch`, the file list from one `git ls-files`, and sha256 per file. Hashes are cached by stat (`file_stat` table: size, mtime_ns) with git's racy-clean rule. Diffs between snapshots drive invalidation. |
| `architecture_map.py` | Views: hierarchy, dependencies (file level; calls, imports, uses, inherits), dataflow (entry -> persistence over `calls`; the project's own entry points first, a detected copy's or reference tree's after them, marked `in`), config (env reads, config files), tests (static reachability; `coverage.xml` if present), history (git log, decision records), impact (reverse reachability; a target is a file of the graph or a name `naming.resolve` resolves exactly, anything else is `unresolved` with its candidates; every name target has a `resolution` row saying what it resolved to or why not, never replaced by a similar name). Every view returns `coverage.method` and `coverage.limits`. |
| `map_text.py` | The plain-text summary of each map view (`verinoda map` without `--json`): folders and packages by symbols, the heaviest dependencies and those between top-level folders, entry -> sink paths, env vars and config files, test reach, recent commits and churn. Every cut list says how much it left out. |
| `testcode.py` | What counts as a test, one rule for every place that recognises one: the map's tests and impact views, `analyze`'s tests intent, the runtime tracer's selection, the change review's test reach, the debug ledger's test files (`test_edited`), guards and decision briefs, search ranking's test demotion and the UI (whose impact lists the same extra test reach as the map's, with its basis). `is_test_file(path)`: test directories (`tests/`, `__tests__/`, `spec/`), Gradle/Maven test source sets (`src/test`, `src/gametest`, ...), pytest/Go/JS/TS/JVM/.NET/Ruby file names, `conftest.py`. `is_test_or_support_file(path)` adds a `testing/` folder outside `src/main/`, for the tracer, the ledger and the review only: projects ship `testing/` as product code (`numpy.testing`, Angular `core/testing`), so the map, search, analyze and guards keep it in the product. Tests per language (`is_test_function`, `test_units`): pytest `test*` functions and methods in test files (not fixtures, whatever their name, not functions of `conftest.py`, not the `Test*` container class); Go `Test`/`Benchmark`/`Example`/`Fuzz` (not `TestMain`); JVM methods annotated `@Test`, `@ParameterizedTest`, `@RepeatedTest`, `@TestFactory`, `@TestTemplate`, `@GameTest`, `@GameTestGenerator` in any source set (JUnit 3 `test*` in test files; a commented-out annotation does not count, and an annotated one-line declaration keeps its annotation); C# `[Test]`/`[Fact]`/...; Rust `#[test]`/`#[...::test]` (a `#[cfg(test)]` module is test code, `is_test_code`); JS/TS the `it()`/`test()` calls of a test file (no graph node: a `TestUnit` named `describe > it`; tagged-template `.each` tables and `fit` included; `.skip`/`.todo`, `xit`/`xtest`/`xdescribe` and a function the file declares under a runner's name left out). Reach the graph does not hold, used by static test reach only (never added to the graph, so search and the other views are unchanged), each step with its kind (`extra_kind`) and words (`reach_basis`): Python calls through a dotted module path (`import pkg.main; pkg.main.run()`; a module named from an import root, and a standard-library name such as `logging.config` only when the project has that top-level package), what the pytest fixtures a test requests call (its parameters and `usefixtures`, looked up in its module, then the `conftest.py` files of its folder and the folders above), Rust calls inside macros of the same file, and for a JS/TS test the symbols its body names from the project files its file imports (a name match; `analyze` says so and grades a reach resting only on it `weak_inference`). `reach(g)` is the static test reach by test id (a same-named test elsewhere is not cited), with the kind of step each reach starts with. Computed once per loaded graph. |
| `retrieval.py` | Question -> a small, justified set of code locations, ranked by `search_index`. `retrieve()` returns JSON for programs; its character budget counts everything returned, and `budget.more` lists further candidates as locators. `render_text()` renders the plain-text context a model reads, skeleton first (D20), and states truncation with the follow-up command. `trace()` gives directed paths in `flow` mode (calls, plus class -> `__init__` construction) or `any` mode, with hints and a next step when an endpoint does not resolve. Endpoints resolve through `naming.resolve`; a similar symbol is kept for plain words only and reported in `fuzzy`. `attach_freshness()` adds the project's changed files (`stale_count`, `stale_files`) and the question's code names that only a changed file spells (`not_in_index`) to a result; `render_text()` prints them under the heading. |
| `when.py` | When a method runs (D47): `when()` walks back over `calls` and `registers` edges to the registration (the event in words from `index.event_label`) or to a method nothing calls; `guards()` reads the conditions around each call from the source (open `if`/`for`/`while` blocks, a braceless `if`, `else`, early exits in a block still open), as written, with their lines. `verinoda when`, MCP `run_when` (full profile), and the callers handler of `analysis.py` for "when does X run" questions. |
| `naming.py` | The one exact resolver for a name a user or agent writes (trace endpoints, `map --view impact` targets, MCP `node_inspect`): the node it names exactly (`retrieval._names_exactly`: a path with backslashes or without its extension, a dotted module, `path::Class.method`, `Class#method`, `name()`, `Owner.name` with a class, module or package owner such as a Java FQN). Candidates come from a lookup built once per graph in one pass (folded bare labels, file nodes, file stems; not question_plan's linking index). Among several: a detected copy or reference tree the text does not name gives way (`copies.roots_not_named`), then test, example, fixture or vendored code (`not_product`), then a function's local definition (`contains` edge or the enclosing function's span); within one file a class is kept over its own constructor and a symbol over the file of that name; still tied is `ambiguous` (candidates listed, none picked). What gave way is in `set_aside` and the note. `module.name` where the module imports `name` is the imported node. A code name that names no node is never replaced by a similar one: `not_indexed` when a file changed since the index spells it (read first) and the indexed version of that file did not (`indexed_spells()`, from the search index's tokens; no candidates are offered), `not_found` when spelled nowhere, `not_a_symbol` (where it occurs, nearest symbols as candidates) when the index spells it as a constant or attribute; plain words are `similar` (with a note) or `unresolved`; the fuzzy scorer runs only for them, once per text (`scored()`). `unindexed_names()` finds a question's code names that only changed files spell (`new`: the indexed version was read and lacks them). |
| `freshness.py` | Which files changed since the index (the latest snapshot), cheap enough for every read: one directory listing per folder holding indexed files, the `file_stat` hashes read in the same query as the snapshot's files, a hash only for a file whose size or time moved; new files are listed from the same listings and kept only when the snapshot's own rule would list them (`git ls-files --cached --others --exclude-standard` with literal pathspecs after `--`: no file of a nested repository or submodule, no untracked build/ or dist/ output; a folder holding `.git` is not walked; a new folder git ignores is not walked either, `git check-ignore`), answers kept per snapshot in `fresh_ignored.json`, so `verinoda update` can always clear what is reported. `note()` / `summary()` give the line and the JSON keys the read commands add. |

### Understanding the question and the references in it

| Module | Role |
|---|---|
| `question_plan.py` | The `verinoda.question_plan/1` contract (D1-D4, D8); the schema ships as package data in `verinoda/schemas/`. `draft()` builds a plan from bilingual rules: clause segmentation, intent cue tables with domain shadowing, Turkish case roles, anaphora via `subject_from`. `check()` is deterministic and offline: schema, integrity (unique ids, DAG, limits), verbatim grounding of mentions and references in the message, version tokens carried by a reference (`version_dropped`), cross-checks against rule intents (warnings only), mention linking in evidence tiers (a mention written as code needs a name tier: otherwise it is at most `weak` when `name_site()` finds it spelled outside imports, and `not_found` with `did_you_mean` when not; a folded label that differs by more than case is `weak`, D31; `name_site()` asks the graph's current `search.db` first, so a name no indexed file spells is answered without reading them; a dotted name whose owner is a class or module of the graph is looked for inside that owner, `_member_site()`; a scan past its time cap never links a similar name), and at most 3 grounded clarifications from fixed TR/EN templates. `store_plan()` records plans immutably; revisions link through `parent_id`. |
| `references/` | Reference resolution (D10-D16): parse -> classify -> bind -> pin -> report, output schema `verinoda.reference_resolution/1`, stored append-only. `mentions.py` extracts TR/EN mentions. `classify.py` is a table-driven classifier (GitHub/GitLab/Codeberg/Bitbucket URL shapes, `owner/repo`, package specs, purl, Go modules, Maven, arXiv, DOI, SWHID). `resolver.py` binds versions to references and reports mismatches M1-M12. `pin.py` holds the precedence ladder. `gitref.py` does qualified ref lookup (`refs/heads/X` vs `refs/tags/X`, a clash is M5) and blobless mirrors. `versions.py` matches version text to tags (PEP 440 when `packaging` is importable). `local.py` reads the versions the project uses from lock files, the project's own venv metadata and runtime pins, without importing project code. `transport.py` is offline-first HTTP: live, cache (`research/http-cache`) and cassette transports, per-host rate-limit blocking, and no credentials stored. `registries.py` does registry lookups, which are pointers only. `contentmatch.py` maps a package to a commit by git blob hashes. `provenance.py` reads PEP 740 source commits (signature not verified). `render.py` gives the compact JSON and text outputs. `evaluate.py` scores the golden corpus. |

### Claims, evidence and trust

| Module | Role |
|---|---|
| `store.py` | SQLite `atlas.db`, schema v6 (migrations v1-v6 applied in order: v5 the decisions tables, v6 the debug ledger; a database a newer Verinoda wrote is refused, and `verinoda doctor` reports it as a failed check). Tables: snapshots and files, claims, evidence, claim-evidence links (with evidence group `grp`), append-only claim history, feedback, experiments, research, memory, analyses, question plans, claim dependencies, evidence locations, runtime runs and calls, reference resolutions, decisions, decision briefs and decision answers (v5), debug sessions and attempts (v6). Derived caches: `file_facts`, `resolutions`, `file_stat`. Triggers reject deletes on every audited table, updates of history, links, plan bodies, evidence locations and reference resolutions, and (v4) any change to a claim's `text` or `created_at`; (v6) debug attempts are append-only and a session's symptom, command and base never change (a closed session stays closed). |
| `evidence.py` | Evidence construction and re-checking. Source ranks run from 1 (project source) to 7 (secondary). `static_resolution` has rank 2. `graph_edge`, `user_feedback`, `search_result`, `model_summary` and `secondary` never verify. `user_feedback`, `search_result` and `model_summary` are not even support for an inference. Cited lines carry an anchor, so `check_source()` tells `same` / `moved` / `changed` / `gone` / `ambiguous` apart. Markdown lines are `design_doc`. |
| `anchors.py` | Symbol facts cached by file sha256 (D23): per-definition signature, body (docstring removed, nested definitions Merkle-hashed) and doc hashes; per-file import bindings, module statements and Markdown sections. Python uses its own AST serializer (not `ast.dump`); other languages hash tree-sitter leaf sequences. Evidence anchors (D25) and `relocate()`: a `changed` anchor is a candidate location only, never verification. An unsupported file has no facts, and callers fall back to file level. |
| `entail.py` | Mechanical entailment grades `full` / `partial` / `none` per claim kind (D26). Relation: an AST call at the cited line inside the claimed caller whose callee is the target or an import alias of it; a method on an unresolved receiver is `partial`; a definitive static resolution or an observed runtime call is `full`. Location: the definition spans exactly the cited lines. Config: an env read of that literal. Flow: every hop and the sink. Behaviour: an order "A before B in F" by the first calls in F's whole body (`call_order`), a pattern by the cited line. Tests/impact: `partial` at most. Decision/history: `partial` at most, and only with attribution. `general`: term coverage, a labelled heuristic that is `partial` at most; only a verbatim `contains:` quote is `full` (D31). Written text (`spec.free_text`) must bind every role: one caller and the callee in a clear EN/TR form (`relation_parse`; no form, no guess and no contradiction), a config text's subject to the name the read is bound to (`env_bindings`, `config_binding`); a negation, quantifier, order, condition, count or uncompared number it adds keeps it `partial` (`unchecked_statements`), so does a code name the check does not bind (`unchecked_names`; another callee or clause counts when the caller's body calls it), and a quote verifies only the quoted text. `order_proposition()` reads explicit order forms only; `call_order()` keeps calls in nested defs and lambdas out of F's order. `caller_scope()` reads a caller's whole body for direct calls. |
| `claims.py` | Status rules in `check_status()`, which every stored status change passes through (`Claims.set_status` always grades the claim), so irrelevant evidence cannot verify a claim on any path. A verified status needs one evidence group that is verifying, fresh and fully graded. `strong_inference` needs relevant non-pointer support; for written text that no typed check covers, a `full` grade (D31), so its word overlap gives `weak_inference` at most. A claim with no evidence is `unknown`. Only a definitive refutation contradicts; a heuristic one lowers one step. `assessed` and `ceiling` live in `spec`, and critique's `penalty` is kept. Dependencies are derived per claim kind (`derive_deps`: signature, body, bindings, module statements, sections, test-set hash; file level as fallback). `assess_change()` / `invalidate_stale()` mark a claim stale only when a facet it depends on changed or its evidence no longer relocates. Otherwise the claim is re-bound to the new snapshot and its history says so. |
| `callsite.py` | Legacy name-level check that a cited line names the call target, import aliases included. The analysis prefers `entail.call_site`. |
| `critique.py` | Tries to break a claim (D27): support, entailment, source re-check, existence of cited commits/runs, graph-only support, call site (AST), ambiguity of INFERRED targets, exclusivity (through `guards.exclusive_hits`: a hit must be code, not a comment or string, and a dotted-call pattern also catches import-alias calls), facet staleness, and counter-hypothesis probes (for example "a call after an earlier raise in a `pytest.raises` block cannot run"). A definitive failure attaches refuting evidence and contradicts; a heuristic one lowers one step with an uncertainty. A call site without the call is checked against the caller's whole body: no call there is definitive and states its scope, a call at another line is only a warning. `check_at_creation()` runs the definitive, scope-stated checks (call site and caller body, config binding, order, a written name that the file neither binds nor spells) when `claim add` creates a claim (D31); a caller read from text whose definition is not found, a nested call in an order and a name spelled but unbound are heuristic only. Status and confidence only go down. Critique is idempotent on an unchanged claim and never restores a stale or contradicted claim (`verify` does). Accepts `current_files` so one freshness pass serves the whole analysis. |
| `precise.py` | Optional (`verinoda[precise]` = jedi, D29). `resolve_call(repo, path, line, target)` returns `definitive` / `dynamic` / `ambiguous` / `external` / `unresolved`, and with the graph's target also `confirms` / `refutes` / `undetermined`. Only a definitive answer confirms or refutes; a method on a parameter or local receiver is `dynamic`. Results are cached in `resolutions` by file sha256. A per-analysis `Budget` (default 20 sites or 1.5 s) bounds fresh work, and a site skipped for budget gets the uncertainty "not resolved (budget)". Without jedi, every call answers `None`. |
| `codecheck.py` | `verinoda check` / `verinoda api` and MCP `code_check` / `api_members` (D32; needs the `precise` extra). Collects the sites of a file, a diff or a snippet - imports, from-imports, attribute loads, keyword arguments, constant keys read from the dict literal a function returns - resolves them with jedi in the project's own environment and gives each one `exists` / `absent` / `unknown` / `not_installed` / `guarded`. `absent` only from a closed container (a module with no `__getattr__`, `exec` or `globals()` writes and closed star imports; a class object; a direct instance or a single unreassigned local that is not handed to code that sets attributes; one known signature without `**kwargs` or an unknown decorator), and only after jedi also found nothing; then with nearest names (rapidfuzz) and where the name is defined elsewhere. ### Loops and entry points

| Module | Role |
|---|---|
| `workflow.py` | `init`, `scan`, `update`, `verify`. After every build it refreshes the derived data: `search_index.update`, then `lexicon.build` and `anchors.update_facts` (errors are reported per step, never raised). A refused or failed index rebuild is reported, not swallowed. `scan` and `update` hold the project's build lock (`buildlock`): a second caller waits up to `wait` seconds and otherwise returns `mode: busy` with who is building, having done nothing. `verify` re-checks cited lines through their anchors and uses `claims.assess_change` for facet-level decisions. |
| `buildlock.py` | One index build at a time per project: an operating-system file lock on `.verinoda/build.lock` (`msvcrt` / `flock`; released with a crashed process), re-entrant in the holding thread, the holder described in `build.owner.json`. The CLI's scan/update (and `analyze --refresh inline`) wait up to 10 minutes and say so; `decide check`'s refresh waits 120 s and MCP `decision_check`'s 30 s (`GATE_WAIT_SECONDS`), after which its no_edge guards are `unknown` and the exit is 2; analyze in `auto` mode on a big project and `ui --watch` do not wait; MCP `index_update` waits 30 s. `build_stats.json` records how long the last graph build took (analyze's estimate). |
| `analysis.py` | The budgeted loop (D7). Refresh the index if the tree changed, outside the answer's time budget; a refresh expected to be slow (the last graph build took over 15 s, or over 200 files changed) or blocked by another build is not run: the answer comes from the previous index, says which files are stale (`index_refresh`, an unknown) and marks each claim that cites one (`refresh=auto`; `inline` and `skip` force it). Draft or parse the plan and check it (an invalid plan stops; `needs_clarification` returns the questions and writes no claim). Then, per sub-question in dependency order, with a share of the budget: retrieval seeded by linked mentions and lexicon expansions, a relevance test (irrelevant items become an `unknown` with a next step), location and relation claims, and the intent handler (flow, dataflow, callers, config, tests with optional test run or `observe`, why/history, impact, behaviour, reference comparison resolved offline; a choice - intent `decide` - goes to the decision brief, runs no retrieval and is always `human_decision_required`; a sub-question of another intent whose words ask for a choice in so many words (`question_plan.asks_for_choice`) keeps its claims as context but gets the brief and the same verdict, and one whose words only may ask for one gets a note and a verdict of at most `met_with_inference`). Relation call sites are graded by `entail.call_site` and, when installed, by `precise`. Critique follows. Each sub-question gets a verdict against its `done_when`. Every returned claim, unknown, step and critique entry is charged to the context budget. `plan audit` recomputes the verdicts later. |
| `analysis_view.py` | What a model reads of an analysis (D20): `render_text` (the default `verinoda analyze` output: snapshot, how the question was understood, one block per sub-question with its verdict, answer claims and unknowns, the other claims, then the passages `query` gives) and `lean` (the MCP `analyze` response, the same content as JSON). Claims keep id, status and text; confidence only below the status's cap, evidence only where it adds a locator the text lacks, uncertainties and not-challenged reasons always; a verified context claim whose cited lines a printed passage window shows is left out and counted (`lean_capped` recounts on the passage lines the MCP cap keeps). Steps, usage (unless a budget ran out), the question echo and per-sub-question plumbing stay in `--json`. |
| `verdict_gate.py` | Honest verdicts (D39), run by `analysis.py` after the claims are made: marks answering claims that cannot make a sub-question `met` (a definition for a question that is not about where something is defined, a definition of X for "which code uses X", code of other classes for "where is X ticked", callers of another callee, a config read without the question's words, evidence only in a reference tree, a detected copy or a vendored folder) and caps the verdict at `met_with_inference` when call sites of the callee stayed unresolved (a text search of the indexed code files) or a "why" has only commit lines; says why in unknowns. Also holds the set-difference test that `analysis._exclusive_guard` refuses with. Only lowers a verdict, never drops a claim. |
| `debug.py` | The debug ledger (D34): `start` opens a session (symptom, repro command, base commit) and runs the repro once; `attempt` (`debug try`) records every later run - through `experiments.run`, or a run the agent reports (`observed_output` + exit code + the command it ran: `run_by=agent`, output sha256 kept, evidence type `agent_report`, never verifying, and outweighed by Verinoda's own runs of the same tree). Each attempt stores its tree (`treestate`: tree hash and code hash), patch vs base (`runs/<attempt>/change.patch`), touched symbols, failure signature (`failsig`; pytest runs load the `verinoda_failsig` plugin, which also records each test's outcome, and with `--trace` the call tracer) and the loop findings, stop and strategies computed at that moment. Strategies run on request and are recorded as attempts: `differential` (the repro on a copy of the base with the symptom's test held fixed - a failing test's file that differs at the base is laid over it; inconclusive when the failing tests did not run there; otherwise hunks ranked: code before tests and before comment-only files, then by the failure's traceback / the failing tests' reach, with "already there at attempt 0" first while the symptom is unchanged; with `--trace` also the failing tests' observed calls at the base vs in the failing tree), `bisect` (both ends run or taken from a recorded run first, then first-parent binary search in commit copies, skips, cost), `rerun` (pass rate over Verinoda's runs) and `observe` (a traced probe: which failing tests reached each edited function, which were called elsewhere, and the observed call chain into the crash symbol); a stop also lists `narrowing` suspects (traceback and changed symbols with evidence; a changed function a complete trace shows called nowhere, with no child process started, is ruled out), and a narrowed repro that passes a test the full repro failed on the same tree reports `order_dependent`. Never says "fixed"; only a pass of the session's own repro command counts as one, and closing as resolved needs such a pass on the current tree in which the earlier failing tests passed (not skipped), no Verinoda run of that tree that did not pass, and the user's recorded acceptance (`--accept-test-edit`) when tests changed since attempt 0. Verinoda never edits or reverts the user's files. |
| `probe.py` | The behaviour probe (D36, `verinoda probe`, MCP `change_probe`): for one changed Python function (or every function changed against a base) the eligibility check (Python functions, static/class methods, instance methods with a recipe; anything else `unsupported` with the reason), the side-effect gate (`probe_gate`), the corpus (`probe_inputs`, one JSON corpus with its sha256 for both sides, written to `runs/<probe id>/corpus.json`), the runs (`experiments.run` with the plugin: the base as a commit copy, the working tree as the default copy, resumed after a hang), the oracles (difference classes, undeclared exceptions, properties, nondeterminism, growth with `scaling`), a confirmation pair of runs for the simplest examples of every class (a class that does not reproduce is `unstable`, never a difference; float drift alone is the low-priority status `numeric_drift_only`; a plugin failure or a module name taken by another module is `inconclusive`; a probe where fewer than half of the inputs returned or raised on both sides is `inconclusive`; `--changed` is `incomplete`, no pass, when a changed function was not compared or a changed file does not parse), the claims (a confirmed class is a `behaviour` claim with `experiment_verified` probe evidence scoped to its runs; "no difference" is `weak_inference`) and `--emit-test` text. Timeouts are listed, never a difference, unless `scaling` puts performance in scope. |
| `probe_inputs.py` | Inputs from syntax trees only (never an import of the project): type descriptors from annotations (scalars, Optional/Union, containers, Literal, enum members from the class body, project classes through recipes: constructor calls with literal arguments found in the code or tests), refined by call-site literals (followed two callers up); boundaries mined from comparisons, `len` checks, slices, `min`/`max`, rounding calls and compared strings, with constants resolved through module assignments, imports and `os.environ.get` defaults (the defining line kept); standard edges; then hypothesis (seeded, generate phase, no database) or a fixed pseudo-random list when it is not installed. The JSON encoding (`encode`, `to_source`) is shared with the plugin's `decode`. |
| `probe_gate.py` | The probe's static side-effect gate: the target's closure (4 levels through imports, re-exports, `self.method()`, constructors and parameters annotated with a project class; `guards._PyIndex` resolves the names), the recipes' constructors, and the module-level statements of every project module they import. | `looprules.py` | Deterministic loop rules over recorded attempts, each citing the attempts it rests on. Definitive (set `stop`; on a passing attempt only the two test rules do): `tree_reverted` (the tree, or the code apart from comments/docstrings/formatting, is back to an earlier attempt's), `signature_recurred`, `no_progress` (since the last pass), `test_edited` (assertions changed, tests switched off, test selection changed in the configuration; formatting alone does not count), `failing_tests_skipped` (earlier failing tests skipped, xfailed or not run), `off_path` (complete trace; the edited functions called nowhere in the run, no child process). | `failsig.py` | Failure signatures: per failing test the exception type, message, crash location (innermost in-repository frame) mapped to `path::symbol` with `anchors.enclosing`, and the in-repo frames. | `treestate.py` | Tree identity for runs (cross-cutting building block): content id = sha256 of CRLF-normalised bytes, tree hash over (path, id), a code hash in which a Python file counts by its syntax tree without docstrings (comments, docstrings and formatting aside), changes vs a base commit as `{path: id or None}`, a content-addressed blob store for changed files (`runs/blobs/`), the base commit's ids cached per commit (`runs/base-ids/`), unified patches, hunks mapped to the definitions they touch. | `review.py` | `verinoda review` / MCP `change_review` (D35): the blast radius of a change by concern. ## Invariants

1. **A verified status needs relevant, fresh, verifying evidence, enforced in
   one place.** `claims.check_status` requires one evidence group that is
   verifying, fresh (relocated through its anchor when the code only moved)
   and graded `full` by `entail`. Every stored status change goes through it
   with the claim, whether it comes from the Claims API, attach + reassess,
   `verify`, `feedback resolve`, experiment runs, runtime observations or MCP.
   This is acceptance criterion 6: unrelated evidence (a passing but unrelated
   test, a foreign evidence id) cannot raise a claim.
2. **A graph edge alone never verifies.** `EXTRACTED` / `INFERRED` edges are
   at most support for `strong_inference`. Search results, model summaries and
   user feedback are not even that.
3. **No evidence means `unknown`.** Insufficient evidence produces `unknown`
   with a next step, including when the budget runs out or retrieval finds
   nothing relevant.
4. **Staleness is facet-level.** A claim goes `stale` on the next
   `update` / `scan` / `analyze` / `verify` when a facet it depends on changed
   (signature, body, binding, module statement, section, test set) or its
   cited lines no longer relocate to identical text. If its files changed but
   its facets did not, it is re-bound to the new snapshot without a status
   change, and the history says so. Files without facts fall back to
   file-level rules.
5. **Evidence is anchored.** A cited line that only moved is re-found at exact
   new lines (`moved`). A `changed` anchor is a candidate location, never
   verification. A duplicated line is `ambiguous`, never relocated by guess.
   Evidence rows are immutable; relocations are appended.
6. **Definitive vs heuristic refutation.** Only a definitive refutation, an
   exhaustive check within a stated scope, makes a claim `contradicted`.
   Examples: no call to the target on the cited line, the line is outside the
   claimed caller, the "only" pattern occurs elsewhere, a precise resolver's
   definitive different target. A heuristic refutation lowers the claim one
   step and adds an uncertainty.
7. **Critique never raises confidence** and never restores a stale or
   contradicted claim. Re-verification cannot go above the assessed ceiling or
   undo critique's penalty.
8. **Nothing is deleted.** Claims change status, memories are invalidated,
   corrections supersede. A claim's text is immutable (schema v4). Plans,
   reference resolutions, runtime runs, evidence locations and debug
   attempts are append-only.
9. **Heuristics are labelled**: `coverage.limits`, `uncertainties`,
   `derived_by` (receiver pass, lexicon, seed dictionary, rules), the
   `general` entailment grade, and query expansions reported in the output
   header.
10. **Runtime observations are run-scoped.** "Observed in run R at commit C"
    never supports an "always" claim, and test-double edges never support
    production edges.
11. **References are pinned, never floated silently.** A named version never
    falls back to the default branch. Every mention is accounted for, and
    every conflict (M1-M12) is reported.
12. **A debug attempt is a recorded run on an identified tree, never a verdict.**
    The ledger says "the repro command passed at tree T in run R" and what was
    not run, never "fixed", and only for the session's own repro command (a
    narrowed command's pass is reported as that command's); a run in which
    earlier failing tests were skipped or deselected is no pass; a run the
    agent reports is labelled, never verifies anything and never outweighs
    Verinoda's own runs of the same tree; an unparsable failure is unknown,
    never "the same"; Verinoda never edits or reverts the user's files.
13. **A probe finding is a run-scoped behaviour difference, never a verdict.**
    "On input X, the base returned A and the working tree B, in runs R1/R2
    (reproduced in R3/R4)"; never "always", never "a bug" (whether a change is
    intended is the user's call). "No difference in N inputs" is
    `weak_inference` with the inputs stated. Project code is never imported in
    Verinoda's process; it runs only through `experiments.run`, after a static
    gate, under an audit hook that blocks side effects. Refused, unsupported
    and inconclusive probes never become "passed".
14. **A name is answered about only when it names that thing, and a stale index
    is never silent.** trace, `map --view impact` and `node_inspect` resolve a
    written name exactly (`naming.resolve`); a copy of the project never
    competes with the original, several matches are listed rather than
    picked, and impact is never computed for a similar name. Reading commands
    say which files changed since the index; a code name only a changed file
    spells is "not in the index yet". One index build runs at a time per
    project, and a second caller is told who is building, never to use
    `--force`.
